- **学び**: 「参照実装と突き合わせる」方法論は、**参照実装を動かせる場所**と

- **モジュール**: params.jl
- **症状**: 「パラメータの具体値は必ず仕様書の表から引き、出典（表番号）を
  コメントに書く」という要件を、**表番号の部分だけ満たせていない**。

- **切り分け**:

  - [x] `nvlpubs.nist.gov`（FIPS 206 ipd PDF）→ 403

  - [x] `eprint.iacr.org` → 403

  試したが、同じ egress proxy を通っており同じく 403。Web 検索は通るのに
  Web 取得は通らないので、一瞬「取得できているのに解析に失敗している」のかと
  勘違いした。ツールのエラーメッセージ（`EGRESS_BLOCKED`）をちゃんと読めば
  すぐ分かった話。
- **原因**: 実行環境のネットワークポリシー。仕様書 PDF のホストが全滅している。

    Python 参照実装（`tprest/falcon.py`）で、`sig_bound` と `sig_bytelen` が
    完全一致することを確認済み（`34034726` / `666`）。
  - 各定数に `[C-ref] common.c:250` のような **実際に読んだ file:line** を付けた。

    PDF が読める環境で埋めたら、このテストが「埋め忘れ」ではなく
    「埋めたのにテストを直し忘れ」で赤くなる。それでよい。

  - byte 長を C のマクロ（Julia に転記した `c_pubkey_size` 等）と logn=2..10 で照合

  - `sigma == 1.17 * sqrt(q) * sigma_min`
  - `sig_bound / (2n sigma^2)` が 1〜2 の間（桁を間違えたら落ちる）
- **学び**: 「出典を書け」という指示の本質は表番号そのものではなく
  **「記憶から書くな」**。到達できる一次資料が変われば出典の形式も変わる。
  ただし**形式を勝手に緩めて黙っていてはいけない**ので、`spec_ref` を
  構造体のフィールドとして残し、テストで見えるようにした。

## [2026-08-17] #003 params: sigma_min の閉じた式を逆算で特定した

- **モジュール**: params.jl
- **症状**: バグではない。定数を「記憶から書かない」ために、
  `sigma_min = 1.2778336969128337` が**どの式から来ているのか**を
  仕様書なしで確定させる必要があった。
- **再現条件**: —
- **切り分け**:
  - [x] 平滑化パラメータの標準形 `eta_eps(Z) = (1/pi) sqrt(ln(2(1+1/eps))/2)` を仮定
  - [x] 参照値を代入して `eps` を逆算 → `log2(1/eps) = 45.50000000002967` (n=512),
        `47.00000000002099` (n=1024)
  - [→] 45.5 と 47.0 という**ほぼ厳密な値**が出た。差 1.5 = 1.5*(logn の差 1)、
        切片 32 → `1/eps = 2^32 * n^(3/2)`、すなわち `eps = 1/sqrt(2^64 * n^3)`
- **外した仮説**:
  - 最初 `sigma = 1.17 * sqrt(q/(2n))` だと思い込んでいた（`ntrugen.py` の
    コメントに出てくる式なので）。n=512 で 4.05 にしかならず、参照値 165.7 と
    2 桁違う。**これは f, g のサンプリング幅 `sigma_fg` であって
    署名の幅 `sigma` ではない**。FALCON には σ が 4 種類（`sigma`, `sigma_min`,
    `sigma_max`, `sigma_fg`）あり、しかも `sigma_fg` は「4096 個サンプルして
    `4096/n` 個ずつ畳む」という実装都合の基底幅 `1.43300980528773` を持つ。
    ここを混ぜたのが 1 つ目の外し。
  - 次に `eta` の中の `2` を `2n`（`Z^{2n}` の平滑化）だと思って試したが、
    `log2(1/eps)` が 35.5 / 35.0 と汚い値になった。`Z^1` の式が正しい。
- **原因**: （バグではない）
- **修正**: `falcon_eps(n) = 1/sqrt(2^64 * n^3)` と `smoothing_eta(eps)` を
  params.jl に書き、`sigma = 1.17 * sqrt(q) * sigma_min` も確認した
  （1.17 は `ntrugen.py:232` の Gram-Schmidt 上限 `(1.17^2)*q` と同じ定数）。
  閉じた式は Float64 評価で参照値と相対 3e-13 まで一致する。**完全一致では
  ないので、権威ある値は引き続き参照実装のリテラル**とし、閉じた式は
  「桁を打ち間違えたら落ちる」ためのテストに使う。
- **回帰テスト**: `test/test_params.jl` の
  `"sigma_min is the smoothing parameter of Z"` と
  `"sigma = 1.17 * sqrt(q) * sigma_min"` と `"sigma_fg and its base"`。
- **学び**: σ が 4 つある。**どの Gaussian の話をしているかを毎回言え。**
  格子上の Gaussian（`sigma`）、Z 上の各座標の Gaussian（`sigma_min`〜`sigma_max`）、
  鍵生成の f,g の Gaussian（`sigma_fg`）、そしてその実装上の基底幅
  （`SIGMA_FG_BASE`）は全部別物で、単位も意味も違う。
  `1.17` だけが 3 つをまたいで現れる（Gram-Schmidt ノルムの上限）ので、
  この定数を見たら「どの σ の話か」を確認する合図にする。

## [2026-08-17] #004 shake: SHA.jl の SHAKE256 は「squeeze の続き」ができない

- **モジュール**: shake.jl
- **症状**: バグではなく設計上の制約。FALCON は SHAKE256 を XOF として使い、
  hash-to-point では**必要な分だけ吸い出しては棄却する**ので、
  「途中まで squeeze して、足りなければ続きを squeeze する」API が要る。
  `SHA.jl` にはそれが無い（`shake256(data, d)` の一発形しかなく、
  `digest!` は呼ぶたびに padding を再適用するので同じ context を 2 度
  squeeze できない）。
- **再現条件**: —
- **切り分け**:
  - [x] `SHA.jl` の `src/shake.jl` を読んだ。`digest!(ctx, d, p)` は
        `d > blocklen` のときは内部で継続 squeeze するが、
        呼び出しをまたいだ継続はできない構造（`used` フラグと再 padding）。
  - [→] XOF の定義から、`SHAKE256(m, d1)` は `SHAKE256(m, d2)` (d1<d2) の
        **prefix** になる。ならばメッセージを保持して長さを倍々にしながら
        取り直せばよい。
- **外した仮説**: なし（最初からこの方針）。
- **原因**: （バグではない）
- **修正**: `SHAKE256XOF` を「吸収済みメッセージ + 生成済みバッファ + 位置」で
  持ち、足りなくなったら倍の長さで `SHA.shake256` を取り直す実装にした。
  償却 O(N) だが、取り直しのたびにメッセージを再吸収するので厳密には
  O(N + |m| log N)。FALCON のサイズでは無視できる。
- **回帰テスト**: `test/test_shake.jl` の `"SHAKE256 prefix property"`。
  **これは FIPS 202 の性質ではなく `SHA.jl` の実装への仮定**なので、
  hashlib 由来のベクタで明示的に検証する。ここが落ちたら
  `squeeze!` を細工するのではなく Keccak-f[1600] を自前で書くこと、
  とテストのコメントに書いた。
- **学び**: 標準ライブラリで代用するとき、**代用が壊れる条件をテストに書いておく**。
  「たぶん prefix になっているはず」で通してしまうと、後で hash-to-point が
  ときどきずれるという最悪の形で返ってくる。

## [2026-08-17] #005 shake: 参照 PRNG の randombytes は「余りを捨てる」

- **モジュール**: shake.jl
- **症状**: バグではなく、移植前に潰しておいた罠。
  `scripts/pyref/rng.py` の `randombytes(k)` は、バッファ残量が `k` に
  満たないとき**残りを連結せず捨てて**新しい 512 バイトを生成する。
- **再現条件**: —
- **切り分け**:
  - [x] `rng.py:111-122` を精読
  - [x] `out = "".join(out[i:i+2] for i in range(2*k-2,-1,-2))` のあと
        `bytes.fromhex(out)[::-1]` している。**この 2 つの反転は打ち消し合って
        恒等写像**。実質「バッファ先頭 k バイトを返して k 進める」だけ。
  - [→] 意味があるのは反転ではなく `if 2*k > len(self.hexbytes): 再生成` の分岐
- **外した仮説**: 反転処理に意味があると思って 15 分読んだ。
  C 参照実装がワード単位で消費するのに合わせた名残で、
  バイト列としては何もしていない。**「変な処理があったら、まず恒等でないか
  確かめる」**べきだった。
- **原因**: （バグではない）
- **修正**: Julia 側は素直に「バッファ先頭 k バイト、足りなければ捨てて再生成」で
  実装し、反転は再現しない。その主張は KAT で担保する。
- **回帰テスト**: `test/vectors/chacha20_kat.jl` に
  `[511, 8]` と `[255,255,255]` という**境界をまたぐ要求パターン**を入れた。
  加えて `test_shake.jl` の `"ChaCha20 buffer boundary behaviour"` が
  「捨てている」ことを直接主張している。
- **学び**: 参照実装の「意味の無いコード」と「意味のあるコード」を分けてから移植する。
  ただし**分けた根拠はテストにする**。恒等だと判断した処理が実は恒等でなかった
  場合、それは KAT でしか気づけない。

## [2026-08-17] #006 ntt: 根テーブルの順序規約を逆算で特定し、ハードコードをやめた

- **モジュール**: ntt.jl
- **症状**: バグではない。参照実装は `roots_dict_Zq`（n=2..1024、計 2046 個の
  定数）を sage スクリプトで生成してハードコードしている。これをそのまま
  写経すると「なぜこの順序なのか」が永久に分からなくなるので、
  **生成則を特定して 20 行の再帰に置き換えられるか**を調べた。
- **再現条件**: —
- **切り分け**:
  - [x] `roots_dict_Zq[n]` の各要素が `x^n+1` の根か → 全 n で成立
  - [x] `ntt(f)[j] == f(roots[j]) mod q` か → 成立。**NTT は素直な多点評価**で、
        ビット反転などの並べ替えは入っていない
  - [x] ペアの構造 → `w[2i] + w[2i+1] == q`（つまり `±w`）が全 n で成立
  - [x] 親子関係 → `w_{2n}[2i]^2 == w_n[i]` が全 n で成立
  - [→] ペア内の順序 → **小さい剰余が先**が全 n・全ペアで成立
- **外した仮説**: 最初「Dilithium と同じくビット反転順だろう」と決めつけて、
  ビット反転を適用してから比較していた。当然合わない。
  FALCON の Python 参照実装は**自然順（塔の順）**であって、ビット反転しない。
  ビット反転が出てくるのは C 実装のほう（下の #007）。
  「NTT といえばビット反転」という Dilithium で刷り込まれた前提が邪魔をした。
- **原因**: （バグではない）
- **修正**: ζ = 7（12289 を法とする位数 2048 の最小の元）から、指数の再帰
  `e ↦ {e/2, e/2 + 1024}` に「値の小さいほうを先」の規則を付けてテーブルを
  生成する実装にした。`NTT_ZETA = 7` はリテラルで置きつつ、
  `find_ntt_zeta()` で再計算できるようにしてテストで検証している。
- **回帰テスト**: `test/test_ntt.jl` の `"root tables match the reference"`。
  生成表が参照実装のハードコード表と n=2..1024 で完全一致することに加え、
  `w^n = -1`・ペアが `(r, q-r)`・小さいほうが先・`w_{2n}[2i]^2 = w_n[i]` を
  すべて主張している。加えて `"NTT product agrees with the schoolbook product"`
  が**順序**を固定する（順序を入れ替えても往復テストは通ってしまうが、
  poly.jl との積の一致は通らない）。
- **学び**: **往復テストは NTT の正しさをほとんど何も保証しない。**
  評価点が全部間違っていても `intt(ntt(f)) == f` は成立する。
  保証するのは (a) 定義そのもの（Horner で評価して一致するか）と
  (b) 独立実装との積の一致、の 2 つ。テストを書くときはこの 2 つを必ず入れる。

## [2026-08-17] #007 ntt: C 参照実装と Python 参照実装で NTT の係数順序が違う

- **モジュール**: ntt.jl
- **症状**: モジュール 4 の突き合わせ相手を C にするか Python にするかで
  詰まった。C の `Zf(to_ntt_monty)`（`inner.h:579`）はビット反転順かつ
  Montgomery 形式で、Python 版の自然順・素直な剰余とは**係数の並びも値も違う**。
- **再現条件**: —
- **切り分け**:
  - [x] Python 版の出力 = 自然順の多点評価（#006 で確認済み）
  - [x] C 版は関数名に `monty` とあり、Montgomery 領域であることが明示されている
  - [→] C と比べるには「置換 + Montgomery 係数の補正」という**2 段階の変換**が
        要る。それ自体がバグの温床になる
- **外した仮説**: 「参照実装は C が正典なのだから C と突き合わせるべき」と
  考えていたが、**突き合わせの目的は仕様の理解であって C の再現ではない**。
  順序と表現が違うものを無理に合わせると、不一致が出たときに
  「移植のバグ」なのか「補正のバグ」なのか切り分けられなくなる。
- **原因**: （バグではない。設計判断の記録）
- **修正**: モジュール 4 の一次オラクルは **Python 参照実装**にした。
  C との突き合わせはモジュール 5（fft.jl）以降で行う
  （`Zf(FFT)` / `Zf(iFFT)` は順序の問題が無いため）。
  この判断の理由を `src/ntt.jl` 冒頭のコメントにも残した。
- **回帰テスト**: なし（設計判断）。ただし `docs/build_cref_macos.md` の
  関数対応表に、モジュール 3・4 に対応する C 関数が無い理由を明記した。
- **学び**: 「参照実装と突き合わせる」と言うとき、**どの参照実装のどの表現と**
  突き合わせるのかを毎回決める必要がある。速い実装（C）と読める実装（Python）は
  同じアルゴリズムの別表現であって、後者のほうが仕様に近い。
  FALCON はその 2 つを両方公開している珍しい例。

## [2026-08-17] #008 方法論: Julia を動かせない環境で、書いた Julia を Python に逐語移植して検証した

- **モジュール**: （方法論）
- **症状**: #001 の通り Julia が動かせないので、`ntt.jl` を書いても
  インデックスがずれていないか確かめる手段が無い。1-based ↔ 0-based の
  変換は移植で最も事故が多い箇所なのに、そこが未検証のまま積み上がる。
- **再現条件**: —
- **切り分け**:
  - [x] golden vector は Python 参照実装から生成しているので、**期待値**は正しい
  - [→] 検証できていないのは**Julia 側のアルゴリズム**。ならば、
        書いた Julia コードを Python に**逐語**（1:1、行対応で）移植して、
        参照実装と比較すればアルゴリズムは検証できる
- **外した仮説**: 最初は「型さえ合っていれば読み直しで十分」と思っていたが、
  `merge_ntt` の `w[2i-1]`（Julia）↔ `w[2i]`（Python）の対応は

  - [x] θ・ρ・π・χ・ι の添字を手で追った → 妥当
  - [x] ラウンド定数を印字 → `RC[1..4] = [1, 0, 0, 0]` のような
        **ほとんどゼロの列**。正解は `1, 8082, 800000000000808a, 8000000080008000`

        `lfsr <<= 1` は UInt8 の中で桁あふれを捨てるので、
        直後の `if (lfsr & 0x100) != 0` は**永遠に偽**。

  同じ間違いをした。**添字は目立つので先に疑いたくなる。**

## [2026-08-17] #017 shake: ChaCha20 のカウンタ溢れで、Python 参照実装のほうが間違っていた

- **モジュール**: shake.jl / scripts/gen_vectors.py
- **症状**: ChaCha20 の KAT が 12 件失敗。しかも**全部が 4 番目のシード**
  （`b"\xff" * 56`）の分。他の 3 シードは全 44 件合格。
- **再現条件**: シードが全 0xff のときのみ、100%。
- **切り分け**:
  - [x] ブロック関数を直接比較 → block0, block1 とも Julia と Python で
        **完全一致**。カウンタ初期値も一致
  - [x] では何が違うのか → 出力先頭 4 バイトは合い、5 バイト目から違う。
        インターリーブにより 5〜8 バイト目は **block1 の word0**
  - [→] シードが全 0xff だと `ctr = s[12] + (s[13]<<32) = 2^64 - 1`。
        **次のブロックで溢れる**。
        Python は多倍長なので `ctr = 2^64` になり、
        `ctr >> 32 = 2^32` を state に XOR して **33 ビットの値**を作る。
        Julia は `UInt64` なので 0 に巻き戻る
  - [x] **どちらが正しいのか** → C 参照実装 `rng.c` の `prng_refill` を読んだ:
        `uint64_t cc = ...; t.w[u] = (uint32_t)(cc + u); ...; cc + 8`
        → **C は uint64_t で巻き戻る**。Julia が正しい
- **外した仮説**:
  - 最初「自分のインターリーブが間違っている」と決めつけた。
    5 バイト目からずれる = ワード境界 = インターリーブ、という短絡。
    しかし block0/block1 を直接比較したら一致していたので、そこではなかった。
  - 次に「巻き戻りは自分のバグ」と思った。**逆だった。**
    参照実装（Python）のほうが実機と違う挙動をしていた。
- **原因**: Python 参照実装が多倍長整数を使っており、
  64 ビットカウンタの巻き戻りを再現しない。全 0xff シードという
  病的な入力でのみ顕在化する。
- **修正**: `scripts/gen_vectors.py` で `ChaCha20` を派生させ、
  `update()` の頭で `self.ctr &= (1<<64)-1` するようにした。
  **C 参照実装が正典**なので、golden vector 側を直した。
  Julia のコードは変更していない（元から正しかった）。
  派生クラスの docstring に理由と C の該当箇所を書いた。
- **回帰テスト**: 全 0xff シードのケースはそのまま KAT に残っている
  （むしろ**これが巻き戻りの回帰テスト**になった）。
- **学び**: **参照実装が間違っていることがある。**
  「テストが落ちた ⇒ 自分が間違い」は 9 割正しいが 10 割ではない。
  切り分けの決め手は「3 番目の独立な実装（C）に聞く」だった。
  参照実装が 2 つあることの価値がここで出た。
  そして**多倍長言語で書かれた参照実装は、固定幅の挙動を隠す**。
  Python の int には桁あふれが無い。移植先には有る。
