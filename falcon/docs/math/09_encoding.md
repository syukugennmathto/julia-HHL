# モジュール 9: シリアライズ ― ここだけが規範的に固定されている

## 9.1 このモジュールが退屈でない理由

2 つある。

### (1) 浮動小数点に触れない唯一の部分

モジュール 5 以降はすべて浮動小数点に依存し、
モジュール 8 でその代償を実測した ―
**定数表の 1 ulp の違いが署名を変える**（#025）。

エンコーディングは float に一切触れない。
だから **C 参照実装のバイト列を厳密に再現できる**。
`test/vectors/cref_kat.jl` には、C 参照実装が固定シードから生成し、
自分で検証まで通した**本物の FALCON-512 の鍵と署名**が入っている。

**相互運用性が実際に検証できるのはここだけ**である。

### (2) 署名長が可変なのに、仕様は固定長を要求する

署名の係数は Golomb-Rice 符号化される ―
符号 1 ビット、下位 7 ビットをそのまま、上位ビットを unary。
何バイトになるかは係数次第なので、
**FALCON-512 が割り当てた 666 バイトに収まらないことがある**。

収まらなければ、署名は**捨てて、新しい salt でやり直す**。
このやり直しループは実装の細部ではなく**方式の一部**であり、
飛ばすと「動くが、たまに動かない」実装ができあがる。

## 9.2 形式（C の codec が規範）

| | 長さ (n=512) | 中身 |
|:---|---:|:---|
| 公開鍵 | 897 | `0x00+logn`、`h` を 14 ビット/係数 |
| 秘密鍵 | 1281 | `0x50+logn`、`f`,`g` を 6 ビット、`F` を 8 ビット |
| 署名 | 666 | `0x30+logn`、salt 40 バイト、圧縮 `s2`、ゼロ詰め |

ヘッダバイトは C 参照実装の実出力で確認した（`0x09`, `0x59`, `0x39`）。

係数幅は `codec.c` の `max_fg_bits` / `max_FG_bits` から引いた。
`logn=9` で `f`,`g` が 6 ビット、`F` が 8 ビット。
`f`,`g` は `σ_fg ≈ 4.05` から引かれるので `|c| < 32` がほぼ確実、
`F` は NTRU 求解から出るので大きく、丸ごと 1 バイト要る。

### G は保存されない

秘密鍵に `G` は入っていない。冗長だからである。
`f·G − g·F = q` から `G = (q + g·F)/f` で復元できる。
復元には `R_q` での除算が要るので、
**`f` が可逆でないときだけ失敗する** ― 鍵生成が既に排除した条件である。

C 参照実装の秘密鍵から `G` を復元し、
**`BigInt` で NTRU 方程式が厳密に成立すること**を確認した。
これは、規範的な実装が作った本物の鍵に対する完全な検証になっている。

## 9.3 正準性 ― 「復号できる」だけでは足りない

C のデコーダは 3 つの余計な検査をしている。

1. **最終バイトの余りビットはゼロでなければならない。**
2. **`-2^(bits-1)` は禁止**（`trim_i8_decode`）。この値はビット幅には収まるが、
   符号化を全単射にするために弾く。
3. **`-0` は無効**（署名の圧縮）。符号ビットが立っていて絶対値が 0 の形。

どれも「復号はできてしまうが、同じ値の別表現になる」ケースを潰している。
放置すると、**鍵や署名を書き換えても無効にならない**（malleability）。

なお `logn=9` では**余りビットが存在しない**:
`512×14 = 7168` ビットはちょうど 896 バイト、`512×6`, `512×8` も同様。
だから (1) の検査を試すには小さい次数を使う必要がある
（`logn=1` なら `2×14 = 28` ビットで 4 ビット余る）。
このテストを最初 n=512 で書いて、
「壊したのに通る」ことになったのを直した（#028）。

## 9.4 参照実装のデコーダは、全ゼロ入力でクラッシュする

Python 参照実装の `decompress` は、末尾のゼロを剥がすループが

```python
while u[-1] == "0":
    u = u[:-1]
```

となっており、**入力が全ゼロだと文字列が空になって `u[-1]` が IndexError**。
しかもこのループは、まさにそれを捕まえるはずの `try/except IndexError` の
**外側**にある。

つまり `decompress(bytes(8), 8, 4)` は「無効」を返すのではなく**例外で落ちる**。

攻撃者が与えたバイト列を食うデコーダがクラッシュするのは、
それ自体が欠陥である。我々の実装は `nothing`（無効）を返す。
テストにも明示的に書いた。

（C 参照実装のほうは `comp_decode` が素直にエラーを返すので、
これは Python 側だけの問題である。）

## 9.5 何が固定でき、何が固定できないか

C 参照実装の KAT を取ったうえで、**できることとできないことを分けて**おく。

| | C 参照実装と厳密一致するか |
|:---|:---|
| 鍵のエンコード／デコード | **する**（整数演算のみ） |
| 署名のエンコード／デコード | **する**（整数演算のみ） |
| 検証 | **するはず**（NTT とノルム、整数演算のみ）→ モジュール 10 |
| **署名の生成** | **しない**。浮動小数点に依存し、#025 の通り 1 ulp で変わる |

だからモジュール 10 の目標は
「C の署名バイトを再現する」ではなく
**「C の署名を検証できる」**である。後者は本物の相互運用であり、
前者は浮動小数点の実装を C に合わせない限り達成できない。

## 9.6 Dilithium との対比

Dilithium のエンコーディングも固定幅のビットパッキングだが、
**可変長の部分が無い**（`z` の範囲が棄却によって保証されているので、
必要なビット幅が事前に決まる）。

FALCON は Gaussian なので係数の大きさに上限が無く、
だから可変長符号にせざるを得ず、
だから**「収まらなければやり直す」**というループが方式に組み込まれる。

「Gaussian を使う」という 1 つの選択が、
鍵生成（モジュール 6）、サンプラ（7）、木（8）に続いて
**エンコーディングにまで**波及している、という話である。
