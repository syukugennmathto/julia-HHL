要旨

FALCON ― NIST が FN-DSA として標準化する格子署名 ― は、選定された署名の中で唯一、出力が浮動小数点演算の関数になる。しかも仕様書の精度解析は、サンプラが出力する分布についてのものであって、二つの適合実装が同じバイト列を返すかどうかについてではない。我々は仕様書だけを読んで Julia で独立実装を書き、参照実装の署名をバイト単位で再現するまで突き合わせた。その突き合わせが、仕様書が中間値を決めていない箇所を 3 クラス炙り出す ― 演算の書き方、公開パラメータから導けない定数、使われているのに印字されていない ε。

そのうち二つの書き方 ― 複素除算と LDL* の D11 ― は署名を 40 万本あたり 3 本、率にして 7.5×10⁻⁶ で変える。しかも必ず最後の 2 回のサンプラ呼び出し、すなわち ePrint 2024/1709（Lin–Tibouchi–Yu–Zhang, EUROCRYPT 2025）が 1 ペアから秘密鍵の全復元に使う位置で。同論文が扱う摂動と違い、これは仕様書と参照実装の差であり、参照実装の両 signing mode に共通に存在し、同論文の対策では塞がらない。我々は同論文の機構を別経路から追認し、同論文が測っていない Heuristic 1 を直接検証する。

01 — 問い

仕様書は署名を決めているか？

FALCON は出力を浮動小数点演算で計算する。ガウスサンプラは Complex{Float64} 上で高速フーリエ最近点再帰を回し、サンプルされる整数 ― そして署名 ― は、その再帰が生む浮動小数点値そのものの関数である。ML-DSA（FIPS 204）と SLH-DSA（FIPS 205）は整数・ハッシュベースで、同じ鍵・メッセージ・乱数を与えれば、どの適合実装でも構成上同じバイト列を返す。FALCON にその保証はなく、仕様書もそれを意図していない ― §2.5.2 は浮動小数点精度をサンプル分布についての Rényi 発散論法で解析し、§4.1 は C の double が IEEE-754 に「少なくとも一致」すればよいとする。どちらも分布の話であって、二実装がビット単位で一致するかの話ではない。

この区別が今や効いてくる。FIPS 206 の状況報告（Perlner, NIST, 2025年9月）は、標準が浮動小数点の演算順序を規定し、FMA を禁じ、実装が KAT にビット一致することを求める方向を示す。標準がビット一致を求めるなら、「仕様書は中間値を決めているか」は規範上の問いになる。本稿は第二の実装を作り、参照実装とどこで食い違うかを正確に測ることでこれに答える。

なぜ Julia か ― 正直に

我々が Julia を選んだのは、速いと期待したからだ。ネイティブ配列と数値計算の評判から、行列が重い部分（FFT・NTT・グラム行列）は書きやすく走りやすいだろうと踏んだ。それは部分的にしか当たらなかった（§6）。もう一つ、本物だが後から気づいた理由があり、そう明記する。FALCON のセキュリティ関連の時間変動には二つの源がある ― アルゴリズム由来（棄却サンプラのデータ依存ループ）と実装由来（GC・JIT・境界検査・動的ディスパッチ）。ガベージコレクト・JIT の言語は後者を閉じることが原理的にできない ― だからこそ、実装由来の変動に隠されずに仕様レベルの変動を観察する、きれいな計測器になる。自分の処理系由来の変動を隠せない言語こそ、仕様書由来の変動が素で現れる言語である。この理由で選んだのではないが、結果としてこの問いに適していた。

02 — 未決定性

仕様書が開けたままの 3 箇所

実装を参照実装と段階ごとに生の 64 ビットパターンで突き合わせると、浮動小数点経路は 3 群に分かれる ― 無改修で一致する原始関数（FFT 一族と B0 行列全体、5120/5120 double）、参照実装の書き方にして初めて一致する 3 つの計算、そして別規約で格納された 1 つの定数。3 つの書き方は代数的に同値で丸めが違う。最初の 2 つについて、両実装パターンを走るコードで示す。

(a) 複素除算

仕様書に式はない。読者は言語の複素除算を使う ― Julia も Python も Smith のアルゴリズムだ。参照実装は逆数を明示的に作る。Smith が数値的に優れ、参照実装のものが KAT を規定する。

パターン S ― 仕様の読者（Julia の /）# Smith のアルゴリズム、数値的に良い
ComplexF64[ f[i] / g[i]
            for i in eachindex(f) ]
パターン C ― 参照実装（FPC_DIV）br = real(b); bi = imag(b)
m  = 1.0 / (br*br + bi*bi)
br *= m; bi *= -m
ComplexF64(ar*br - ai*bi,
           ar*bi + ai*br)

(b) LDL* の D11

Algorithm 8 と Python 参照実装は D11 を乗算 3 回で計算し、C 参照実装は商を逆向きに保って畳み込み、乗算 1 回で済ませる。G00 がエルミート＝実数なので等しい。

パターン S ― Algorithm 8 / Python# 乗算 3 回
L10 = div_fft(G[2,1], G[1,1])
D11 = sub_fft(G[2,2],
        mul_fft(mul_fft(L10,
          adj_fft(L10)), G[1,1]))
パターン C ― Zf(poly_LDL_fft)# 乗算 1 回
G01 = adj_fft(G[2,1])
mu  = div_fft(G01, G[1,1])
L10 = adj_fft(mu)
D11 = sub_fft(G[2,2],
        mul_fft(mu, G[2,1]))

3 つ目の書き方 (c) は、参照実装が ffSampling の最下 2 段を手展開し、split/merge の捻り係数を 1/√2・1/√8 に畳んだものだ。3 つは with_spec_spelling(f; cdiv, ldl, ffsampling) で独立に切り替わり、既定は参照実装の書き方 ― この独立性こそが要で、発散を一つの式に帰属できる。あと 2 クラスは定数だ ― (II) fpr_inv_sigma は印字された σ の正しく丸めた逆数ではなく（§5）、(III) σ_min は本文が印字しない ε を使う。

03 — 伝播

どの選択が署名に届くか

100 個の鍵それぞれを、鍵・メッセージ・PRNG 状態を揃えたまま二つの書き方で何度も署名し、署名が食い違う回数を数える。測定前に、各腕が木の 9728 個の double のうち何個を動かすかを印字する ― どのゼロも「何もしていない腕」ではないことを示すためだ。

A1 は陽性対照 ― ePrint 2024/1709 §6.1 の sign_dyn/sign_tree の差そのもので、率（52.5 万本で 1.9×10⁻⁵）は同論文 Table 2 に載る。B は陰性対照で、そのゼロは理論から予期される ― 幅を摂動し、同論文 Lemma 2 がそれを ≈10⁻¹¹ と抑える。分解能より遥か下なので、ゼロは何も語らない。A2 が、同論文にない腕であり、ゼロでない ― そして n=1024 でも再現する（35 万本で 1 件、やはり最後の 2 回、floor が 427/426 をまたぎ、幅はビット一致）。A2 と A1 は点推定で 2.5 倍違うが有意でなく（p ≈ 0.23）、ともに 10⁻⁵ の桁 ― 機構を共有することと整合するので、順序ではなく同程度と報告する。

A2 の 3 件はすべて機構を正確になぞる ― 3 件とも呼び出し 2n−1 か 2n、3 件とも整数をまたぎ、3 件とも該当節点の幅がビット一致。つまり発散は中心だけで起きている：

# scripts/first_divergence.jl
key 70 sig  534   call 1023/1024   mu -267.00000000000006  vs -267
key 65 sig 1239   call 1023/1024   mu  337                 vs  336.99999999999994
key 68 sig 1885   call 1024/1024   mu  285.99999999999989  vs  286

その1ペアから、鍵

「鍵回復の位置」は帰結の主張だ ― 引用でなく実行して片づける。A2 ペア（key 70, sig 534、同じ syndrome で最後の2回のサンプラ出力だけ違う2署名）の差は Δs0 = Δz0·g, Δs1 = −Δz0·f、Δz0 = a + b·x^{n/2}。(a+bx^{n/2})⁻¹ = (a−bx^{n/2})/(a²+b²) なので、復元は (a,b) ∈ {−19..19}² の探索で済み、環の逆元計算は要らない。(s, s') と公開鍵だけから：

# scripts/key_recovery.jl 70 534
hit at (a, b) = (-1, 0)
candidate reproduces the public key h (mod q): yes
|g_cand| max = 14, |f_cand| max = 13   (true |g| = 14, |f| = 13)
matches the stored secret up to negation: (f,g) = -(f_true, g_true)
*** 単一の A2 発散ペアから、秘密鍵を完全復元。***

復元された (f, g) は符号対称 (f,g) ↦ (−f,−g) を除いて格納鍵と一致 ― 同じ署名鍵だ。つまり複素除算と D11 は、署名を変えるだけでなく、syndrome を2回署名する derandomized の設定で鍵を露出させるのに十分。復元の代数は回帰テスト済み（test_falcon.jl）。

なぜ最後の2回が支配的か ― 論文が残した未解決を解いた

2024/1709 §6.1 は「整数中心を条件づけると最後の2回が最初の2回より発散しやすいが、理由は完全には分からない」と書いた（sign_dyn/sign_tree の差、FMA では起きない）。綴りが中心に与える摂動 |Δμ| を全位置で測ると、木の降下に沿って累積し、中点で段になる：

# scripts/position_profile.jl（位置ブロックごとの平均 |Δμ|）
pos    0.. 511  (z1, 第1降下) : 2.7e-15 → 1.0e-14
pos  512..1023  (z0, 第2降下) : 7.4e-14 → 8.7e-14   # ~7倍の段
最初の2回 (0,1)     : 2.7e-15
最後の2回 (1022,1023): 8.6e-14        比 ≈ 32×

段は構造的だ：ffSampling は z1 を先に引き、t0 ← t0 + (t1 − z1)·l10 を作ってから z0 を引く。z0（後半＝最後の2回を含む）の中心は上位 l10 補正を経由し、丸め差がそこに乗る。前半の中心は経由しない。中心が整数をまたぐのは |Δμ| が整数までの距離を超えるときなので、32倍大きい |Δμ| は 32倍多い発散 ― これが非対称性の正体。そして A2（木のみ）では最初の2回の |Δμ| は厳密に 0（第1葉の中心は l10 補正前の純粋な目標 split）なので、A2 の発散は構造的に最後の2回に限られる。敏感位置は固定ではなく、摂動がどこから入るかで決まる。

04 — 位置づけ

何が新しく、何が新しくないか

正直な位置づけが、貢献のほとんどだ。演算の機構、参照実装の 2 モードが発散すること、幅への非感受性 ― すべて ePrint 2024/1709 の結果である。我々はそれらを独立に追認し、2 点を加える。

唯一の新しい実験事実は A2 だ。その意義は新しい機構ではない ― Lemma 1 だ ― が、源が違う。同論文の 2 源はどちらも参照実装の内側にある：FMA はビルドフラグ、sign_dyn/sign_tree は §7.2 の対策が互いに揃える 2 つの入口だ。複素除算と D11 は仕様書と参照実装の差なので、両 signing mode に存在し、その対策を生き延びる。ビット一致 KAT を意図する標準にとって、これは「二実装を一致させるべき」と「本文がどちらの式かを言わねばならない」の差である。

先に、三度、間違えた 初期の枠組みは「仕様書の未決定性だけで足りる、違うビルドは要らない」と主張した ― §6.1 の再発見だった。読み込んでいなかった 1 個のフラグが、クラス I(c) しか動かしていなかったからだ。さらに古い主張「この差は署名に届かない」は 480 署名に依っていて、それでは 10⁻⁵ とゼロを区別できない。論文を読み、3 つの書き方を分離し、大標本で測ったことが、正しく狭い主張を生んだ。

05 — 性能

どれくらい速いか、何に対して

1 台（4 コア、FMA 付き x86-64 ― 1 台という制約は実在し、隠さない）。変えられるものは変えた ― C は 2 コンパイラ・3 最適化レベル・エミュ対ネイティブ浮動小数点、Julia は 3 最適化レベル、そして run 間分布の中央値を報告する。

Julia −O2 の行から比を読む：

  • 検証は C を含め最速 ― 0.015 ms 対 最速 C ビルドの 0.0165（≈1.1 倍）、gcc −O2 の 0.026（≈1.6 倍）、そして Python の 235 倍。検証はサンプラも多倍長整数もない NTT 主体の整数演算で、Julia の配列と LLVM が最も得意とする所だ。
  • 署名はエミュ C ビルドの ≈1.8 倍速く（配備される FALCON の多くが走らせる版）、Python の 20 倍、ネイティブ C の ≈6 倍遅い ― 浮動小数点サンプラが C の SSE2 double に負ける。
  • 鍵生成は ≈9.78 ms ― 全エミュ C ビルドより速く、Python の 272 倍だが、ネイティブ C の ≈1.9 倍遅い。多倍長整数を BigInt で持つのが、参照実装の 31 ビットリム RNS に対する差だ。

n=1024 では傾向が鋭くなる ― 検証は再び最速（0.031 ms 対 最速 C 0.035、Python の 245 倍）、署名はエミュ C の ≈1.7 倍・Python の 18.8 倍、鍵生成は Python の 296 倍だが今度はエミュ C にも ≈1.3 倍遅い（BigInt 対 RNS の差が次数で開く）。特筆すべきは Julia −O2 が 512 で、−O3 が 1024 で勝つこと ― 最良のレベルは演算ごとで、1 レベルだけ報告すれば実装を誤って伝える。鍵生成は長い最適化の到達点でもある ― 最初の動作版は 9610 ms で、9.78 ms への道はほぼ全て確保の除去であり、高水準の配列書き換えではなかった。

06 — 範囲と限界

定数時間性、そしてまだ言えないこと

この実装は定数時間ではなく、目指してもいない。定数時間実装ならできない事をする箇所には CONSTANT TIME: コメントを残した。Julia 実装は実装由来のチャネル（GC・JIT・境界検査・ディスパッチ）を一切閉じられない ― だからこそここでの仕様レベルの問いにはきれいな計測器で、配備用の署名器としては不向きなのだ。していない側面攻撃の貢献を主張するのでなく、そう明記する。

未解決として明示するもの：

  • A2a / A2b は分離できていない ― 複素除算単独と D11 単独はどちらも 0/10万。単独率 ≈3.75×10⁻⁶ をゼロから分けるには数百万署名が要り、そこまで到達していない。二つ合わせれば署名に届く、とは言えるが、どちらが効くかは言えない。
  • A2 と A1 の率は区別できない ― 点推定で 2.5 倍だが、92.5 万本のプールで p ≈ 0.23。順序ではなく「同程度」と報告する。
  • §6.1 の非対称性は同論文も未解決とし、我々も解けていない。
  • FALCON-1024 は低volume（35万本、1 件）で測定。率の推定は緩いが、その 1 件が機構を完全になぞるので、再現は確立された。
07 — 提言

FIPS 206 がすべきこと

FIPS 206 がビット一致 KAT を求めるなら：

  1. 書き方を固定する ― 複素除算・D11・最下段 ffSampling を明示するか、より良くは ePrint 2024/1709 §7.1 の構造的修正（中心を floor でなく round でサンプルし、‖(g,−f)‖² を奇数に制限）を採る。後者は感受性そのものを除く。ただし現状の C 鍵生成が ‖(g,−f)‖² を偶数に強制しているので、そのパリティ条件の緩和も要る。
  2. fpr_inv_sigma を全精度で公表する ― 丸めた σ から導かせず、中間値が KAT の対象かを述べる。
  3. σ_min の ε を明記する、あるいは導出を。
  4. SamplerZ のバイト組み立て規約をベクタと並べて記す。
