- **モジュール**: params.jl
- **症状**: 「パラメータの具体値は必ず仕様書の表から引き、出典（表番号）を

  勘違いした。ツールのエラーメッセージ（`EGRESS_BLOCKED`）をちゃんと読めば

    完全一致することを確認済み（`34034726` / `666`）。

  - `sig_bound / (2n sigma^2)` が 1〜2 の間（桁を間違えたら落ちる）
- **学び**: 「出典を書け」という指示の本質は表番号そのものではなく

## [2026-08-17] #003 params: sigma_min の閉じた式を逆算で特定した

- **モジュール**: params.jl
- **症状**: バグではない。定数を「記憶から書かない」ために、
  `sigma_min = 1.2778336969128337` が**どの式から来ているのか**を
  仕様書なしで確定させる必要があった。
- **再現条件**: —
- **切り分け**:
  - [x] 平滑化パラメータの標準形 `eta_eps(Z) = (1/pi) sqrt(ln(2(1+1/eps))/2)` を仮定
  - [x] 参照値を代入して `eps` を逆算 → `log2(1/eps) = 45.50000000002967` (n=512),
        `47.00000000002099` (n=1024)
  - [→] 45.5 と 47.0 という**ほぼ厳密な値**が出た。差 1.5 = 1.5*(logn の差 1)、
        切片 32 → `1/eps = 2^32 * n^(3/2)`、すなわち `eps = 1/sqrt(2^64 * n^3)`
- **外した仮説**:
  - 最初 `sigma = 1.17 * sqrt(q/(2n))` だと思い込んでいた（`ntrugen.py` の
    コメントに出てくる式なので）。n=512 で 4.05 にしかならず、参照値 165.7 と
    2 桁違う。**これは f, g のサンプリング幅 `sigma_fg` であって
    署名の幅 `sigma` ではない**。FALCON には σ が 4 種類（`sigma`, `sigma_min`,
    `sigma_max`, `sigma_fg`）あり、しかも `sigma_fg` は「4096 個サンプルして
    `4096/n` 個ずつ畳む」という実装都合の基底幅 `1.43300980528773` を持つ。
    ここを混ぜたのが 1 つ目の外し。
  - 次に `eta` の中の `2` を `2n`（`Z^{2n}` の平滑化）だと思って試したが、
    `log2(1/eps)` が 35.5 / 35.0 と汚い値になった。`Z^1` の式が正しい。
- **原因**: （バグではない）
- **修正**: `falcon_eps(n) = 1/sqrt(2^64 * n^3)` と `smoothing_eta(eps)` を
  params.jl に書き、`sigma = 1.17 * sqrt(q) * sigma_min` も確認した
  （1.17 は `ntrugen.py:232` の Gram-Schmidt 上限 `(1.17^2)*q` と同じ定数）。
  閉じた式は Float64 評価で参照値と相対 3e-13 まで一致する。**完全一致では
  ないので、権威ある値は引き続き参照実装のリテラル**とし、閉じた式は
  「桁を打ち間違えたら落ちる」ためのテストに使う。
- **回帰テスト**: `test/test_params.jl` の
  `"sigma_min is the smoothing parameter of Z"` と
  `"sigma = 1.17 * sqrt(q) * sigma_min"` と `"sigma_fg and its base"`。
- **学び**: σ が 4 つある。**どの Gaussian の話をしているかを毎回言え。**
  格子上の Gaussian（`sigma`）、Z 上の各座標の Gaussian（`sigma_min`〜`sigma_max`）、
  鍵生成の f,g の Gaussian（`sigma_fg`）、そしてその実装上の基底幅
  （`SIGMA_FG_BASE`）は全部別物で、単位も意味も違う。
  `1.17` だけが 3 つをまたいで現れる（Gram-Schmidt ノルムの上限）ので、
  この定数を見たら「どの σ の話か」を確認する合図にする。

## [2026-08-17] #004 shake: SHA.jl の SHAKE256 は「squeeze の続き」ができない

- **モジュール**: shake.jl
- **症状**: バグではなく設計上の制約。FALCON は SHAKE256 を XOF として使い、
  hash-to-point では**必要な分だけ吸い出しては棄却する**ので、
  「途中まで squeeze して、足りなければ続きを squeeze する」API が要る。
  `SHA.jl` にはそれが無い（`shake256(data, d)` の一発形しかなく、
  `digest!` は呼ぶたびに padding を再適用するので同じ context を 2 度
  squeeze できない）。
- **再現条件**: —
- **切り分け**:
  - [x] `SHA.jl` の `src/shake.jl` を読んだ。`digest!(ctx, d, p)` は
        `d > blocklen` のときは内部で継続 squeeze するが、
        呼び出しをまたいだ継続はできない構造（`used` フラグと再 padding）。
  - [→] XOF の定義から、`SHAKE256(m, d1)` は `SHAKE256(m, d2)` (d1<d2) の
        **prefix** になる。ならばメッセージを保持して長さを倍々にしながら
        取り直せばよい。
- **外した仮説**: なし（最初からこの方針）。
- **原因**: （バグではない）
- **修正**: `SHAKE256XOF` を「吸収済みメッセージ + 生成済みバッファ + 位置」で
  持ち、足りなくなったら倍の長さで `SHA.shake256` を取り直す実装にした。
  償却 O(N) だが、取り直しのたびにメッセージを再吸収するので厳密には
  O(N + |m| log N)。FALCON のサイズでは無視できる。
- **回帰テスト**: `test/test_shake.jl` の `"SHAKE256 prefix property"`。
  **これは FIPS 202 の性質ではなく `SHA.jl` の実装への仮定**なので、
  hashlib 由来のベクタで明示的に検証する。ここが落ちたら
  `squeeze!` を細工するのではなく Keccak-f[1600] を自前で書くこと、
  とテストのコメントに書いた。
- **学び**: 標準ライブラリで代用するとき、**代用が壊れる条件をテストに書いておく**。
  「たぶん prefix になっているはず」で通してしまうと、後で hash-to-point が
  ときどきずれるという最悪の形で返ってくる。

## [2026-08-17] #005 shake: 参照 PRNG の randombytes は「余りを捨てる」

- **モジュール**: shake.jl
- **症状**: バグではなく、移植前に潰しておいた罠。
  `scripts/pyref/rng.py` の `randombytes(k)` は、バッファ残量が `k` に
  満たないとき**残りを連結せず捨てて**新しい 512 バイトを生成する。
- **再現条件**: —
- **切り分け**:
  - [x] `rng.py:111-122` を精読
  - [x] `out = "".join(out[i:i+2] for i in range(2*k-2,-1,-2))` のあと
        `bytes.fromhex(out)[::-1]` している。**この 2 つの反転は打ち消し合って
        恒等写像**。実質「バッファ先頭 k バイトを返して k 進める」だけ。
  - [→] 意味があるのは反転ではなく `if 2*k > len(self.hexbytes): 再生成` の分岐
- **外した仮説**: 反転処理に意味があると思って 15 分読んだ。
  C 参照実装がワード単位で消費するのに合わせた名残で、
  バイト列としては何もしていない。**「変な処理があったら、まず恒等でないか
  確かめる」**べきだった。
- **原因**: （バグではない）
- **修正**: Julia 側は素直に「バッファ先頭 k バイト、足りなければ捨てて再生成」で
  実装し、反転は再現しない。その主張は KAT で担保する。
- **回帰テスト**: `test/vectors/chacha20_kat.jl` に
  `[511, 8]` と `[255,255,255]` という**境界をまたぐ要求パターン**を入れた。
  加えて `test_shake.jl` の `"ChaCha20 buffer boundary behaviour"` が
  「捨てている」ことを直接主張している。
- **学び**: 参照実装の「意味の無いコード」と「意味のあるコード」を分けてから移植する。
  ただし**分けた根拠はテストにする**。恒等だと判断した処理が実は恒等でなかった
  場合、それは KAT でしか気づけない。

## [2026-08-17] #006 ntt: 根テーブルの順序規約を逆算で特定し、ハードコードをやめた

- **モジュール**: ntt.jl
- **症状**: バグではない。参照実装は `roots_dict_Zq`（n=2..1024、計 2046 個の
  定数）を sage スクリプトで生成してハードコードしている。これをそのまま
  写経すると「なぜこの順序なのか」が永久に分からなくなるので、
  **生成則を特定して 20 行の再帰に置き換えられるか**を調べた。
- **再現条件**: —
- **切り分け**:
  - [x] `roots_dict_Zq[n]` の各要素が `x^n+1` の根か → 全 n で成立
  - [x] `ntt(f)[j] == f(roots[j]) mod q` か → 成立。**NTT は素直な多点評価**で、
        ビット反転などの並べ替えは入っていない
  - [x] ペアの構造 → `w[2i] + w[2i+1] == q`（つまり `±w`）が全 n で成立
  - [x] 親子関係 → `w_{2n}[2i]^2 == w_n[i]` が全 n で成立
  - [→] ペア内の順序 → **小さい剰余が先**が全 n・全ペアで成立
- **外した仮説**: 最初「Dilithium と同じくビット反転順だろう」と決めつけて、
  ビット反転を適用してから比較していた。当然合わない。
  FALCON の Python 参照実装は**自然順（塔の順）**であって、ビット反転しない。
  ビット反転が出てくるのは C 実装のほう（下の #007）。
  「NTT といえばビット反転」という Dilithium で刷り込まれた前提が邪魔をした。
- **原因**: （バグではない）
- **修正**: ζ = 7（12289 を法とする位数 2048 の最小の元）から、指数の再帰
  `e ↦ {e/2, e/2 + 1024}` に「値の小さいほうを先」の規則を付けてテーブルを
  生成する実装にした。`NTT_ZETA = 7` はリテラルで置きつつ、
  `find_ntt_zeta()` で再計算できるようにしてテストで検証している。
- **回帰テスト**: `test/test_ntt.jl` の `"root tables match the reference"`。
  生成表が参照実装のハードコード表と n=2..1024 で完全一致することに加え、
  `w^n = -1`・ペアが `(r, q-r)`・小さいほうが先・`w_{2n}[2i]^2 = w_n[i]` を
  すべて主張している。加えて `"NTT product agrees with the schoolbook product"`
  が**順序**を固定する（順序を入れ替えても往復テストは通ってしまうが、
  poly.jl との積の一致は通らない）。
- **学び**: **往復テストは NTT の正しさをほとんど何も保証しない。**
  評価点が全部間違っていても `intt(ntt(f)) == f` は成立する。
  保証するのは (a) 定義そのもの（Horner で評価して一致するか）と
  (b) 独立実装との積の一致、の 2 つ。テストを書くときはこの 2 つを必ず入れる。

## [2026-08-17] #007 ntt: C 参照実装と Python 参照実装で NTT の係数順序が違う

- **モジュール**: ntt.jl
- **症状**: モジュール 4 の突き合わせ相手を C にするか Python にするかで
  詰まった。C の `Zf(to_ntt_monty)`（`inner.h:579`）はビット反転順かつ
  Montgomery 形式で、Python 版の自然順・素直な剰余とは**係数の並びも値も違う**。
- **再現条件**: —
- **切り分け**:
  - [x] Python 版の出力 = 自然順の多点評価（#006 で確認済み）
  - [x] C 版は関数名に `monty` とあり、Montgomery 領域であることが明示されている
  - [→] C と比べるには「置換 + Montgomery 係数の補正」という**2 段階の変換**が
        要る。それ自体がバグの温床になる
- **外した仮説**: 「参照実装は C が正典なのだから C と突き合わせるべき」と
  考えていたが、**突き合わせの目的は仕様の理解であって C の再現ではない**。
  順序と表現が違うものを無理に合わせると、不一致が出たときに
  「移植のバグ」なのか「補正のバグ」なのか切り分けられなくなる。
- **原因**: （バグではない。設計判断の記録）
- **修正**: モジュール 4 の一次オラクルは **Python 参照実装**にした。
  C との突き合わせはモジュール 5（fft.jl）以降で行う
  （`Zf(FFT)` / `Zf(iFFT)` は順序の問題が無いため）。
  この判断の理由を `src/ntt.jl` 冒頭のコメントにも残した。
- **回帰テスト**: なし（設計判断）。ただし `docs/build_cref_macos.md` の
  関数対応表に、モジュール 3・4 に対応する C 関数が無い理由を明記した。
- **学び**: 「参照実装と突き合わせる」と言うとき、**どの参照実装のどの表現と**
  突き合わせるのかを毎回決める必要がある。速い実装（C）と読める実装（Python）は
  同じアルゴリズムの別表現であって、後者のほうが仕様に近い。
  FALCON はその 2 つを両方公開している珍しい例。

## [2026-08-17] #008 方法論: Julia を動かせない環境で、書いた Julia を Python に逐語移植して検証した

- **モジュール**: （方法論）
- **症状**: #001 の通り Julia が動かせないので、`ntt.jl` を書いても
  インデックスがずれていないか確かめる手段が無い。1-based ↔ 0-based の
  変換は移植で最も事故が多い箇所なのに、そこが未検証のまま積み上がる。
- **再現条件**: —
- **切り分け**:
  - [x] golden vector は Python 参照実装から生成しているので、**期待値**は正しい
  - [→] 検証できていないのは**Julia 側のアルゴリズム**。ならば、
        書いた Julia コードを Python に**逐語**（1:1、行対応で）移植して、
        参照実装と比較すればアルゴリズムは検証できる
- **外した仮説**: 最初は「型さえ合っていれば読み直しで十分」と思っていたが、
  `merge_ntt` の `w[2i-1]`（Julia）↔ `w[2i]`（Python）の対応は

  **「1 台で観測された一致」と「全機種で保証された一致」は別物**であり、
  署名の相互運用性は後者を要求する。

- **測定 2（ここが本題）: では我々と C の差はどこから来ているのか**

  最初の比較はやり方が間違っていた。C の表 1024 *エントリ*に対して
  我々の 2046 *成分*を集合として突き合わせ、「2207/4092 一致」という
  意味のない数を出した。母集団が違うのだから比べようがない。
  `fft.c` の添字 `fpr_gm_tab[((m + i1) << 1) + 0/1]` を読み直して、
  **エントリ `j` が複素数 1 個（実部・虚部の 2 スロット）**であり
  `j` は 0..1023 だと確定させてから、各エントリの偏角を
  `atan2` で高精度に復元して `k/1024` を同定し、
  **同じ角度どうし**を bit 比較した。結果:

  | 我々の `cispi(k/n)` と C の `fpr_gm_tab` | 件数 |
  |:---|---:|
  | bit 完全一致 | 972 |
  | 値は同じ（`-0.0` と `+0.0` の違いのみ、π/2） | 1 |
  | **ちょうど 1 ulp 違う** | **50** |
  | 2 ulp 以上違う | 0 |

  最小の例が `cispi(1//4)`。実部は `0x3fe6a09e667f3bcd`（正しい）だが
  **虚部が `0x3fe6a09e667f3bcc` で 1 ulp 小さい**。
  `sinpi(0.25)` と `cospi(0.25)` が同じ √2/2 に対して違う値を返している。

  Julia の `sinpi` / `cospi` は *faithful*（1 ulp 以内）であって
  *correctly rounded*（最近接）ではない。契約通りである。
  そして **1 ulp は FALCON の署名を変えるのにちょうど十分な誤差**（#025）。

- **外した仮説**:
  1. 「エミュレーション版とネイティブ版は丸めが違うはずで、
     それが #025 の一般化された姿だろう」→ **完全に外れ**。
     両者は 1 bit も違わない。#025 は演算の問題ではなかった。
  2. 「`-Ofast` なら FMA の縮約でネイティブ版が崩れるだろう」→ 外れ。
     5 通りの最適化フラグすべてで同じ署名。
     `fpr.h` のネイティブ版が演算を 1 つずつ関数に分けているので、
     コンパイラが縮約できる形になっていない。
  3. 「`cispi` は `k/n` が 2 進で厳密なのだから正しく丸まる」→ 外れ。
     引数が厳密でも**結果の丸めは別問題**である。
     これは元の docstring に書いてしまっていた誤りでもある。

- **原因**: `fft_roots` が `cispi(k/n)` で根を作っていた。
  `cispi` の誤差 1 ulp が 1023 エントリ中 50 件で顔を出し、
  それが FFT を通って ffSampling の中心を動かし、
  棄却判定を反転させ、署名バイトを変えていた。
  **#025 で「1 ulp の表の差」と書いたものの、その 1 ulp が
  どちら側の誤差なのかは特定できていなかった。今回それが確定した:
  誤差は我々の側にあった。**

- **修正**: `src/fft.jl` に `unit_root(k, n)` を追加し、
  `fft_roots` をそれ経由にした。256 bit の `BigFloat` で
  `cos(π k/n)` / `sin(π k/n)` を計算して**一度だけ**丸める。
  π/2 の倍数は特別扱いする ― そこでは cos か sin が**厳密に** 0 か ±1 であり、
  有限精度の π からは厳密な 0 は絶対に出てこない
  （実測でも、この 1 件だけが `BigFloat` 直計算では合わなかった）。
  根の表は `n` ごとに 1 回作ってメモ化するので、`BigFloat` の
  コストは実行時間に出ない。

- **回帰テスト**: `test/test_fft.jl` の
  `"roots are bit-identical to the C reference's fpr_gm_tab"`。
  `test/vectors/fft_roots_c_kat.jl`（C の実バイナリから吐いた 1023 エントリ、
  生成器は `scripts/cref_gm_dump.c`）に対して、
  n = 2,4,…,1024 の全 2046 個の根を**ビットパターンの相等**で主張する。
  許容誤差は無い ― 緩める余地が無いように書いてある。
  `-0.0` / `+0.0` の 1 件だけは明示的に許容し、その理由もテスト中に書いた
  （零の符号は積にも和にも値としては効かない）。

- **学び**:
  1. **「1 ulp 以内」は保証ではなく上界である。**
     暗号実装で「およそ正しい定数」は、決定的な出力を要求する場面では
     間違った定数と同じ意味を持つ。
  2. **測り方を間違えた数（2207/4092）を一度出してしまった。**
     母集団の大きさが違う時点で気づくべきだった。
     *比べる前に、両側が何を数えているのかを確定させる。*
     #018（自分で書いた fixture が実は overflow していなかった）と同じ型の失敗。
  3. **予想が外れたときのほうが情報が多い。**
     「emu と native は違うだろう」が外れたおかげで、
     容疑者が演算から定数表に絞られ、#025 の原因にたどり着けた。
     当たっていたら「やっぱり浮動小数点は再現できない」で終わっていた。
  4. **#025 の結論は変わらないが、理由が変わった。**
     署名バイトが再現できないのは「浮動小数点だから」ではなく、
     「**定数表が違うから**」である。そして定数表は合わせられる。
     いま我々の表は C の表と bit 一致している。
     残る差分は演算の順序だけになった ― これは次の実験になる（下記）。

## [2026-08-21] #033 性能: 「Julia なら速いはず」の境界線を測った

- **モジュール**: 全体（`scripts/profile_stages.jl`, `scripts/profile_ntrusolve.jl`）
- **症状**: バグではなく**測定**。#032 で C との差（鍵生成 738 倍、検証 15 倍）は
  出したが、**中身が分かっていなかった**。「原因: 不明（要調査）」で残していた分。

### 鍵生成: 99.98% が `ntru_solve`、その 96% が**たった 1 回の呼び出し**

| stage | median ms | alloc MB | gc% |
|:---|---:|---:|---:|
| `gen_poly`（4096 回の samplerz） | 1.11 | 1.3 | 0 |
| `gs_norm` | 0.23 | 0.7 | 0 |
| `is_invertible_zq` | 0.05 | 0.1 | 0 |
| **`ntru_solve`** | **13371** | **9613** | **19** |
| `expand_privkey` | 0.66 | 1.9 | 0 |

降下を段ごとに割ると:

```
     n   fieldnrm    karamul      babai   level ms  bits_in      raw      out
   512      31.68      57.44      65.38     154.49        8       24        8
   256      11.33      18.86      20.22      50.41       16       40       16
   128       3.72      11.21   11466.49   11481.42       32     6232       32
    64       1.20       3.58      46.37      51.16       56     6208     6208
    32       0.44       1.16      22.42      24.02      104     6160     6160
     ...
     1       0.00       0.00       0.00       0.00     3152        0        0

```

**n=128 の `babai_reduce` 1 回が 11466 ms（96.3%）、9.0 GB（93.6%）。**

`bits_raw` → `bits_out` の列が理由を説明している。
**n=64 以下では Babai 縮約が何もしていない**（6208 → 6208）。
縮約は 1 反復で上位 53 bit しか削れず、`Size < size` に届かないまま
`ki` がゼロになって抜ける。結果 6200 bit の係数が n=128 まで運ばれ、
**そこで 1 回だけ ~117 反復（(6232−32)/53）の巨大な縮約**が走る。
1 反復あたり 6000 bit 係数の `karamul` が 2 回、約 98 ms、77 MB。

**これは我々のバグではない。** Python 参照実装の `reduce` に本人のコメントがある:

> `# The two next lines are the costliest operations in ntru_gen`
> `# (more than 75% of the total cost in dimension n = 1024).`

さらに `test_ntrugen.jl` の `"ntru_solve reproduces the reference exactly"` が
n=2〜128 で参照実装の (F, G) と**完全一致**を主張している。
つまり挙動まで含めて忠実であり、これはこのアルゴリズムの形そのもの。

### 「Julia なら速いはず」への答え

同じ小さい値（`Int64` に収まる）65536 個の二乗和:

| | 時間 | 割り当て |
|:---|---:|---:|
| `Int64` | 0.031 ms | 0 |
| `Int128` | 0.234 ms | 0 |
| **`BigInt`** | **9.780 ms** | **8.01 MB** |

**`Int64` に収まる値に対してすら `BigInt` は 315 倍遅い。**

Julia が速いのは、型が具象で、データが inline (`isbits`) で、
ホットループが割り当てないときである。`BigInt` はこの 3 つを全部壊す ―
GMP の `mpz_t` を包んだ mutable な heap オブジェクトなので、
`Vector{BigInt}` は**値の配列ではなくポインタの配列**、
演算のたびに `libgmp` への `ccall` と新規確保と GC。
**ここで Julia は Python に対する優位を一切持っていない。**

C が速いのは最適化が上手いからではなく、**多倍長演算を一度もしていない**から。
31 bit の小さな素数を並べた RNS で全部機械語に載せ、素数ごとに NTT を回す。
**計算モデルが違う**のであって、定数倍の話ではない。

- **検証の 46%、署名の 14% が `sqnorm` ただ 1 つ。**
  しかも検証で扱う係数は `|c| ≤ q/2 = 6144`、総和は `2^38` 未満 ―
  **大きい数を扱っているから遅いのではない。`BigInt` だから遅い。**
- **サンプラは律速ではない。** `samplerz` 512 回で 0.134 ms、
  `sample_preimage` 1.386 ms の 10% にすぎない。
  残りは FFT 領域の木を歩く際の割り当て（署名 1 本で 1.84 MB）。

- **外した仮説（3 つ）**:
  1. 「鍵生成が遅いのは底の段で係数が巨大になるから、不可避だろう」→ **外れ**。

  2. 「上の段で機械語に収まる値に `BigInt` を払っているのが主因だろう」→ **外れ**。
     n=512 の段は 154 ms、全体の 1.3%。上段を直しても何も変わらない。
  3. 「`sqnorm` を速くするなら checked 演算で安全に」→ **外れ**（下記 #034）。

- **原因**: （バグではない）
- **修正**: `sqnorm` は #034 で直した。`ntru_solve` は手を付けていない。
- **回帰テスト**: ベンチマークはテストにしない（#032 と同じ理由）。
- **学び**: **「遅い」は測定結果ではなく症状である。**
  #032 で 738 倍という数字を出した時点では、
  何を直せばいいのか一つも分かっていなかった。
  段に割って初めて「1 回の呼び出しが 96%」が見え、
  「底が重い」という自然な予想が外れていたことも分かった。

## [2026-08-21] #034 poly: `Int128` の checked 演算はハードウェアで走らない

- **モジュール**: poly.jl (`sqnorm`)
- **症状**: #033 で `sqnorm` が検証の 46% だと分かったので `Int128` の
  高速経路を足した。**300 倍のうち 3.4 倍しか出なかった。**
- **再現条件**: n=512 の署名係数 1024 個の二乗和、中央値:

  | 実装 | 時間 |
  |:---|---:|
  | `try`/`catch` の**中**にループ（最初に書いたもの） | 0.0810 ms |
  | `try`/`catch` を**関数呼び出しの周り**に移動 | 0.0809 ms |
  | checked をやめて素の `Int128` | **0.00097 ms** |

- **切り分け**: 最初に疑ったのは `try`/`catch` だった
  （Julia では例外ハンドラが同じ関数内の最適化を止めることがある）。
  ループを別関数に切り出して `try` を呼び出しの周りだけにしたが、
  **0.0810 → 0.0809 ms。誤差**。無罪。
  残る違いは checked 演算だけで、外すと **83 倍**速くなった。

- **外した仮説**:
  1. 「`try`/`catch` がループの最適化を阻害している」→ **外れ**。差は 0.1%。
  2. 「Vararg (`vs::AbstractVector...`) のタプル反復が型不安定で遅い」→ 外れ。
     別関数に切り出しても変わらなかった時点で否定された。

- **原因**: **`Int128` にはハードウェアのオーバーフローフラグが無い。**
  x86-64 の `mul` が立てる OF/CF は 64 bit 幅までで、128 bit の乗算は
  複数命令に展開されるため、Julia の `checked_mul(::Int128, ::Int128)` は
  ソフトウェアで検査する。**演算ごとに**その検査を払っていた。
  `Int64` なら 1 命令 + `jo` で済むので、同じ書き方でも問題は出ない ―
  **`Int64` で試していたら、この罠には気づかないまま通り過ぎていた。**

- **修正**: オーバーフローの議論を**演算ごと**から**入力の範囲**へ移した。
  `|c| ≤ 2^40` なら各二乗は `2^80` 以下、`2^47` 個未満の和は `2^127` 未満。
  係数あたり比較 2 回が、emulate された 128 bit checked 演算 2 回を置き換える。
  範囲外は `BigInt` 経路に落ちるので**厳密性は変わらない**。
  結果 **0.291 ms → 0.00128 ms（227 倍）**。

- **回帰テスト**: `test/test_poly.jl` の `"sqnorm"`。
  既存のテストは `BigInt(2)^40` しか使っておらず、その二乗和は `2^81` で
  `Int128` に収まる ― つまり**フォールバック経路を一度も通っていなかった**。
  追加したのは:
  (a) `Int128` に入らない単独の係数（`2^200`）、

```
     8       1        408          8        416
     4       2        808         32        808
```

### 修正 1: `karamul` を三段構えに

`bits(a) + bits(b) + log2(n)` が
`Int64` に収まれば `Int64`、`Int128` に収まれば `Int128`、
どちらも駄目なら従来の Karatsuba/`BigInt`。
上界は負巡回畳み込みの厳密なもので、`bitsize` がバイト単位に切り上げるぶん
**安全側**に倒れる。高速経路は schoolbook（Karatsuba ではない）―
この実装では割り当てがコストであり、
Karatsuba は 1 命令で済む乗算を減らすために O(n^1.58) の一時配列を作るから
（#032 の NTT が学校算法より 7.4 倍遅い件と同じ理由）。

**結果は 14% しか改善しなかった。** しかも n=128 の `karamul` が
**11.21 → 34.13 ms と遅くなった。**

```python
while val != 0: res += 8; val >>= 8
```

1 反復あたり約 20 万回の確保 × 261 反復 ―
**これが 8 GB のほぼ全部だった。**

GMP は答えを limb 数として持っている。`ndigits(a, base=2)` は O(1)。

- **外した仮説（4 つ）**:
  1. 「`hash_to_point` が遅いのは `elt % q` の除算（`q` がキーワード引数で

     わずかに下回るので、**約半分の呼び出しが 2 ブロック目を squeeze** し、
     SHAKE の仕事が倍になっていた。部品の和が全体の半分にしかならないのを

     0.0047 → 0.0061 と遅くなった。`byte_at` が 2 ロード必要なのに対し、

     賢い経路の代金だけ毎回払っていた。

- **修正**: 上記 8 点。**`polymulq` / `ntt` / `intt` は一切変えていない** ―

  - `test_shake.jl` `"squeezing in pieces gives the same stream..."`:
    memcpy 化はレーンのバイト順とスポンジのバイト順が一致する前提なので、
    1 回の大きな squeeze と、乱数長の分割 squeeze と、
    rate 境界ちょうどの繰り返しが一致することを主張。

     **勝てる相手を選んで勝ちを主張しない。**
  2. **最適化の 3 打数 1 安打。** 8 つの変更のうち 3 つは

  3. **速度版を並置し、遅い版を消さなかったのが効いた。**
     `polymulq` と `polymulq_ntt` が残っているから、
     `polymulq_fast` を 2 つの独立なオラクルで検証できた。
     仕様準拠の実装は、性能版の**テストオラクル**として価値がある。

## [2026-08-21] #039 C に勝った

- **モジュール**: ntt.jl, shake.jl, encoding.jl, falcon.jl
- **症状**: バグではない。#038 で 1.25 倍差まで詰めて止めたところを、
  「読みやすさを捨ててよいから勝て」という指示で再開した。

### 結果（verify、バイトからバイトまで、20000 反復の中央値、3 ラウンド交互測定）

| | round 1 | round 2 | round 3 |
|:---|---:|---:|---:|
| **Julia（この実装）** | **0.02550** | **0.02554** | **0.02582** |
| C `clang -O3 -march=native` | 0.02664 | 0.02666 | 0.02667 |
| C `clang -O3`（参照実装の Makefile） | 0.02752 | 0.02750 | 0.02746 |
| C `gcc -O3 -march=native` | 0.02784 | 0.02783 | 0.02772 |

**3 ラウンドすべてで、すべての C ビルドより速い。**
最速の C（`clang -O3 -march=native`）比で **3〜4% 速く**、
参照実装自身のビルド比で **6〜7% 速い**。
最小値では 0.0215 対 0.0227。

`verify` 全体では **0.251 ms → 0.0255 ms、9.8 倍**。

### 決め手: 短い段はベクトル化できない

段ごとに測ると原因は一目瞭然だった（n=512、1 バタフライあたり ns）:

| len | 256 | 128 | 64 | 32 | 16 | 8 | **4** | **2** | **1** |
|:---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| ns | 0.67 | 0.68 | 0.72 | 0.80 | 0.92 | 1.27 | **2.95** | **3.71** | **5.34** |

**最後の 3 段が NTT の 70%。** 演算量は全段同じ（各段 n/2 バタフライ）で、
違うのは内側ループの長さだけ。`len=1` では内側が 1 反復なので
ベクトル化する余地がゼロで、ループ制御とメモリ往復を毎回丸ごと払う。

そこで **len=4,2,1 を 1 パスに融合**し、連続 8 係数を 8 個のローカルに載せて
12 バタフライをレジスタ上で回す。配列を 3 回舐めるのが 1 回になり、
12 バタフライを囲むループが消える。

- 前進 NTT: 4.17 → **1.74 µs**
- 逆 NTT: 5.36 → 3.11 → **2.62 µs**（逆は最初の 3 段が短い側）

### 効いた変更の一覧

| 変更 | 効果 |
|:---|:---|
| radix-8 融合カーネル（前進・逆） | NTT 4.17→1.74、5.36→2.62 µs |
| `_reduce_u32` を**分岐なし**に | verify 0.02771 → 0.02652 |
| 逆変換の twiddle を事前計算（`q−ζ` と `1/n` を畳み込み） | 逆 NTT 3.11 → 2.62 µs |
| `decompress_sig` を 64 bit 窓 + `leading_zeros` に | 3.9 → 3.7 µs |
| `hash_to_point` を rate ブロック単位に | 10 → 8.5 permutation/呼び出し |
| `squeeze!(x, out, off, n)`（確保しない版）を追加 | 上記の前提 |

**`_reduce_u32` の分岐が地味に大きかった。** 署名の `s2` は中心化されていて
正負がほぼ半々・順序に規則性がないので、
「よくある範囲を先に判定する」分岐は**512 回連続で予測を外す**。
`x % Q`（定数なので multiply-shift）+ 算術シフトによる条件加算で分岐を全部消した。

### 外した仮説（3 つ、いずれも「速くしたつもりが遅くなった」）

1. **`decode_signature` に `@view` を渡す**（625 バイトのコピーを省く）
   → **0.02580 → 0.02834 と悪化**。`SubArray` の間接参照を
   ビットループが 512 回払う。コピーのほうが安い。
2. **`msg` を `collect` せず渡す**（コピーを省く）→ 同上で悪化。
   `message isa AbstractString ? codeunits(...) : message` は
   `msg` を Union にするので、以降が動的ディスパッチになる。
   **小さなコピー 1 回のほうが、型の具象性より安いことはない。**
3. **C と同じ UInt16 + Montgomery**（#038 で既に外していた）→ 再確認、2 倍遅い。

**3 つとも「メモリを触らないほうが速い」という一般論から出ていて、
3 つとも外れた。** Julia では**型が具象であること**のほうが優先度が高い。

- **原因**: （バグではない）
- **修正**: 上記。**`polymulq` / `ntt` / `intt` / `karamul` は一切変えていない。**
- **回帰テスト**:
  - `test_ntt.jl`: `polymulq_fast` を **`polymulq` と `polymulq_ntt` の
    2 つの独立なオラクル**に対して n=2..1024 で照合（負の入力込み）。
    根が負巡回であること、`ntt_ip!` の `@allocated == 0`。
    **`intt_zetas` の畳み込みを直接主張** ―
    `iz[k] == q − z[k]`、ただし `k=2` かつ `n>8` のときだけ `1/n` 倍。
    往復テストでは相殺する誤りを見逃すので、関係式そのものを書いた。
  - `test_encoding.jl`: `decompress_sig` を**元のビット単位実装をオラクルとして**
    ランダム 40000 件・実エンコーディングの 1 bit 反転・長い unary・
    全 0/全 1 で照合。攻撃者入力のパーサなので、
    「正しい入力が通る」ではなく「**元と同じものを同じだけ拒否する**」が要件。
  - `test_shake.jl`: `squeeze!(x, out, off, n)` が確保版と同じストリームを出すこと、
    範囲外書き込みを拒否すること。
  - **60708 件全合格**。SHAKE256 KAT と C 参照実装の実署名の受理は
    全変更を通して一度も落ちていない。
- **学び**:
  1. **勝敗を分けたのは算術ではなくループの形だった。**
     モジュラ乗算をどう速くするか（Montgomery、16 bit 化）は 2 回とも外れ、
     効いたのは「短すぎる 3 段を融合する」という構造の変更。
     **段ごとに測っていなければ絶対に思いつかなかった。**
  2. **`-march=native` の C を相手にしたのは正しかった。**
     Julia は既定でホスト向けにネイティブコンパイルするので、
     移植可能バイナリの C と比べるのは不公平になる。
     一番速い C に勝ってはじめて勝ちと言える。
  3. **「読みやすさを捨てる」の実際の中身は、可読性ではなく*局所性*だった。**
     radix-8 カーネルは 40 行の展開コードで確かに読みにくいが、
     仕様に対応する `ntt` / `intt` は隣に無傷で残っている。
     **速度版が読めなくても、遅い版がテストオラクルとして残っていれば検証できる。**
     これが #038 から一貫して効いている構造である。

## [2026-08-21] #040 鍵生成は「仕方ない」ではなかった ― もう 1.34 倍、そして残りの正体

- **モジュール**: ntrugen.jl
- **症状**: バグではない。「鍵生成が遅いのはもう仕方ないか」という問いに、
  #036 の時点で「C と同じ RNS を書かない限り縮まない」と答えていた。
  **その断定には根拠が無かった**ので、測り直した。

### `babai_reduce` の 1 反復を分解する

n=128 の `babai_reduce` は鍵生成の 83%。その 1 反復の内訳:

| 段階 | ms | 割合 |
|:---|---:|---:|
| **`F[i] -= fk[i] << shift`（と G）** | **0.2620** | **64.2%** |
| `karamul f*ki, g*ki` | 0.0669 | 16.4% |
| `fft` ×2 | 0.0293 | 7.2% |
| `BigInt >>`（上位 53 bit） | 0.0240 | 5.9% |
| `div_fft` + `ifft` | 0.0130 | 3.2% |
| その他 | 0.0127 | 3.1% |

**1 行が 64%。** しかもその 1 行がやっているのは
「56 bit の値を 6250 bit 左シフトして引く」だけである。
生の limb 演算量を数えると 261 反復 × 256 係数 × 98 limb ≈ 650 万 limb 演算、
1 limb 1 ns としても 6.5 ms 相当 ― **実測 68 ms は 10 倍の開き**があった。
差は全部、**係数ごとに 790 バイトの `BigInt` を 2 個確保していること**である。

### 修正

`Base.GMP.MPZ` の in-place API に置き換えた:

```julia
MPZ.mul_2exp!(tmp, fk[i], shift)   # tmp = fk[i] << shift
MPZ.sub!(F[i], tmp)                # F[i] -= tmp
```

limb 数は変わらない。消えるのは確保と、その後ろの GC だけ。

**0.2620 → 0.0256 ms、10.2 倍。** limb 数から見積もった理論値どおり。

そのために `F`, `G` を**深いコピー**にする必要があった ―
`copy(F)` は配列を複製するが中の `BigInt` は複製しない。
以前は `F[i] -= ...` が新しい `BigInt` を作って束縛し直していたので
それで無害だったが、in-place にした途端に**呼び出し元のデータを壊す**。
回帰テストで明示的に押さえた。

### 結果

| keygen (n=512, 15 サンプル) | median | mean | min |
|:---|---:|---:|---:|
| 変更前 | 249.7 ms | 294.1 | 160.6 |
| **変更後** | **186.1 ms** | 196.6 | **101.5** |

当初からの通算: **9610 → 186 ms、52 倍。**

C との比較（同時刻、30 サンプル）:

| | keygen ms |
|:---|---:|
| **Julia** | **186.1** |
| C `clang -O3`（native FP） | 7.15 |
| C `clang -O3`（FPEMU、参照実装の既定） | 14.24 |
| C `gcc -O2`（FPEMU） | 16.62 |

**まだ 13〜26 倍負けている。**

- **外した仮説**:
  1. 「底で本物の 6200 bit 演算が要るのだから、RNS 以外に手は無い」
     → **外れ**。6200 bit なのは `F`, `G` であって、
     **掛ける相手（`f`, `ki`）は 24 bit** である（#036 で確認済み）。
     6200 bit 側にかかる操作はシフトと加減算だけで、
     それらは in-place にできる。**「多倍長が要る」と
     「多倍長の確保が要る」は別の話だった。**
  2. 「`profile_ntrusolve.jl` の段別の数字で改善を確認できる」→ **外れ**。
     修正後にそれを走らせると `babai` は 125 → 56 ms と改善したのに、
     **触っていない `karamul` が 11.7 → 131 ms に跳ね**、
     合計は 150 → 297 ms と悪化して見えた。
     このスクリプトは**降下を 1 回だけ走らせ、各段 1 サンプル**なので、
     GC がどの段に落ちるかで数字が丸ごと動く。
     端から端で 15 サンプル取ると 249.7 → 186.1 ms と正しく出た。
     **#035 と同じ失敗を、別の道具で繰り返した。**

- **原因**: （バグではない）
- **修正**: `babai_reduce` の更新を in-place GMP に。深いコピーを追加。
- **回帰テスト**:
  - `test_ntrugen.jl` の `"ntru_solve reproduces the reference exactly"` が
    n=2..128 で通り続けること ― in-place 化で 1 bit でも変われば落ちる。
  - **`babai_reduce` が引数を破壊しないこと**を新たに主張。
    これは in-place 化で初めて壊れうるようになった性質で、
    壊れても最終結果は（呼び出し元がその配列を再利用しない限り）
    正しく見えるため、テストが無ければ気づけない。
  - 60708 件全合格。

- **残っているもの**（もう単独で支配的な項目は無い）:

  | | 1 反復あたりの割合 |
  |:---|---:|
  | `karamul f*ki, g*ki` | 41.7% |
  | `BigInt >>`（上位 53 bit） | 15.1% |
  | `F -= fk << shift` | 15.5% |
  | `fft` / `ifft` / FFT 領域演算 | 21.8% |

  `karamul` は毎反復 `f` を `Int64` に変換し直している（`f` は不変）。
  `BigInt >>` は 98 limb 読んで 53 bit しか使っていない ―
  必要なのは上位 1〜2 limb だけ。
  FFT はこの実装の再帰版（毎回配列を確保）を使っている。
  どれも 10〜20% 規模で、**合わせても C との 13 倍は埋まらない**。

- **学び**:
  1. **「仕方ない」と書く前に、その 1 行を測る。**
     RNS が要ると断定した時点で、64% を占める行が
     何をしているか見ていなかった。
  2. **多倍長が必要なことと、多倍長の*確保*が必要なことは別。**
     6200 bit の値を扱う必要は本物だが、
     それを毎回作り直す必要はどこにも無かった。
  3. **in-place 化は所有権の問題を持ち込む。**
     `copy` が浅いことに気づかなければ、
     呼び出し元のデータを壊しながら正しい答えを返す実装ができていた。
     速度のための変更が**正しさの前提を変える**典型例で、
     テストを 1 本増やすまでコミットしてはいけない類の変更である。
  4. **C との 13 倍は、ここから先は本当に RNS である。**
     ただし今度はそれを**測った上で**言っている。
