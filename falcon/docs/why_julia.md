# なぜ Julia で書いたのか ― 期待と、実際に起きたこと

査読者は必ず訊く。後付けの理屈を書くより、実際の動機を書いて、
**その動機がどこで当たり、どこで外れたか**を測定で示す方が強い。

---

## 1. 当初の動機（後付けではない）

> **Julia なら速くなると思ったから。**
> とくに **Julia は行列計算が得意だ**と知っていたので、
> FFT と NTT と多項式演算が主役の FALCON は向いていると考えた。

これが本当の理由である。仮説として書き下すと:

- **H1**: 数値計算向けの言語なので、FFT / NTT / 多項式演算が C 並みかそれ以上になる。
- **H2**: 配列演算とブロードキャストが速いので、素直に書くだけで性能が出る。
- **H3**: 高水準に書けるぶん、C より読みやすく、仕様書との対応が付けやすい。

---

## 2. 何が起きたか

### H1 は当たった。ただし「行列計算が得意だから」ではない

| op | C の 12 ビルドの幅 | Julia |
|:---|---:|---:|
| `verify`（整数のみ） | 0.0166〜0.0268 ms | **0.0164〜0.0213 ms** ― 同着 |
| `sign_tree` | 0.136〜0.173（native）/ 1.59〜1.82（FPEMU） | 0.98〜1.49 |
| `keygen` | 4.98〜6.07 / 11.2〜13.2 | 11.7〜12.7 |

`verify` は C と並んだ。しかしそこに至った道は「配列演算が速い」ではない:

- NTT を**根の表の順序ごと書き換え**、最下 3 段を**レジスタ常駐の radix-8
  融合カーネル**に手で展開した（#038、2.4 倍）。
- 内積とノルムを `BigInt` から `Int128` の**範囲判定つき**経路に落とした（#034）。
- 復号のビット走査を 64 bit 窓と `leading_zeros` で書き直した（#039）。

**どれも「高水準に書いたら速かった」ではなく、
「C でやることを Julia でやった」である。**

### H2 は外れた。しかも系統的に

素直に書くと**遅い**。しかも遅さの原因が一貫していた:

| 現象 | 実測 | 出典 |
|:---|:---|:---|
| `polymulq_ntt` が schoolbook より遅い | **7.4 倍** | #032 |
| `bitsize` が 1 鍵で 5000 万回確保 | 83.6 ms → 0.005 ms | #036 |
| クロージャの捕捉変数再代入が `Core.Box` に | **34 倍** | #043 |
| 降下時間の内訳 | **55% が確保** | #044 |
| Karatsuba が schoolbook に負ける | n=2 から 2048 まで**全部**、最大 35 倍 | #047 |

最後の 2 つが H2 への直接の反証である。
`n^1.58 < n^2` は**乗算 1 回のコストが同じ**という仮定を要する。
片方が `malloc` を含むと、漸近は何も言っていない。
鍵生成が 9610 ms から 11 ms になった 875 倍のうち、
**「配列演算を使った」ことによる寄与はゼロ**である。効いたのは全部、
確保を消すこと（GMP の融合積和、機械語ワードの段、in-place GMP）だった。

### H3 は当たった、が代償があった

仕様書との対応は確かに付けやすい。
`docs/refs.md` の対応表と `test/test_spec.jl` の転記は、
C ではこの密度で書けなかったと思う。
一方で、**読みやすさを捨てた場所ほど速い**という関係が全体に出た。
`ntt.jl` の radix-8 カーネルと `ntrugen.jl` の `_negacyclic_addmul!` は、
このリポジトリで最も読みにくく、最も効いたコードである。

### 予期していなかった収穫

**Julia を選んだことの最大の効能は、速度ではなかった。**

1. **署名バイトの再現**（#050）。参照実装と bit 一致するまで詰めるという
   作業は、C で書いていたら「同じコードを書いたのだから同じで当たり前」
   になって、**仕様書と参照実装の差**が見えなかった。
   別言語で書いたからこそ、`div_fft` の書き方の差、`LDL*` の `D11` の
   書き方の差、`fpr_inv_sigma` が σ の逆数でないことが表に出た。
2. **定数時間性の切り分け**（#051）。Julia では処理系由来の変時間性を
   閉じられない。それは弱点だが、**閉じられないことが分かっている**ので、
   残った漏洩がアルゴリズム由来か処理系由来かを分けて議論できる。

## 3. 正直に言うと

**「行列計算が得意だから FALCON に向いている」という当初の見立ては、
外れていた。**

FALCON の重い部分は行列計算ではない:

- 鍵生成の支配項は **Babai 縮約**で、これは**多倍長整数の積和**である。
  論文 §5.5 も「支配的なコストは Babai 縮約のままである」と書いている。
- 署名の支配項は **ffSampling の再帰**で、これは長さ 1〜n の
  複素ベクトルに対する**分割統治**であり、大きな行列積ではない。
- `verify` の支配項は **NTT** で、これは配列演算ではなく
  **バタフライのメモリアクセスパターン**である。

つまり、この問題領域には BLAS 的な塊が無い。
Julia の強みとされる部分は、ここでは効かなかった。

**それでも Julia を選んだことは無駄ではなかった** ―
ただしその理由は、当初考えていた理由とは違う。
上の「予期していなかった収穫」の 2 つがそれである。

---

## 4. 査読者への一文

> 我々が Julia を選んだのは、数値計算向け言語なら FFT と多項式演算が速いと
> 期待したからである。その期待は `verify` については当たり（C と同着）、
> 鍵生成については**外れた** ― 875 倍の高速化のうち高水準の配列演算に
> 由来する部分は無く、すべて確保の除去によるものだった。
> 結果として本研究の主たる貢献は性能ではなく、
> **参照実装から独立に書かれた実装が、参照実装の署名をビット単位で
> 再現するために何を必要とし、何を必要としなかったか**の測定になった。
> それは同じ言語で書き直していたら得られなかった。
