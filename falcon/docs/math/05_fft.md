# モジュール 5: FFT ― 浮動小数点が「仕様」になるということ

## 5.1 この章で答える問い

構造だけ見れば、この章は前章の焼き直しである。`Z_q` を `C` に、
2n 乗根を `exp(iπk/n)` に置き換えれば、`split` / `merge` の再帰も
バタフライも同じ。実際 Python 参照実装の `fft.py` と `ntt.py` は
「テンプレート化すればひとつにできる」とコメントに書かれている。

にもかかわらず、この章が本の中心になる。理由は 3 つ。

1. **なぜ FALCON は浮動小数点を使わざるを得ないのか**
2. **なぜ FFTW ではだめなのか**
3. **なぜ「Float64 の結果がプラットフォーム間で bit 単位に一致すること」が
   セキュリティ要件になるのか**

3 番目が、序盤で立てた問い「NIST PQC 4 方式のうち、なぜ FN-DSA だけ
標準化が遅れたのか」への、この章での回収である。

## 5.2 なぜ浮動小数点が要るのか

Dilithium は `Z_q` から一歩も出ない。FALCON は出ざるを得ない。

署名は**格子上の Gaussian** からのサンプリングで作る。そのサンプラは
Gram 行列の LDL\* 分解（Cholesky の親戚）を作り、その木を降りながら
各ノードで整数を引く。LDL\* には**平方根と除算**が要る。

`Z_q` に平方根や除算が無いわけではない。だが意味が無い。
「短い」というのは剰余の話ではなく**実埋め込みでの長さ**の話だからだ。
`q - 1` は `Z_q` では小さい元（`-1`）だが、
ノルムを測るときは `-1` として測らねばならない。
短さを扱う以上、実数体（と、その上の複素埋め込み）に出るしかない。

つまり FALCON の浮動小数点は、速度のための近似ではなく、
**扱っている量が実数だから**である。ここが Dilithium との分水嶺。

## 5.3 なぜ FFTW ではだめなのか

FFTW は「FFT」をくれる。FALCON が要るのは「**この** FFT」である。

`ffLDL` は次の再帰で二分木を作る。

```
f(x) = f0(x²) + x·f1(x²)
```

これは部分体の塔 `Q(ζ_4) ⊂ Q(ζ_8) ⊂ … ⊂ Q(ζ_2n)` を 1 段ずつ降りる操作
（モジュール 3 参照）。そして `ffSampling` は**その木を降りながら**、
途中のノードで `splitfft` / `mergefft` を**直接呼ぶ**。

つまり `splitfft` / `mergefft` は変換の内部実装ではなく、
**サンプラが呼ぶ公開 API** である。基数の違う FFT や出力順の違う FFT は、
同じ多項式の同じ評価値を返しても、木の形が違えば使えない。

これが「FFTW に頼らず自前で書く」ことの実質的な理由であって、
「依存を減らしたい」ではない。

## 5.4 根のテーブル ― NTT と同じ木、違う順序

`x^n+1` の根は `w_k = exp(iπk/n)`（k は奇数）。生成則は NTT と同型:

- 底: `x²+1` の根は `±i`、指数で `k = ±1`
- 1 段上: 親 `w` の上には `±√w` の 2 つ。指数では `k ↦ {k, k∓n}`
  （`|k| < 2n` に収まるよう符号を選ぶ）
- ペアの先頭は**主平方根**（偏角が `(-π/2, π/2]`）

この規則で生成したテーブルは、参照実装のハードコード表と
n = 2〜1024 で一致する（差 9.1e-16、これは参照表自身の丸め誤差）。

### ただし NTT とは順序が違う

ここは踏んだ罠なので明示しておく。

- NTT はペアを**剰余の小さい順**に並べる
- FFT はペアを**主平方根が先**に並べる

**この 2 つの基準は一致しない。** 実際、両者の指数列を同じ単位に
揃えて比べると、**集合としては同じだが列としては異なる**
（n = 4, 8, 16, 512 すべてで確認）。
つまり `ntt_roots(n)[j]` と `fft_roots(n)[j]` は、
一般に**互いの符号違い**の根を指している。

害は無い。NTT と FFT は別の対象に適用されるからだ
（NTT は公開鍵の mod q 演算に、FFT は秘密基底の実数演算に）。
共有されているのは**木の形**（ペアであること、親 = 二乗であること）で、
`split`/`merge` の再帰が乗っているのはそちらである。

しかし「同じ表を 2 つの環で読んだもの」という自然な推測は**誤り**なので、
テストに明示的な主張として残してある。

## 5.5 `split_fft` の共役 ― 例の符号

```julia
f1[i] = 0.5 * (f_fft[2i-1] - f_fft[2i]) * conj(w[2i-1])
```

数学的には `/(2w)` である。`|w| = 1` なので `1/w = conj(w)`。
共役を使うほうが速く、しかも**除算より正確**。

ここを `* w` と書くと（逆回転が共役であることを忘れると）、
往復テストは落ちるが、もっと悪いことに
**木のノード値が静かに間違ったまま ffLDL が完走する**。
症状は「署名が検証を通らない」で、原因からは遠い。

テストには「わざと `* w` にしたら壊れること」を主張する項目を入れてある
（相対 0.95 の差が出る、つまり静かには壊れない）。
正しさのテストだけでなく、**間違いが大声で失敗することのテスト**である。

## 5.6 誤差はどこまで許されるか ― 測った値

仕様書には誤差解析の議論があるはずだが、
この実装を書いたセッションからは PDF に到達できなかった（debug_log #002）。
**なので以下は引用ではなく実測**である。仕様の議論の代用にはならない。

n = 512、倍精度、この再帰での実測値:

| 係数の大きさ | 往復誤差 | 積の誤差 |
|---:|---:|---:|
| `|c| ≤ 10`（f, g 相当） | 2.5e-14 | 5.0e-12 |
| `|c| ≤ 6144`（署名相当） | 1.7e-11 | 1.5e-06 |
| `|c| ≤ 1e6`（F, G の中間値相当） | 2.6e-09 | **4.3e-02** |

往復誤差は相対 2.5e-15、教科書どおりの FFT の挙動。
面白いのは**積の列**のほうだ。

FALCON が積に要求するのは「**整数に丸めたら正しい**」ことだけなので、
許容誤差は絶対値で **0.5**。署名サイズでは 5 桁の余裕がある。
しかし係数が 1e6 になると余裕は 10 倍しかなく、1e7 で**消える**。

これが「どこで多倍長が必要になるか」への定量的な答えである。
「数が大きそうだから」ではなく、
**FFT の積の誤差が 1/2 を超える地点から**。
モジュール 6（NTRU 求解）でここに突き当たる。

## 5.7 定数時間性ではなく「決定性」の話

ここが本章の山場である。

C 参照実装（algorand fork）の `config.h` を読むと、
浮動小数点**エミュレーション**が既定で有効になっており、
こう書かれている:

> *** CRITICAL SECURITY WARNING ***:
> ここで浮動小数点エミュレーションを有効にしているのは、
> **信頼できる決定的署名**を得るためである。ネイティブ FPU やコード最適化は
> わずかな差異を生み、決定性に影響しうる。
> **FALCON_FPEMU を有効のままにすることを強く推奨する。**
> 署名の非決定性は**壊滅的なセキュリティ障害**につながりうる。
> すなわち、同一メッセージに対する 2 つ以上の異なる署名を得た攻撃者が、
> 任意メッセージの偽造を作れるようになる可能性がある。

つまり FALCON にとって、
**Float64 の結果がプラットフォーム間で bit 単位に再現すること自体が
セキュリティ性質**である。「そのほうが望ましい」ではない。

なぜそこまで効くのか。FALCON の署名は
「ハッシュ点 c を格子の点にずらす」形で作られ、ずらし方は
秘密基底に依存した Gaussian から引く。同じ (鍵, メッセージ, salt) から
**別の** `(s1, s2)` が 2 つ得られると、その差は格子の元であり、
しかも短い。短い格子ベクトルは秘密基底そのものの情報である。
署名を集めるほど基底が復元されていく。

だから参照実装は、FPU を信用せず、
**整数演算で IEEE-754 binary64 を自前でエミュレート**する道を選んでいる。
（エミュレーション版の定数表は `uint64` の bit パターンとして焼かれており、
実際に IEEE-754 の bit 列そのものだった。）

そしてこれが、序盤の問いの答えである。

> **NIST PQC 4 方式のうち、なぜ FN-DSA だけ標準化が遅れたのか。**

ML-DSA も SLH-DSA も HQC も、整数演算だけで閉じている。
標準化とは「誰が実装しても同じ答えになる手順を書き下すこと」だが、
整数演算ならそれは容易だ。FALCON だけが、
**浮動小数点の丸めまで含めて手順を固定しなければならない**。
しかも実装は同時に定数時間でなければならない（モジュール 7・8）。
「bit 単位に再現し、かつ秘密に依存して分岐しない浮動小数点」
という要求は、他の 3 方式には一切存在しない。

## 5.8 C 参照実装との突き合わせ ― 表現が違う

前章で「fft.jl から C との突き合わせが素直に効く」と書いたが、
**これは誤りだった**（debug_log #011）。C の FFT 表現は我々のものと違う。

- **半分しか持たない。** 実多項式の FFT は共役対称なので、
  C は `n/2` 個の複素数しか保持しない
  （我々と Python 参照実装は冗長に `n` 個持つ）。
- **実部と虚部を分けて置く。** `n/2` 個の実部の後に `n/2` 個の虚部。
- **順序が違う。** 前半 `n/2` 個の中での並びが、
  我々の並びと**グレイコード置換**でずれている。
  C の添字 `k` は我々の添字 `k XOR (k >> 1)`（0 始まり）に対応する。

最後の項は `inner.h` に書かれていない（"see falcon-fft.c for details on the
internal representation" とあるだけ）。実際に C 参照実装をビルドして
n = 4〜1024 で出力を突き合わせ、**実験的に determine した**。

対応が付いたので、`from_c_fft` / `to_c_fft` として実装に入れてある。
C 実装から取った実際のベクタが `test/vectors/fft_c_kat.jl` にあり、
Julia のテストはそれに対して**相対 1e-10** で照合する
（Python 参照実装に対しては 1e-9 と緩い。理由は次節）。

## 5.9 参照実装 2 つの精度差

副産物として分かったこと。

- **Python 参照実装の根テーブルは 15 桁しかない。**
  `0.707106781186548` は正しく丸めた倍精度 `0.70710678118654757` から
  2 ulp ずれている。n = 512 では最大 **約 370 ulp** の誤差がある。
- **C 参照実装の表は 27 桁**（`0.707106781186547524400844362`）で、
  正しく丸めた倍精度になる。エミュレーション版の `uint64` bit パターンも
  IEEE-754 のそれと完全一致。

我々の実装は `cispi(k/n)` で計算する。`n` が 2 冪なので `k/n` は
2 進で厳密、したがって根は 1 ulp 程度の精度になる。
**つまり Python 参照実装より正確**であり、だから Python 由来のベクタとは
「一致」ではなく「許容誤差内」で比べるしかない。
実測すると、我々は C とは 2.3e-13、Python とは 1.2e-15〜3.9e-12 で一致する。

「参照実装が正典」という素朴な態度が成立しない実例である。
参照実装は 2 つあり、精度が違い、
**そして KAT を定義しているのは C のほう**。

## 5.10 Dilithium との対比（まとめ）

| | Dilithium | FALCON |
|:---|:---|:---|
| 実数演算 | 無し | **必須**（LDL\*, Gaussian） |
| 変換 | NTT のみ | NTT と FFT |
| FFT の役割 | — | サンプラの木そのもの |
| 決定性 | 整数なので自明 | **bit 再現がセキュリティ要件** |
| 標準化の争点 | 実装最適化 | **浮動小数点の規定** |
| 参照実装の FP | — | 既定でソフトウェアエミュレーション |

Dilithium を移植したときに「浮動小数点をどう扱うか」を
一度も考えずに済んだのは、偶然でも幸運でもない。
**そこが 2 つの方式の設計上の分岐点**であり、
片方が 2024 年に標準化され、もう片方が 2026 年になっても
ドラフトのままである理由でもある。
