要旨

FALCON ― NIST が FN-DSA として標準化する格子署名 ― は、選定された署名の中で唯一、出力が浮動小数点演算の関数になる。しかも仕様書の精度解析は、サンプラが出力する分布についてのものであって、二つの適合実装が同じバイト列を返すかどうかについてではない。我々は仕様書だけを読んで Julia で独立実装を書き、参照実装の署名をバイト単位で再現するまで突き合わせた。その突き合わせが、仕様書が中間値を決めていない箇所を 3 クラス炙り出す ― 演算の書き方、公開パラメータから導けない定数、使われているのに印字されていない ε。

そのうち二つの書き方 ― 複素除算と LDL* の D11 ― は署名を 40 万本あたり 3 本、率にして 7.5×10⁻⁶ で変える。しかも必ず最後の 2 回のサンプラ呼び出し、すなわち ePrint 2024/1709（Lin–Tibouchi–Yu–Zhang, EUROCRYPT 2025）が 1 ペアから秘密鍵の全復元に使う位置で。同論文が扱う摂動と違い、これは仕様書と参照実装の差であり、参照実装の両 signing mode に共通に存在し、同論文の対策では塞がらない。我々は同論文の機構を別経路から追認し、同論文が測っていない Heuristic 1 を直接検証する。

さらに二つの結果は、同論文が「使えない」として脇に置いた最初の 2 回に関わる。第一に、最初の 2 回の中心は厳密に (c·f)[n/2−1] / q、すなわち秘密についての公開線形形式である。だからそこでの整数中心は F_q 上の方程式 1 本にほかならず、n−1 個の事象を集めれば、差ベクトルも格子簡約も使わずにガウス消去だけで秘密鍵が戻る ― 実際に走らせた。第二に、そのチャネルが必要とするオラクルは、摂動の大きさについての両側の窓の中にだけ存在する。窓の両端を実測した。本稿自身の「書き方の差」は窓の下にある。しかし最適化オプション一つが窓の中に落ちる ― clang -ffp-contract=fast で建てた C 参照実装は、既定で建てた同じ clang と 10 万本中 12 本で食い違い、そのうち 8 組から秘密鍵が出る ― しかも復元した鍵で新しいメッセージに署名すると、被害者の公開鍵が 8 件とも受理する（万能偽造、約 1.3×10⁴ メッセージ）。普通のビルドの選択 9 通り（2 コンパイラ、native 対 emulated、参照実装自身の手書き AVX2 経路）は全部バイト一致するので、危険なのはビルドのばらつき一般ではなく旗ひとつである。しかもスカラー経路ではなくベクトル経路を縮約すると、さらに第 3 の互いに矛盾する列が出る。

01 — 問い

仕様書は署名を決めているか？

FALCON は出力を浮動小数点演算で計算する。ガウスサンプラは Complex{Float64} 上で高速フーリエ最近点再帰を回し、サンプルされる整数 ― そして署名 ― は、その再帰が生む浮動小数点値そのものの関数である。ML-DSA（FIPS 204）と SLH-DSA（FIPS 205）は整数・ハッシュベースで、同じ鍵・メッセージ・乱数を与えれば、どの適合実装でも構成上同じバイト列を返す。FALCON にその保証はなく、仕様書もそれを意図していない ― §2.5.2 は浮動小数点精度をサンプル分布についての Rényi 発散論法で解析し、§4.1 は C の double が IEEE-754 に「少なくとも一致」すればよいとする。どちらも分布の話であって、二実装がビット単位で一致するかの話ではない。

この区別が今や効いてくる。FIPS 206 の状況報告（Perlner, NIST, 2025年9月）は、標準が浮動小数点の演算順序を規定し、FMA を禁じ、実装が KAT にビット一致することを求める方向を示す。標準がビット一致を求めるなら、「仕様書は中間値を決めているか」は規範上の問いになる。本稿は第二の実装を作り、参照実装とどこで食い違うかを正確に測ることでこれに答える。

なぜ Julia か ― 正直に

我々が Julia を選んだのは、速いと期待したからだ。ネイティブ配列と数値計算の評判から、行列が重い部分（FFT・NTT・グラム行列）は書きやすく走りやすいだろうと踏んだ。それは部分的にしか当たらなかった（§6）。もう一つ、本物だが後から気づいた理由があり、そう明記する。FALCON のセキュリティ関連の時間変動には二つの源がある ― アルゴリズム由来（棄却サンプラのデータ依存ループ）と実装由来（GC・JIT・境界検査・動的ディスパッチ）。ガベージコレクト・JIT の言語は後者を閉じることが原理的にできない ― だからこそ、実装由来の変動に隠されずに仕様レベルの変動を観察する、きれいな計測器になる。自分の処理系由来の変動を隠せない言語こそ、仕様書由来の変動が素で現れる言語である。この理由で選んだのではないが、結果としてこの問いに適していた。

02 — 未決定性

仕様書が開けたままの 3 箇所

実装を参照実装と段階ごとに生の 64 ビットパターンで突き合わせると、浮動小数点経路は 3 群に分かれる ― 無改修で一致する原始関数（FFT 一族と B0 行列全体、5120/5120 double）、参照実装の書き方にして初めて一致する 3 つの計算、そして別規約で格納された 1 つの定数。3 つの書き方は代数的に同値で丸めが違う。最初の 2 つについて、両実装パターンを走るコードで示す。

(a) 複素除算

仕様書に式はない。読者は言語の複素除算を使う ― Julia も Python も Smith のアルゴリズムだ。参照実装は逆数を明示的に作る。Smith が数値的に優れ、参照実装のものが KAT を規定する。

パターン S ― 仕様の読者（Julia の /）# Smith のアルゴリズム、数値的に良い
ComplexF64[ f[i] / g[i]
            for i in eachindex(f) ]
パターン C ― 参照実装（FPC_DIV）br = real(b); bi = imag(b)
m  = 1.0 / (br*br + bi*bi)
br *= m; bi *= -m
ComplexF64(ar*br - ai*bi,
           ar*bi + ai*br)

(b) LDL* の D11

Algorithm 8 と Python 参照実装は D11 を乗算 3 回で計算し、C 参照実装は商を逆向きに保って畳み込み、乗算 1 回で済ませる。G00 がエルミート＝実数なので等しい。

パターン S ― Algorithm 8 / Python# 乗算 3 回
L10 = div_fft(G[2,1], G[1,1])
D11 = sub_fft(G[2,2],
        mul_fft(mul_fft(L10,
          adj_fft(L10)), G[1,1]))
パターン C ― Zf(poly_LDL_fft)# 乗算 1 回
G01 = adj_fft(G[2,1])
mu  = div_fft(G01, G[1,1])
L10 = adj_fft(mu)
D11 = sub_fft(G[2,2],
        mul_fft(mu, G[2,1]))

3 つ目の書き方 (c) は、参照実装が ffSampling の最下 2 段を手展開し、split/merge の捻り係数を 1/√2・1/√8 に畳んだものだ。3 つは with_spec_spelling(f; cdiv, ldl, ffsampling) で独立に切り替わり、既定は参照実装の書き方 ― この独立性こそが要で、発散を一つの式に帰属できる。あと 2 クラスは定数だ ― (II) fpr_inv_sigma は印字された σ の正しく丸めた逆数ではなく（§5）、(III) σ_min は本文が印字しない ε を使う。

03 — 伝播

どの選択が署名に届くか

100 個の鍵それぞれを、鍵・メッセージ・PRNG 状態を揃えたまま二つの書き方で何度も署名し、署名が食い違う回数を数える。測定前に、各腕が木の 9728 個の double のうち何個を動かすかを印字する ― どのゼロも「何もしていない腕」ではないことを示すためだ。

A1 は陽性対照 ― ePrint 2024/1709 §6.1 の sign_dyn/sign_tree の差そのもので、率（52.5 万本で 1.9×10⁻⁵）は同論文 Table 2 に載る。B は陰性対照で、そのゼロは理論から予期される ― 幅を摂動し、同論文 Lemma 2 がそれを ≈10⁻¹¹ と抑える。分解能より遥か下なので、ゼロは何も語らない。A2 が、同論文にない腕であり、ゼロでない ― そして n=1024 でも再現する（35 万本で 1 件、やはり最後の 2 回、floor が 427/426 をまたぎ、幅はビット一致）。A2 と A1 は点推定で 2.5 倍違うが有意でなく（p ≈ 0.23）、ともに 10⁻⁵ の桁 ― 機構を共有することと整合するので、順序ではなく同程度と報告する。

A2 の 3 件はすべて機構を正確になぞる ― 3 件とも呼び出し 2n−1 か 2n、3 件とも整数をまたぎ、3 件とも該当節点の幅がビット一致。つまり発散は中心だけで起きている：

# scripts/first_divergence.jl
key 70 sig  534   call 1023/1024   mu -267.00000000000006  vs -267
key 65 sig 1239   call 1023/1024   mu  337                 vs  336.99999999999994
key 68 sig 1885   call 1024/1024   mu  285.99999999999989  vs  286

その1ペアから、鍵

「鍵回復の位置」は帰結の主張だ ― 引用でなく実行して片づける。A2 ペア（key 70, sig 534、同じ syndrome で最後の2回のサンプラ出力だけ違う2署名）の差は Δs0 = Δz0·g, Δs1 = −Δz0·f、Δz0 = a + b·x^{n/2}。(a+bx^{n/2})⁻¹ = (a−bx^{n/2})/(a²+b²) なので、復元は (a,b) ∈ {−19..19}² の探索で済み、環の逆元計算は要らない。(s, s') と公開鍵だけから：

# scripts/key_recovery.jl 70 534
hit at (a, b) = (-1, 0)
candidate reproduces the public key h (mod q): yes
|g_cand| max = 14, |f_cand| max = 13   (true |g| = 14, |f| = 13)
matches the stored secret up to negation: (f,g) = -(f_true, g_true)
*** 単一の A2 発散ペアから、秘密鍵を完全復元。***

復元された (f, g) は符号対称 (f,g) ↦ (−f,−g) を除いて格納鍵と一致 ― 同じ署名鍵だ。つまり複素除算と D11 は、署名を変えるだけでなく、syndrome を2回署名する derandomized の設定で鍵を露出させるのに十分。復元の代数は回帰テスト済み（test_falcon.jl）。

なぜ最後の2回が支配的か ― 論文が残した未解決を解いた

2024/1709 §6.1 は「整数中心を条件づけると最後の2回が最初の2回より発散しやすいが、理由は完全には分からない」と書いた（sign_dyn/sign_tree の差、FMA では起きない）。綴りが中心に与える摂動 |Δμ| を全位置で測ると、木の降下に沿って累積し、中点で段になる：

# scripts/position_profile.jl（位置ブロックごとの平均 |Δμ|）
pos    0.. 511  (z1, 第1降下) : 2.7e-15 → 1.0e-14
pos  512..1023  (z0, 第2降下) : 7.4e-14 → 8.7e-14   # ~7倍の段
最初の2回 (0,1)     : 2.7e-15
最後の2回 (1022,1023): 8.6e-14        比 ≈ 32×

段は構造的だ：ffSampling は z1 を先に引き、t0 ← t0 + (t1 − z1)·l10 を作ってから z0 を引く。z0（後半＝最後の2回を含む）の中心は上位 l10 補正を経由し、丸め差がそこに乗る。前半の中心は経由しない。中心が整数をまたぐのは |Δμ| が整数までの距離を超えるときなので、32倍大きい |Δμ| は 32倍多い発散 ― これが非対称性の正体。そして A2（木のみ）では最初の2回の |Δμ| は厳密に 0（第1葉の中心は l10 補正前の純粋な目標 split）なので、A2 の発散は構造的に最後の2回に限られる。敏感位置は固定ではなく、摂動がどこから入るかで決まる。

04 — もう一つのチャネル

誰もが脇に置いた 2 回

ePrint 2024/1709 §5 は、最初の 2 回での発散を 1 段落で退ける ― 生じる差ベクトルは「短い格子ベクトルではあるが、鍵復元を可能にするほど短いとは期待できない」。これは差ベクトルについての主張である。あの位置には、差ベクトルを一切読まないチャネルがある。

sample_preimage の第 2 成分は t1 = (−ĉ·b)/q、b = −f なので、環の元として t1 = (c·f)/q が厳密に成り立つ（c は公開のハッシュ点）。Int128 の厳密な negacyclic 演算と突き合わせると、最初の 2 回の中心はその商の係数に、固定インデックスで、浮動小数点誤差の範囲で一致する。つまり call 1 での整数中心とは、ちょうど

(c·f)[n/2−1] ≡ 0  (mod q)

― 秘密についての F_q 線形方程式 1 本であり、その係数は攻撃者が公開メッセージから計算できる。漏れているのは値ではなく事象の発生そのものである。解いてみた:

# scripts/event_solve.jl
collected 511 events from 5823368 syndromes (rate 8.77e-05, predicted 1/q = 8.14e-05)
system rank 511 of 512 unknowns
recovered vector: max |.| = 16   (true f has max |.| = 16)
matches the secret f: true  (up to sign)

n−1 件の事象で階数 511 の系ができ、核は 1 次元。核ベクトルの q−1 通りのスカラー倍を走査して最短を取ると f そのものが出る。512×512 のガウス消去 1 回、49 秒 ― 格子簡約も差ベクトルもなし。ここで二つの前提が崩れた: Δs の短さが問題だという前提と、f mod q から f への持ち上げに格子が要るという前提である。

必要なオラクルは「窓」であり、両端とも測れる

このチャネルには「どのメッセージが事象だったか」を教える何かが要る。二実装の差がそれになるのは、中心への摂動が小さすぎず大きすぎないときだけである。

小さすぎる側の境界が面白い。誰の精度の話でもないからだ。事象では真の中心は厳密な整数 m だが、両方の実装が同じ累積誤差で m + η を計算する ― FFT も木も降下も両者に共通だからである。floor が食い違うのは、差が η の符号をひっくり返したときだけ。200 件の事象で |η| の中央値は 2.8×10⁻¹⁴、そして注入した摂動 δ に対する跨ぎ確率は、ちょうどそこで立ち上がる:

δ010⁻¹⁶10⁻¹⁵10⁻¹⁴10⁻¹³10⁻¹²10⁻¹¹10⁻⁸
P(跨ぐ | 整数中心)0.0000.0000.0000.0300.2900.4250.4350.440

大きすぎる側は内部の偽陽性率である。同じ摂動は約 2n 個の一般の中心を κδ（κ = 1.62×10³）の率で跨ぎ、解法が許す偽の割合は約 1/n。両者から窓は 2.8×10⁻¹⁴ 〜 4.9×10⁻¹¹、幅 3.2 桁。

本稿自身の発見はどこにあるか

窓の下である。§02 の書き方の差は最初の 2 回の中心を 2.7×10⁻¹⁵（腕 A1）と厳密に 0（腕 A2）しか動かさない。整数中心を 10 件作って 1 件も跨がなかった以前の実験は、運が悪かったのではない。いま名前のついた閾値の、一桁下にいた。

05 — 参照実装 対 参照実装

最適化オプション一つと、秘密鍵

C99 6.5p8 は、コンパイラが a*b + c を丸め 1 回の融合積和に縮約することを許し、FP_CONTRACT がそれを制御する。FALCON 参照実装はプラグマも旗も設定せず、仕様書は縮約に言及しない。そこで模型をやめ、参照実装そのものを 3 通りに建てた ― 同じソース、同じ鍵、同じメッセージ、同じ PRNG テープ。

cl_def:    0                    [clang -O2 -march=native]
gc_def:    0                    [gcc   -O2 -march=native]

gcc default == clang default : identical over 100000 signatures

12 件中 8 件 ― そして 8 件とも偽造できた。復元された鍵はいずれも保存鍵の厳密な NTRU 対称 ±x^k(f,g) で、‖(g,−f)‖² = 16676 ≤ 1.17²q = 16822。だが公開鍵関係は「h に対する NTRU 対のひとつ」を、ノルム条件は「十分短い」を言うだけで、サンプラが回るとは言っていない。そこで、使って確かめた: 復元した各 (f,g) について fG − gF = q を解いて基底を完成させ（鍵生成が回すのと同じ降下で、攻撃者が持っていないものは要らない）、被害者が署名していないメッセージに署名し、被害者の公開鍵に出す。8 件中 8 件が受理される。署名 2 本からの万能偽造である。率が費用を決める: 鍵を渡す発散は 10 万本中 8 本なので、両ビルドの署名を同じメッセージで取れる攻撃者に必要なのは約 1.3×10⁴ メッセージ、そのあとは 40×40 の探索だけ。残る 4 件は §04 のチャネルそのもの: Δz が 2-疎でないことを厳密除算の失敗が証明し、内部の整数中心は 1.02×10⁸ 回引いて 0 件だった。差の係数数がきれいに分かれるので、攻撃者は 2 つのチャネルを区別できる。4/12 という比は、まったく別の摂動源であるにもかかわらず同論文 Table 2 の 30/70 に近い。FALCON-1024 でも再現する ― 6 万本中 6 本。x86 の特殊事情でもない: クロスツールチェインと qemu-user で aarch64 でも再実行した。実 fft.c は同じフラグでだけ縮約し（gcc は決してせず、clang は -ffp-contract=fast/-Ofast/-ffast-math のみ）、FMA が基本 ISA でも fpr ラッパが止めるので既定は縮約しない。エミュレーション下で 15 万本中 19 本（1.27×10⁻⁴）発散、最初の 12 メッセージは x86 と同一、ペアから鍵と偽造が出る。危険はアーキ非依存である。

スイッチは参照実装自身が用意し、過小評価している。 AVX2 経路には FALCON_FMA という明示オプションがあり、真の _mm256_fmadd_pd を出す。config.h はその危険を「署名が変わるのは < 2⁻⁴⁰、safe and interoperable」と自己評価する。AVX2+FMA 機で有無 2 通りに建て同一鍵で 274,944 本署名すると 30 本＝ 2⁻¹³·² で食い違い、参照の見積りより約 2²⁷ 高く、発散ペアから鍵と偽造が出る。「safe and interoperable」は署名 1 本では真、両ビルドの 2 本を並べると偽 ― 差が鍵だから。本稿の主張が参照実装の設定ファイルに書かれ、握りつぶされている。

今、実際に危険なのか

いいえ ― だからこそ今動くべきである。出荷エコシステムを調べた限り、FMA 可能ターゲットで縮約する Falcon ビルドは存在しない: liboqs・PQClean は整数エミュか手書きの 2 回丸め AVX2 intrinsics、Bouncy Castle は Java、OpenSSL 3.5・AWS-LC・Botan・CIRCL・Go は Falcon 自体を出荷していない。脅威は潜在的で、参照の FPEMU 既定・intrinsics・fpr ラッパ・警告だけが防いでいる ― どれも仕様書にはない。FIPS 206 が native-FP・bit 一致へ動くことこそ潜在を顕在に変える圧力なので、その前に規範で禁じるべきである。

陰性対照が価値の半分である

「参照実装のビルドどうしが食い違う」という結果は、普通のビルドの選択でも食い違うのなら、警告としては強くても使えない ― どの差が効いたか言えないからだ。食い違わない。各 3 万署名で:

さらに 2 点。GCC は AVX2 の intrinsics も縮約しない ― -ffp-contract=fast を明示しても fma 命令は 0 ― ので、ベクトル経路の既定ビルドと縮約ビルドは同じプログラムである。clang は縮約し、結果は第 3 の列になる。既定とも、clang のスカラー縮約ビルドとも違う: 3 万署名で、2 つの縮約ビルドはそれぞれ既定と 5 本ずつ食い違い、4 本は共通、1 本ずつが固有である。これは「参照実装と壊れたビルド」ではない。互いに矛盾する適合ビルドが 3 つあり、どのメッセージが漏れるかは、コンパイラがたまたまどの経路を縮約したかで決まる。

いま FN-DSA とこれの間に立っているもの

偶然である。native ビルドは double を typedef struct { double v; } fpr; で包み、fpr.h はその理由を書いている ― 生の演算子を使ったらコンパイラに叱ってほしいから。誰も書き残していない第二の効果がある。GCC は我々が試したどの設定でもこのラッパ越しに縮約せず、clang も -ffp-contract=fast のときだけ縮約する。型安全のためのイディオムが、ヘッダの中で、別のことを書いた注釈の下で、暗号的な仕事をしている。我々は一つ前の版で「GCC と clang の既定が食い違う」と書いた。建てて測ったらそれは誤りで、訂正後の主張 ― 2 つのコンパイラではなく旗ひとつ ― は、より狭く、より鋭い。

07 — 破って、直す

対策の半分では何も守れない ― そして、より簡単な代替

ePrint 2024/1709 §7.1 の対策は2部構成：(1) SamplerZ を四捨五入版（Algorithm 4）に置換し、不安定点を整数から半整数へ移す。(2) ‖(g,−f)‖² を奇数に制限し、半整数中心を不可能にする。実装した。5 つの (μ,σ) で各 20 万標本の χ² は χ²/df = 0.72〜1.02 ― Algorithm 4 は分布的に健全（独立確認）。

09 — 範囲と限界

定数時間性、そしてまだ言えないこと

この実装は定数時間ではなく、目指してもいない。定数時間実装ならできない事をする箇所には CONSTANT TIME: コメントを残した。Julia 実装は実装由来のチャネル（GC・JIT・境界検査・ディスパッチ）を一切閉じられない ― だからこそここでの仕様レベルの問いにはきれいな計測器で、配備用の署名器としては不向きなのだ。していない側面攻撃の貢献を主張するのでなく、そう明記する。

未解決として明示するもの：

  • A2a / A2b は分離できていない ― 複素除算単独と D11 単独はどちらも 0/10万。単独率 ≈3.75×10⁻⁶ をゼロから分けるには数百万署名が要り、そこまで到達していない。二つ合わせれば署名に届く、とは言えるが、どちらが効くかは言えない。
  • A2 と A1 の率は区別できない ― 点推定で 2.5 倍だが、92.5 万本のプールで p ≈ 0.23。順序ではなく「同程度」と報告する。
  • 非対称性には機構を与えたが、較正済みの法則は与えていない ― 比の推定 3 通りが一桁にまたがり、突き合わせられていない。
  • 事象チャネルは実ハッシュで通したが、盲目オラクルに残余がある。event_attack.jl が一様近似を外し、実 hash_to_point 事象 511 本で復元・偽造まで届く。§05 の係数数分類も実 12 発散を 12/12 正しく分類する。閉じていないのは完全盲目の攻撃 ― first-two 発散が call-1 か call-2 か区別できず（one-of-two）、素朴な反復解法は収束しない（合成 n=64,128 で 0/5）。ラベル既知での解法は示したが、盲目のラベル復元は open。
  • 縮約の結果は 2 アーキだが全組合せではない。x86-64（gcc 13.3 / clang 18.1）と aarch64（gcc 13.2 / clang 18.1、qemu-user）で同一結果 ― gcc は縮約せず、clang は -ffp-contract=fast 系のみ、率も鍵復元も一致。FMA が基本 ISA の aarch64 でも既定は縮約しない（fpr ラッパが効く）。未検証: MSVC、他バージョン、実機 aarch64、AVX2/NEON ベクトル経路の動的比較。
  • 検証の速さは最速の C ビルドを約 10% 上回るが、これはビルドオプションだけで生じるばらつきの内側である。擁護できる主張は「C と同等」であって順位ではない。
  • FALCON-1024 は書き方の差については低volume（35万本、1 件）だが、縮約の結果はここでも再現する（6万本中 6 本）。
10 — 提言

FIPS 206 がすべきこと

FIPS 206 がビット一致 KAT を求めるなら：

  1. FP_CONTRACT を規範として off と書く。これを最初に置く。§05 がその代価である ― 旗ひとつで 10 万本中 12 本の食い違いと 8 本の秘密鍵。-Ofast と -ffast-math はどちらもその旗を含む。いま参照実装を守っているのは型安全イディオムの文書化されていない副作用であり、偶然は仕様ではない。
  2. 最後の 2 回だけの修正は修正でない、と書く。§04 は最初の 2 回の事象から鍵を復元する。2024/1709 §5 があの位置を無害とみなす理由は成り立たないので、その理由に依拠した対策には別の根拠が要る。
  3. 浮動小数点環境が対象かを書く。周囲の IEEE-754 丸め方向以外はすべて適合している署名器は、ノルム条件を満たしたまま検証に落ちる署名を出す ― FE_UPWARD / FE_DOWNWARD で 200 本中 0 本が有効。これは決定性ではなく正当性の要件で、現行のどの本文にも書かれていない。
  4. 書き方を固定する ― 複素除算・D11・最下段 ffSampling を明示するか、より良くは ePrint 2024/1709 §7.1 の構造的修正（中心を floor でなく round でサンプルし、‖(g,−f)‖² を奇数に制限）を採る。後者は感受性そのものを除く。ただし両方の part を同じ条項で義務づけること ― round にすると q が奇数なので最初の 2 回は無条件に閉じるが、最後の 2 回（最も安い鍵復元位置）は以前とまったく同じだけ露出したままになる。また現状の C 鍵生成が ‖(g,−f)‖² を偶数に強制しているので、そのパリティ条件の緩和も要る。
  5. fpr_inv_sigma を全精度で公表する ― 丸めた σ から導かせず、中間値が KAT の対象かを述べる。
  6. σ_min の ε を明記する、あるいは導出を。
  7. SamplerZ のバイト組み立て規約をベクタと並べて記す。
