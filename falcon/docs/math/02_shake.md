# モジュール 2: 乱数 ― ハッシュと PRNG が別物である理由

## 2.1 この章で答える問い

FALCON は擬似乱数を 2 種類の経路で作る。

1. **SHAKE256**: メッセージと salt から「ハッシュ点 c」を作る（公開・決定的）
2. **ChaCha20 ベースの PRNG**: 56 バイトのシードから、
   `samplerz` が食う長い乱数列を作る（秘密・大量消費）

Dilithium は SHAKE128/256 だけで済ませていた。なぜ FALCON は 2 本立てなのか。

答えは**消費量**である。Dilithium の乱数消費は署名 1 回あたり数 KB だが、
FALCON の `ffSampling` は再帰の各ノードで棄却サンプリングを回すので、
乱数を桁違いに食う。Keccak の置換は 1 ブロック 136 バイトあたり 24 ラウンドで、
ChaCha20 の 512 バイトあたり 8×20 ラウンドに比べて割高だ。
だから**「暗号学的に固い入口」と「速い蛇口」を分けた**。
シードは SHAKE256 で作り、そこから先は ChaCha20 で伸ばす。

これは珍しい設計ではなく、「XOF は KDF に、ストリーム暗号は本流に」という
定石そのものだが、**KAT を通す側から見ると罠**になる。
乱数の消費順序・消費量が 1 バイトでもずれると署名が変わるからだ。

## 2.2 XOF としての SHAKE256

SHAKE256 は「任意長出力ハッシュ (XOF)」である。Keccak のスポンジ構造では、

- **吸収 (absorb)**: メッセージを 136 バイトずつ状態に XOR し、置換 f を適用
- **絞り出し (squeeze)**: 状態の先頭 136 バイトを出力し、置換 f を適用、を繰り返す

この構造から、決定的に重要な性質が出る:

> `d1 < d2` のとき、`SHAKE256(m, d1)` は `SHAKE256(m, d2)` の**接頭辞**である。

出力は 1 本のストリームで、`d` は「どこで止めるか」でしかないからだ。
FALCON の `hash_to_point` は「2 バイトずつ読んで、`q` 以上なら棄却して次を読む」
という可変長消費をするので、この性質が無いと実装できない。

### 実装上の落とし穴

`SHA.jl` は `shake256(data, d)` という一発形しか公開しておらず、
同じ context を 2 回 squeeze することができない（`digest!` が
呼ぶたびに padding を再適用する）。そこで本実装は
「メッセージを保持し、足りなくなったら長さを倍にして取り直す」
という**接頭辞性質に全面的に依存した**回避策を採っている。

ここで重要なのは、**接頭辞性質は FIPS 202 の性質であって
`SHA.jl` の実装が正しいことの保証ではない**という点だ。
だから `test/test_shake.jl` は CPython の `hashlib`（独立実装）由来のベクタで
接頭辞性質そのものを検証している。ここが落ちたら回避策を細工するのではなく、
Keccak-f[1600] を自前で書くのが正しい対処になる。

## 2.3 参照実装の ChaCha20 は RFC 7539 ではない

これは移植で最も時間を溶かしうる箇所なので、差分を明示しておく。

ChaCha20 の**ブロック関数**（16 ワードの状態、10 回の double round、
最後に初期状態を加算）は RFC 7539 と同一である。違うのは**周辺**の 3 点。

### (a) 鍵とカウンタの詰め方

56 バイトのシードを little-endian の 32bit ワード `s[0..13]` に切る。

```
状態:  CW[0] CW[1] CW[2] CW[3]
       s[0]  s[1]  s[2]  s[3]
       s[4]  s[5]  s[6]  s[7]
       s[8]  s[9]  s[10]^lo(ctr)  s[11]^hi(ctr)

初期カウンタ:  ctr = s[12] + (s[13] << 32)
```

RFC 7539 なら「鍵 8 ワード + カウンタ 1 ワード + nonce 3 ワード」だが、
ここでは `s[10]`, `s[11]` が**カウンタと XOR される**し、
`s[12]`, `s[13]` はカウンタの**初期値**になる。
つまりシードが鍵とカウンタを兼ねている。

### (b) 8 ブロック分をワード単位でインターリーブする

参照実装は 8 ブロックを一度に生成し、128 ワードのバッファに

```
buffer[8*j + i] = (ブロック i のワード j)
```

と**格子状に**並べる。これは C 実装が SIMD レジスタで 8 ブロックを
並列生成するときのレジスタ配置がそのまま出力仕様になったもので、
数学的な意味は無い。しかし**再現しないと KAT が通らない**。

「速いから」という理由でできた構造が、標準化によって
「そう並べなければならない」という規範に変わっている。
この本の主題（実装都合が仕様に昇格する現象）の、小さいが分かりやすい実例。

### (c) `randombytes(k)` は端数を捨てる

512 バイトのバッファに `k` バイト分の残りが無いとき、
参照実装は**残りを使わずに捨てて**新しい 512 バイトを生成する。

```python
if 2 * k > len(self.hexbytes):      # 残量不足
    self.hexbytes = self.block_update()   # 残りは捨てられる
```

だから 511 バイト消費した直後に 8 バイト要求すると、
返ってくるのは「ストリームの 512〜519 バイト目」ではなく
**新しいバッファの先頭 8 バイト**である。

このバグは**要求サイズが境界をまたぐときだけ**顕在化するので、
小さいテストでは絶対に見つからない。
`test/vectors/chacha20_kat.jl` に `[511, 8]` と `[255,255,255]` という
境界をまたぐ要求列を意図的に入れてあるのはこのためだ。

### おまけ: 意味の無いコード

Python 参照実装の `randombytes` には 2 回のバイト反転が入っているが、
`bytes.fromhex(reversed_hex)[::-1]` は選択したスライスに対して**恒等写像**である。
C 実装のワード単位消費に合わせた名残で、バイト列としては何もしていない。
（この判断で 15 分溶かした記録が debug_log #005 にある。
「変な処理を見たら、まず恒等でないか確かめる」。）

## 2.4 定数時間性について

このモジュールは、FALCON の中では珍しく**副作用のない場所**である。

- SHAKE256 は公開データ（salt とメッセージ）にしか適用されない。
- ChaCha20 は加算・XOR・回転だけで、分岐もテーブル引きも無い。
  つまり**努力しなくても定数時間**。

対比が効いてくるのは次からだ。この章で作った乱数を**消費する側**、
つまり `samplerz`（モジュール 7）が、まさに
「消費した乱数の量が秘密に依存する」という形で漏らす。
**乱数の生産は安全で、消費が危ない。** FN-DSA の標準化を遅らせたのは
後者であって、前者ではない。

## 2.5 Dilithium との対比

| | Dilithium | FALCON |
|:---|:---|:---|
| ハッシュ | SHAKE128 (行列展開) / SHAKE256 (challenge, 鍵) | SHAKE256 のみ |
| 乱数の伸長 | SHAKE128 をそのまま XOF として使う | **ChaCha20 に切り替える** |
| 可変長消費 | あり（棄却サンプリングで係数を作る） | あり（hash_to_point、samplerz） |
| 消費量 | 数 KB / 署名 | ffSampling が桁違いに食う |
| 定数時間性 | SHAKE の消費量が秘密依存しない設計 | **samplerz が秘密依存する** |

Dilithium 移植で「SHAKE を XOF として使い、必要なだけ絞る」パターンを
書いたことがあるなら、モジュール 2 の SHAKE 部分は素直に再利用できる。
新しいのは ChaCha20 の側で、しかも新しさの中身は暗号ではなく
**バッファリングの癖**である。
