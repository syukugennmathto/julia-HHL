# 第0部　前提と方法論 ― なぜこの検証が可能だったか

FALCON（NIST 標準化名 **FN-DSA**）は、格子暗号にもとづくデジタル署名方式である。「格子」とは、ベクトルを整数係数で足し合わせて得られる点の集まりで、その中から短いベクトルを見つける問題が計算的に難しいことが安全性の根拠になる。FALCON は他の標準化方式（ML-DSA, SLH-DSA, HQC）と違い、署名生成の途中で**浮動小数点演算（実数の近似計算）を使う**。この一点が本研究全体の主題につながる。

本研究は、**仕様書だけを読んで FALCON を Julia で独立に実装し**、既存の C 参照実装・Python 参照実装の両方と、最終出力だけでなく**内部の中間値レベル**で突き合わせて検証する、という方針で始まった。

## 0.1 参照実装が2つあることを設計に組み込む `[#007,#010]`

FALCON は珍しく、**速いが読みにくい C 実装**（`algorand/falcon`, Python の `tprest/falcon.py`）と**遅いが読みやすい Python 実装**の両方が公開されている。両者は同じアルゴリズムの別表現である。

- **どちらと突き合わせるかを毎回決める**必要があった `[#007]`。C は NTT（数論変換）の係数をビット反転順かつ Montgomery 形式で持ち、Python は自然順・素直な剰余で持つ。表現が違うものを無理に合わせると、不一致が出たときに「移植のバグ」か「変換のバグ」か切り分けられなくなる。そこでモジュール4（NTT）の一次照合相手は Python にした。
- 参照実装は**精度も同じではない** `[#010]`。Python 参照実装の FFT 根テーブルは有効数字15桁しかなく、C は27桁。我々が `cispi`（π 倍角の複素指数）で計算した根のほうが Python より正確で、C とは一致した。「参照実装と突き合わせる」と言うとき、どちらを正典にするかで許容誤差が桁で変わる。

**この「参照実装2つ」という構図が、後に何度も効く**。カウンタ溢れで Python 側が間違っていることを C が教え（#017）、Babai 縮約で C と Python が別アルゴリズムだと判明し（#041）、最終的に「同じ C 参照実装を2通りにビルドすると署名が違う」（#071）へつながる。

## 0.2 実行環境の制約と、その回避の履歴 `[#001,#008,#013]`

- **#001**: リモート実行環境に Julia が無い。`julialang.org` 系ドメインは egress プロキシが 403、apt にもパッケージが無い、GitHub Releases に Linux バイナリが無い。到達できるのは `raw.githubusercontent.com`, `github.com`, PyPI などのみ。→ 当面、検証責任を分割した：数学の正しさは Python 参照実装から golden vector（期待値を記録したテストデータ）を生成してコミット、Julia コードの正しさは別環境に委ねる。
- **#008**: Julia が動かせないので、書いた Julia コードを Python に**逐語移植**（1:1 で行対応）して参照実装と比較し、アルゴリズムだけは検証した。ただしこれは「アルゴリズムの検証」であって「Julia コードの検証」ではない（構文・型・Julia 固有の意味論は未検証のまま）。
- **#013**: Docker デーモンは無いが、**Docker レジストリは単なる HTTP API** だと気づき、匿名トークン→ manifest → レイヤ blob の順に叩いて `mirror.gcr.io` 経由で Julia 1.11.9 を入手。**これ以降、全モジュールが実際に実行されている**。→ #001 の「境界に置けるのはコミットされたベクタだけ」という結論は早すぎた。「入手経路が全部塞がっている」と結論する前に、同じものを配る別プロトコルを探せ、という教訓。

## 0.3 「記憶から書かない」という一貫方針 `[#002,#014]`

- **#002**: 仕様書 PDF に到達できず、パラメータの「表番号」を引けなかった。→ 値そのものは相互に独立な2つの参照実装から引き（C と Python で `sig_bound`/`sig_bytelen` が完全一致するのを確認）、各定数に実際に読んだ `file:line` を付け、`spec_ref` フィールドは `"TODO"` のまま残してテストで監視した。**指示の本質は「表番号」ではなく「記憶から書くな」**だと解釈した。
- **#014**: その舌の根も乾かぬうちに、`Project.toml` の SHA パッケージの UUID を記憶で書いて間違えた。→ **記憶で書いていい定数は無い**（暗号定数だけの話ではない）ことの実演。
- のちに #046 で仕様書が届き、全定数が一致し、`spec_ref` の `"TODO"` は正しく閉じた。**保留は誤った断定より強い**、という方針がここで回収される。

## 0.4 このプロジェクトで最も再発した失敗＝計測器自身の欠陥 `[#035,#042,#050,#051]`

後続の伏線として先に述べておく。性能や漏洩を測るたびに、**測定器のほうが嘘をついていた**ことが繰り返し起きた。

- #035: プロファイラが計測区間の外で GC を走らせ、割り当てコストを消していた。
- #042: A/B 測定のループ内で `git stash` してしまい、自分の変更を捨てたまま「main と main」を比べていた。
- #050: 「3箇所の修正が署名再現の鍵だ」と書きかけたが、修正を全部戻しても基準線が既に一致していた（修正は効いていなかった）。
- #051: 定数時間性の計測器を5回直し、5回とも直す前は嘘の数字を出していた。

**教訓**: 独立した計測器を2つ持て、対照（コントロール）を必ず置け、「その日に書いたコード」を最初に疑え。この規律が、後半の脆弱性実証（陽性対照・陰性対照つきの主張）の質を支えている。

# 第1部　独立実装と中間値検証（モジュール1〜10）

FALCON をモジュール1〜10（パラメータ、SHAKE/PRNG、多項式、NTT、FFT、NTRU 鍵生成、離散ガウスサンプラ、ffSampling、符号化、署名本体）に分けて実装し、各段で参照実装と突き合わせた。本部では「実装の正しさ」と、その過程で拾った失敗のうち代表的なものを述べる。個々の「外した仮説」は第9部の一覧に集約する。

## 1.1 パラメータと4つのσ `[#003,#019,#046]`

FALCON には σ（標準偏差）が4種類ある。**どのガウス分布の話かを毎回言え**、が方針になった `[#003]`。

- `sigma` … 格子上のガウス分布の幅（署名の幅）。n=512 で 165.7366171829776。
- `sigma_min`, `sigma_max` … 整数格子 Z 上の各座標のガウスの幅。`sigma_min` は平滑化パラメータ（分布が十分「なめらか」になる下限）で、`falcon_eps(n)=1/√(2⁶⁴·n³)` から `sigma_min=1.2778336969128337`（n=512）が逆算できる。
- `sigma_fg` … 鍵生成で秘密多項式 f, g をサンプルする幅。実装都合の基底幅 `SIGMA_FG_BASE=1.43300980528773` を持つ。

`1.17`（Gram–Schmidt ノルムの上限に由来する定数）が複数のσにまたがって現れるので、この定数を見たら「どのσの話か」を確認する合図にした。

- **#019**: テスト側が「σ/σ_max ≈ 100 倍」と根拠なく書いていて落ちた。実測は約 91 倍。**性質テストの閾値も定数**であり、記憶で書けばパラメータを記憶で書くのと同じ誤りになる。
- **#046（仕様書到達後）**: 仕様書 v1.2 Table 3.3 と全定数が一致（σ, σmin, σmax, ⌊β²⌋, 鍵・署名バイト長すべて）。さらに、**σ と σ_min は別の ε（誤差許容パラメータ）から出ている**ことが分かった：σ は `Z^{2n}` の平滑化 `log(4n(1+1/ε))` 由来、σ_min は `Z` の平滑化 `η_ε(Z)` 由来。片方の ε をもう片方に流用すると 10% 違う値が静かに出る（落ちないので危険）。テストで両方向（「正しい ε で一致」かつ「もう片方の ε では一致しない」）を主張した。

## 1.2 SHAKE256 / Keccak / ChaCha20 `[#004,#005,#015,#016,#017]`

ハッシュと擬似乱数生成器（PRNG）の層。**壊れてもランダムに見える**種類のバグが多く、KAT（Known Answer Test＝既知の入出力対）でしか守れない。

- **#015→#016**: Julia 同梱の `SHA` には SHAKE256 が無かったので、Keccak-f[1600] を自前実装（約90行）。すると `shake256("abc")` が全く違う値に。原因は、ラウンド定数を生成する LFSR（線形帰還シフトレジスタ）を `lfsr = 0x01`（Julia では **UInt8**）で回していたこと。`lfsr <<= 1` が8ビットで桁あふれを捨て、帰還多項式が一度も適用されなかった。C なら `int` に昇格するので同じコードが動いてしまう。→ `lfsr = 1`（Int）で1文字修正。**Julia の16進リテラルは型が幅で決まる**という、C からの移植で必ず踏む罠。
- **#017**: ChaCha20 の KAT が、シードが全 0xff のときだけ12件失敗。カウンタが 2⁶⁴−1 で、次ブロックで溢れる。**Python 参照実装は多倍長整数なので巻き戻らず 33 ビット値を作る**が、C 参照実装 `rng.c` は `uint64_t` で巻き戻る。第3の独立実装（C）に聞いて、**Julia が正しく Python 参照実装が間違い**と判明。golden vector 側（Python 生成）を直した。→ **参照実装が間違っていることがある**。多倍長言語で書かれた参照実装は固定幅の挙動を隠す。

## 1.3 NTT と FFT の根テーブル `[#006,#007,#009,#010,#011]`

NTT（数論変換）と FFT（高速フーリエ変換）は、多項式の積を高速に計算する道具。両者は「同じ木の形」を持つが、根（回転因子）の並べ方が違う。

- **#006**: NTT の根テーブルの生成則（ζ=7 からの指数再帰＋「小さい剰余が先」）を逆算し、2046個のハードコード定数を20行の再帰に置き換えた。**往復テスト `intt(ntt(f))==f` は NTT の正しさをほとんど保証しない**（評価点が全部間違っていても通る）ので、定義そのものとの一致・独立実装との積の一致で固定した。
- **#009**: 「NTT と FFT は同じ表を2つの環で読んだだけ」だと期待したが、**集合としては同じ、列としては違う**。NTT は ± ペアを剰余の小さい順に、FFT は主平方根が先に並べる。木の形は同じでも、ノードに付けるラベルの選び方に自由度が残る。
- **#011**: 「C との突き合わせは FFT から効く（順序問題が無い）」と前セッションで書いたが**誤り**だった。C の FFT は共役対称性を使って半分（N/2個）しか持たず、グレイコード置換 `k↦k XOR (k>>1)` でずれている。→ 推測をやめて実際に C をビルドして測り、`from_c_fft`/`to_c_fft` を実装した。

## 1.4 参照実装は既定で浮動小数点をエミュレートする ― 本研究の主題の初出 `[#012]`

C 参照実装（Algorand フォーク）をビルドすると、`fpr`（浮動小数点数の型）が `double` ではなく `uint64_t` になっていた。`config.h` が `FALCON_FPEMU`（整数によるソフトウェア浮動小数点エミュレーション）を無条件で有効にしていたためである。その理由が `config.h` に明記されている（要約）：

> ネイティブ FPU やコード最適化はわずかな差異を生み、**決定的署名**を壊しうる。署名の非決定性は**壊滅的なセキュリティ障害**につながる ― 同一メッセージに対する2つの異なる署名から、任意メッセージの偽造が可能になりうる。

**この一文が、本研究の後半すべての予告になっている**。「Float64 の結果がビット単位で再現すること」自体がセキュリティ性質であり、他の3方式（整数演算で閉じている）にはこの要求が存在しない。「なぜ FN-DSA だけ標準化が遅れたのか」の答えの半分がここにある（残り半分は定数時間な Gaussian サンプリング）。

> **注**: この「参照実装の既定は FPEMU」という記述は、後に #045 で**部分的に訂正される**。FPEMU を既定にしているのは Algorand フォークであって、Falcon 公式参照実装の既定は native FP だった。ただし「非決定性は壊滅的」という警告文自体は Algorand の `config.h` に実在する。

## 1.5 poly / ntrugen / samplerz / encoding の検証 `[#018,#020,#021,#022,#023,#024,#027,#028]`

- **#018**: 「わざと溢れさせた」テストベクタが実は溢れていなかった。最悪係数を `n·B²` で見積もったが、乱数の符号はそろわないので実際は `√n·B²` のオーダー。**見積もりに中心極限定理を入れ忘れた**。→「わざと壊すテストは、本当に壊れていることを確かめる」。
- **#022**: 公式 KAT（samplerz、3072本）はバイトを**チャンクごとに逆順**で食わせないと合わない。消費バイト数は一致していた（＝制御フローは正しい）ので、疑うべきは入力の解釈だった。この規約はハーネスのコードにしかない、と結論した（→ #046 で仕様書 Table 3.2 にもあると判明、半分訂正）。
- **#023**: 参照実装の docstring が「2⁶³」と書いていたが正しくは「2⁶⁴」で、それを写して性質テストがきっかり2倍ずれた。KAT は通っていたので実装は正しく、**間違っていたのは参照実装のコメントと自分の理解**。「コードは正典だがコメントは正典ではない」。
- **#027**: 参照実装(Python)のデコーダが全ゼロ入力でクラッシュする。攻撃者が与えるバイト列を食うデコーダがクラッシュするのは欠陥なので、ここは真似せず、Julia 側は `nothing` を返すようにした。

## 1.6 ffLDL / ffSampling と「理解のバグ」 `[#025,#026]`

- **#026**: 残差 `d0=t0−z0` が n=512 で「32.5 < 8」で落ちた。**GPV（署名の基礎になる格子サンプリング補題）が保証するのは「残差が座標ごとに小さい」ではなく「残差を基底で写した像が短い」**。`‖(t−z)·B‖²` を測ると理論値 `2n·σ²=2.81e7` とぴったり。実装ではなく理解の誤りで、これは原稿に直接効く。
- **#025** は第2部で詳述する（決定性問題の発芽）。

## 1.7 到達点 ― C参照実装との相互運用が成立 `[#029,#030]` 🟢

- **#029**: 「再試行のとき salt を引き直す」と自分で書いた説明が誤り。参照実装は salt をループ外で1回だけ引き、ループ内は同じ salt で解き方（サンプラ）を振り直す。**もっともらしい説明ほど出典を確認する**。
- **#030**: モジュール10（署名本体）は一発で通った。**C 参照実装が固定シードから生成した本物の FALCON-512 の署名を、我々の `falcon_verify` が受理**（`‖(s1,s2)‖²=26536387 ≤ β²=34034726`）。さらに **C の秘密鍵で我々が署名し、C の公開鍵で検証できる**ことも確認。バイトは C と違うが有効な署名である。🟢

この「バイトは違うが相互運用はできる」という切り分けが、次の主題（署名バイトはなぜ一致しないのか）への入口になる。

# 第2部　決定性問題の発芽と、性能改善

## 2.1 1 ulp が署名を変える ― 実測 `[#025]` 🟢

ffLDL 木も決定的版サンプラ `ffnp` も参照実装と一致するのに、`ffSampling`（乱数を使う本番のサンプラ）を同じバイト列で再生すると **6本中5本が違う答え**になった。追うと、離散ガウスサンプラに渡る中心 μ が1回目から `3.000000000000002`（Python）対 `3.0`（Julia）と 2e-15 だけ違い、以降ずれが増幅していた。

決定実験として、Julia の根テーブルに**参照実装の表を注入**して再実行すると **6/6 一致**した。原因は FFT の根テーブルの最下位ビット差（`ulp`＝浮動小数点で表せる隣り合う値の刻み幅、"unit in the last place"）である。

> **これがこの研究の主題の最初の実測**である。「浮動小数点の bit 再現性がセキュリティ性質」というのは抽象論ではなく、**定数表の最下位ビットを1つ変えると署名が変わる**という具体的事実だった。`floor`（切り捨て）で始まるサンプラが不連続なので、1 ulp の差が整数境界をまたいだ瞬間に出力整数が1違う。

## 2.2 【訂正ボックス #025 → #031】犯人は「浮動小数点演算」ではなく「自分の定数表」だった

| 段 | 内容 |
|:--|:--|
| **初期の見立て（#025）** | 「浮動小数点だから署名が再現できない」。原因を漠然と演算に帰した。1 ulp の差が**どちら側の誤差か**は特定できていなかった。 |
| **測定（#031）** | (1) FPEMU 版と native FP 版の C 出力を全比較 → **バイト完全一致**。x86-64/SSE2 では、ソフトウェア浮動小数点とハードウェア浮動小数点は1ビットも違わない（`-Ofast` でも同じ）。(2) 我々の `cispi(k/n)` と C の根テーブル `fpr_gm_tab` を同じ角度どうしで比較 → **1023 中 50 個がちょうど 1 ulp 違う**。最小例は `cispi(1/4)` の虚部。Julia の `sinpi`/`cospi` は *faithful*（1 ulp 以内）であって *correctly rounded*（最近接）ではない。 |
| **修正後の主張** | **犯人は演算ではなく我々の定数表**だった。256 ビットの `BigFloat` で cos/sin を計算して一度だけ丸める `unit_root(k,n)` に置き換え、C の `fpr_gm_tab` と**ビット完全一致**させた（π/2 の倍数だけは厳密な 0・±1 として特別扱い）。「#025 の結論（1 ulp が署名を変える）は変わらないが、理由が変わった」。 |

教訓が二つ。**「1 ulp 以内」は保証ではなく上界**であり、決定的出力を要求する場面では「およそ正しい定数」は間違った定数と同じ意味を持つ。そして**予想が外れたときのほうが情報が多い**（「emu と native は違うはず」が外れたおかげで、容疑者が演算から定数表に絞られた）。

## 2.3 性能 ― 738倍から互角へ `[#032,#033,#034,#036,#040,#041,#043,#044,#047]`

C 参照実装（デフォルトビルド）と性能を突き合わせ、原因を測定で分解していった。数値はすべて中央値（ms）、`docs/benchmarks.md` に記録。

- **#032（初回対決, n=512）**: keygen C(FPEMU) 13.0 / C(native) 6.35 / **Julia 9610**（**738倍遅い**）。sign は C(FPEMU) と互角（2.05 対 2.04）。verify は15倍遅い。「署名が互角」なのは Julia が速いのではなく FPEMU が高いから。ここで NTT 経由の多項式積が学校算法より 7.4 倍**遅い**ことも判明（固定次数では漸近計算量が勝つ次数に届かない）。
- **#033**: 鍵生成の 99.98% が `ntru_solve`、その 96% が **n=128 の Babai 縮約 1 回**。`BigInt`（多倍長整数）は `Int64` に収まる値でも 315 倍遅い。**C が速いのは最適化ではなく、多倍長演算を一度もしていないから**（31ビット素数を並べた RNS＝剰余系表現で全部機械語に載せる）。計算モデルが違う。
- **#034**: `sqnorm`（二乗和）に `Int128` checked 演算を入れたら期待の3.4倍しか出ず。**`Int128` にはハードウェアのオーバーフローフラグが無く**、検査がソフトウェアで走っていた。オーバーフロー議論を「演算ごと」から「入力の範囲」へ移して 227 倍高速化。
- **#036, #040**: `karamul`/`bitsize` の機械語化と、Babai 更新の in-place GMP 化で、鍵生成 9610 → 186 ms（通算 **52倍**）。in-place 化は所有権の問題（浅いコピー）を持ち込み、速度のための変更が正しさの前提を変えることを実演。
- **#041**: 「残りは RNS でしか埋まらない」を三度書いて三度とも測っていなかった。分解すると、我々の Babai 縮約が深い段で「降参」して縮約を n=128 に押し込む機構（`max(53,…)` のクランプ）が主因。**参照実装2つが、この一点で違うアルゴリズムを実装している**（Python 準拠の我々は仕様書寄り、C は明示的な bit 予算方式）。
- **#043, #044, #047（分岐版）**: `Core.Box`（クロージャの変数再代入で発生する型消去）を外して 34 倍、降下の 55% が BigInt 確保だったのを `mpz_addmul_ui` で潰し、Karatsuba が全次数で学校算法に負けることを測って閾値を捨てた。**#047 で鍵生成が C の FPEMU ビルドを抜いた**（10.99 ms、公式既定 native FP の 1.85倍まで）。

## 2.4 分岐版(cschedule)という判断 `[#042]`

# 第5部　先行研究との遭遇と、決定性の署名伝播

## 5.1 【訂正ボックス #048/#050/#053 → #054】「伝播しない」を反証 ― 10万本で5本 🟢

| 段 | 内容 |
|:--|:--|

## 5.3 A2腕は §7.2 の対策で塞がらない位置で発火 `[#056]` 🟢

未検証だった (a)+(b)＝**A2腕**（木だけを変える）を測ると、**立った**：40万本で3本（率 7.5e-6）。機構は3/3一致で、**全て呼び出し 2n−1 か 2n、全て `floor` が整数をまたぎ、該当節点の幅はビット一致**（Lemma 1 であって Lemma 2 ではない）。ここは §5 が「1ペアから秘密鍵を全復元」とする位置である。

## 5.6 精度→漏洩率の法則 ― 6桁差が「構造」を裏づける `[#059]`

# 第6部　対策の検証（撤回を含む）

2024/1709 §7.1 の対策（`floor`→`round` ＋ ‖(g,−f)‖² を奇数に）を独立実装し、敵対的に検証した。この部は本研究で最も紆余曲折が大きく、**一度「対策を破った」と主張し、自分自身への敵対的査読で過大な主張だったと気づいて撤回**している。

## 6.1 §7.1 対策の実装と、part 1 単独の非対称性 `[#061]` 🟢

- 対策の base sampler（Algorithm 4）を実装し、χ² 検定（各20万標本、5つの (μ,σ)）で**分布を壊さない**ことを独立確認（論文の Alg 4 の正しさの独立確認は誰もやっていない）。
- 中心の有理構造（Theorem 1）を実装で直接確認：呼び出し1,2 は分母 g=q=12289、呼び出し 2n−1,2n は g=‖(g,−f)‖²、いずれも `g·c` が浮動小数点誤差の範囲で厳密に整数。
- **★ 発見：対策は非対称に効く**。中心 n/g が半整数になるのは g が偶数のときだけ。呼び出し1,2 は **g=q=12289＝奇数** → 半整数中心は原理的に存在しない。呼び出し 2n−1,2n は **g=‖(g,−f)‖²＝参照実装では常に偶数** → 半整数中心が整数と同じ密度で残る。
- 帰結：`floor`（現行）では危険端の露出が「整数中心7件」、`round`（対策 part 1 単独）では「半整数中心11件すべて」が危険端。**part 1 単独は無害な側（最初の2回）だけを消し、危険な側（最後の2回＝1ペアで全復元）を丸ごと残す**。実測でも発散率は下がらない（NewSamplerZ 1.33e-5 対 floor 1.9e-5、統計的に区別できない）。
- part 2（‖(g,−f)‖² を奇数に）は参照実装の鍵生成では作れない（0/3000）。→ この「作れない」の解釈は #067 で訂正される。

「対策があると対策が配備できるは別」。「算術で決まることは統計を待たなくてよい」（q が奇数という一事実から最初の2回は半整数中心を持てないと確定する）。

## 6.2 最初の2回はなぜ跨がないか `[#062]`

最初の2回の中心は n/q なので、メッセージを選べば 1/12289 で整数中心に当たる（攻撃者が狙える）。48000 対を走査すると整数中心10件だが**発散は0件**。理由：計算された中心は厳密な整数ではなく**両実行に共通して 1〜3 ulp ずれて**おり、A1 の摂動 |dμ|≈2.7e-15 はその共通ずれより小さいので、2つの値は必ず整数の同じ側に落ちる。「必要条件（整数中心）と十分条件（跨ぎ）を分けて測る」。この「共通の丸めずれ」が #070 でオラクルの窓の下端として定量化される。

## 6.3 対策を配備した状態で鍵を復元 ― 3/3 `[#063]` 🟢

NewSamplerZ（part 1）を配備し、参照実装の鍵（t 偶数、part 2 使用不可）で16万署名を走査 → **3件発散、3件すべて鍵復元**。復元鍵は格子の対称（回転 x^i と符号）を除いて格納鍵と厳密一致。率 1.9e-5 は floor 版と同一。

**この時点の主張**：「ePrint 2024/1709 §7.1 の対策のうち、実装者が今日配備できる半分は、秘密鍵の全復元を防がない」。**この主張は #067 で「言い過ぎ」として訂正される。**（対策の数学に穴があるのではなく配備可能性の問題であること、そして実験が §7.2 で消える A1 腕を使っていたこと。）

## 6.4 鍵生成を触らない厳密な対策 ― rational snapping `[#064]`

破りっぱなしにせず直した。敏感位置では厳密な中心が有理数 n/g で、**分母 g は署名者が既に知っている**。浮動小数点の中心 μ̂ は n/g を ~1e-13 で近似するので、`n = round(g·μ̂)` が n を厳密に復元し、`s = fld(n,g)` は純粋な整数演算になる。余裕は実測で7桁（1.4e-9 対 0.5）。

- 既知の発散ペアを snapping off/on で再生 → **4/4 解消**、通常署名は 0/1200 しか変わらない（分割を動かさず厳密にするだけなので分布不変、Lemma 2 が保証）。
- §7.1 と違い**鍵生成変更が不要**。
- ⚪ **正直な限界**：1e-9 の余裕は**実測であって証明ではない**（標準が依拠するには中心計算の前進誤差の厳密な上界が要る）。使えるのは g が既知かつ FP 精度内の位置（最初/最後の6回）のみ。
- 副次（負の結果）：`div_fft` は鍵生成の Babai 縮約でも使うが、同一シードから両綴りで生成した鍵は 0/400 完全一致（**鍵生成の相互運用性は安全**）。

## 6.5 最初の2回の中心は「f の公開線形形式」 ― Heuristic 1 が定理になる `[#065]`

`sample_preimage` の代数から、最初の2回の中心は環の元として **(c·f)/q** の係数（c は公開のハッシュ点、f は秘密）と厳密に一致する（Int128 の厳密積で照合、|diff|=0 と 2.5e-14）。

# 第7部　鍵復元・偽造の実証（脅威モデルを明記）

第6部までで「事象そのものが f の線形方程式」（#065）と分かった。第7部はそれを**実際に解いて鍵を出し、偽造まで届く**ところまで進める。各節で攻撃者の前提を明記する。

## 7.1 事象だけで鍵を復元 ― 差ベクトルなし、格子簡約なし `[#069]` 🟢

**脅威モデル**：攻撃者は、呼び出し1（または2）で整数中心事象が起きたことを教えるオラクルを持つと**仮定**する（オラクル自体はこの節では作らない）。シンドローム（ハッシュ点）c は公開。

公開 c に対し call 1 の整数中心は厳密に `(c·f)[n/2−1] ≡ 0 (mod q)`。negacyclic（負巡回）な巻き戻しを展開すると、これは c から攻撃者が計算できる行ベクトル（事象1件で1行）。**511行集めて F_q 上でガウス消去**すると：

```
collected 511 events from 5823368 syndromes (rate 8.77e-5, predicted 1/q = 8.14e-5)
system rank 511 of 512 unknowns
recovered vector: max|.| = 16   (true f has max|.| = 16)
matches the secret f: true  (up to sign)
```

核は1次元。核ベクトルを F_q のスカラー倍で走査して最短を取ると、それが f そのもの（符号を除く）。**512×512 のガウス消去だけ**で終わる（格子簡約も差ベクトルも不要）。約49秒。🟢

- 「最初の2回は短いベクトルしか出ないので使えない」（2024/1709 §5 の想定）は、**この経路には無関係**だった（§5 の反論は「差ベクトルから読む攻撃」にしか当たらない）。
- ⚪ **限界**：(1) オラクルはまだ作っていない（解く側だけ確立）。(2) シンドローム c を**ハッシュではなく一様乱数で引いている**（理想化。→ #073 で実ハッシュに置換）。

## 7.2 オラクルの窓を測る `[#070]`

#069 のオラクルが「なぜ綴り差では作れないか」を量で言えるようにした。整数中心では真値は整数 m だが、両実装とも m+η を計算する（η は FFT・木・降下という**共通部分**の累積誤差なので両者で同じ）。floor が食い違うのは m+η+Δμ が m の反対側に落ちたときだけ。

- **下端**：|η| median 2.84e-14。P(跨ぐ|整数中心) の曲線はちょうど |η| で曲がる。**|Δμ| ≪ |η| なら整数中心が何件あっても跨がない**（#062 の「10件作って0跨ぎ」に名前がついた）。
- **上端**：内部 call の偽陽性率 κδ（κ=1.62e3）が事象率を汚さない条件から 4.89e-11。**窓の幅 3.24 桁**。
- **窓の中に「誰も選んでいない差」がある**：C99 は `a*b+c` の1回丸めへの縮約（FMA/FP contraction）を許し、**GCC の既定は `-ffp-contract=fast`、clang/MSVC の既定は off**。どちらも適合で参照実装はどちらも指定していない。`FMA_FFT` 腕を作ると median 1.42e-14＝**窓の中**（本稿の綴り差 A1=2.7e-15, A2=0 は窓の下）。1ビットオラクルの純度は 5/6（83%）が方程式を運ぶ。511行に必要な問い合わせ ≈ 1.5e7。

「効かないは量で言う」「仕様が許した自由は、誰も選ばなくても差になる」。ただし `FMA_FFT` 腕は**模型**であり、#071 で実物に置き換える。

## 7.3 参照実装そのものが2通りの適合ビルドで違う署名を出す ― 8/12で鍵、偽造まで `[#071]` 🟢

> **脅威モデル（この節の核心。誤読を避けるため固定して読むこと）**
> これは任意の FALCON 利用者への汎用的な遠隔攻撃**ではない**。前提は「**同一の秘密鍵**を **2通りの標準準拠ビルド**（`clang -O2 -march=native -ffp-contract=fast` 対 既定ビルド）でビルドし、**同一メッセージへの両方の署名を入手できる**攻撃者」という特定の状況である。この条件下で、両署名2本から秘密鍵が復元され、任意の新メッセージへの万能偽造が可能になる。

#070 の模型をやめ、**C 参照実装そのものを2通りにビルドして差分を取った**。

- **事実0（誰も書いていない）**：参照実装の `fpr` ラッパ（`typedef struct { double v; } fpr;`、目的は型安全）が、**副作用として GCC の縮約をどの設定でも止めていた**。危険なのは `clang -ffp-contract=fast`（＝ `-Ofast`/`-ffast-math`）のみ。
- **事実1**：3ビルド（clang fast / clang 既定 / gcc 既定）は同一シードから**同一の秘密鍵**を作る。10万署名で `gcc default == clang default`（完全一致）、`clang -ffp-contract=fast vs clang default : 12/100000 differ`（率 1.2e-4、A2 綴り差の16倍）。
- **事実2**：12組を攻撃者に渡すと **8/12 で鍵が出る**（すべて ±x^k(f,g) の厳密な NTRU 対称）。しかも復元鍵で基底を完成させ、**被害者が署名していない新メッセージに署名して、被害者の公開鍵が受理（8/8）**。🟢 差分係数数で分類器になる（復元可 916〜966、不可 1020〜1023）。残り4/12 は #069 のチャネル（最初の2回）そのもの。FALCON-1024 でも 6/60000。
- **事実3（陰性対照＝価値の半分）**：普通のビルドの違い（2コンパイラ×native/emulated×`-march`×AVX2 経路の8構成）は**全部ビット一致**。発散は**旗ひとつ**に帰属する。

## 7.4 aarch64 でも同一 ― アーキ非依存、QEMU 上で動的に鍵復元 `[#072]` 🟢

§12 の最大の限界「1プラットフォームのみ」を、別アーキでの完全再現で閉じた。aarch64 は FMA が基本 ISA なので「既定ビルドが危険になるのでは」と警戒したが、**実 `fft.c` の縮約パターンは x86 と同一**（gcc は決して縮約せず、clang は `-ffp-contract=fast` でだけ縮約）。`fpr` ラッパの防御はアーキ非依存。clang aarch64 `-ffp-contract=fast` 対既定を qemu 上で実行すると 19/150000 発散（最初の12個の発散インデックスは x86 実行と完全一致）、低インデックス5ペアから **3/3 で鍵が出て偽造が受理**。🟢 悪化はしていない（既定ビルドは aarch64 でも安全）。

⚪ 残る未測定：MSVC、aarch64 の gcc 実機、AVX2/NEON ベクトル経路の動的比較。

## 7.6 参照実装自身の FALCON_FMA を測る ― config.h の「< 2⁻⁴⁰」は 2²⁷ 甘い `[#074]` 🟢

ユーザの Deep Research：実運用で `-ffast-math` 等で建てている Falcon は無い（脅威は潜在的）。だが参照実装は **FALCON_FMA という明示オプション**を持ち、`config.h` が「署名が変わるのは < 2⁻⁴⁰、safe and interoperable」と自己評価している ― 本稿の主張を参照実装自身が書いて握りつぶしている。

`-DFALCON_FPNATIVE=1 -DFALCON_AVX2=1` を FALCON_FMA 有無で274944本測ると：**30/274944 = 1.09e-4 = 2⁻¹³·²**。config.h の見積り 2⁻⁴⁰ より**約8桁（2²⁷）大きい**。発散ペアは鍵を出す（index 23215/23823 で KEY RECOVERED＋偽造受理）。🟢 「safe and interoperable」は個別には真、**2本揃うと偽**（差が鍵だから）。

⚪ **陰性対照の訂正**：#071 で「AVX2 は安全」と置いたが、正しくは「**FALCON_FMA オフの AVX2 なら**安全」。コンパイラは AVX2 intrinsics を縮約しないが、参照自身の FALCON_FMA スイッチが `_mm256_fmadd_pd` を出す。「効かないの陰性対照は条件を厳密に書く」。「相手が自分で書いて握りつぶした主張は最良の攻め所」。

# 第8部　盲目 which-call 問題の解決

## 8.1 否定的結果2つ `[#075]`

#073 の残余＝**盲目の which-call 曖昧性解消**（オラクルは first-two 発散を教えるが call-1 か call-2 か言わない）を、open で放置せず新技法として解いた。まず2つの素直な道が閉じたことを記録する：

1. 公開データ (s,s',c,h) での判別器 → 精度 0.50〜0.60（ほぼ偶然）。**判別器は無い**（きれいな否定的結果）。
2. 素朴な反復 EM（ランダム初期化→線形解→再ラベル）→ 合成 n=64,128 で 0/5 収束。

## 8.2 rank-2 リフト ― ラベル無しに鍵復元 `[#075]`

**用語**：*rank-2 対称行列*とは、対称（転置しても同じ）で、独立な情報が実質2方向ぶんしかない正方行列。ここでは秘密 f とその固定シフト f' から作る `S = sym(f f'ᵀ)` がそれにあたる。*線形化*とは、二次の関係式を、未知数を行列 S の成分と見ることで一次（線形）の方程式に読み替える技法。

2つの候補行は `b_i = x^{n/2} a_i` の関係にある（f' = −x^{n/2}f は f の固定シフト）。よって「どちらかが0」という論理和は `(a_i·f)(a_i·f')=0`、展開すると

```
a_iᵀ S a_i ≡ 0 (mod q),   S = sym(f f'ᵀ),   rank ≤ 2
```

これは **rank-2 対称行列 S への線形測定**になる。約 M ≈ n(n+1)/2 事象で S が一意に決まり（核次元1）、その**列空間が厳密に span{f,f'}**。そこから f は短ベクトルとして2次元格子抽出で取れる。

`blind_solve.jl` は全パイプラインを合成事象（実 q）で走らせ、**ラベル情報ゼロで f を復元**：n=8 は 7/8、n=16 は 8/8、n=32 は 8/8（M=1.4·n(n+1)/2）。⚪ 代数は n=512 でも同一だが、O(n²) の線形解のため実行は小 n に留まる（未実行）。

## 8.3 帰結 ― 不可能性ではなくクエリコスト則 `[#075]`

- ラベル既知（#065/#073）：**O(n) 事象**。
- 盲目（本項）：**O(n²) 事象**（n 倍のオーバーヘッド）。n=512 で ~1.3e7 対 ~3.3e9 first-two 事象。高いが**多項式**。
- **ブールのみのオラクル**（冗長計算の不一致検出＝1ビット、署名もラベルも無し）でも鍵が出る。「最初の2回は短い格子ベクトルしか出ない」は放置の理由にならない ― 盲目でも**線形**チャネルだから。

「解けないと書く前に、構造を一段深く掘る（2行の関係 b=x^{n/2}a に気づくまで EM 頼みで詰んでいた）。#065 の『n本集めれば決まる』で止めた轍を、今度は踏まなかった」。

## 9.3 FIPS 206 への含意

- **浮動小数点環境は正しさの前提条件であり、仕様が明記しなければならない**（bit 一致 KAT の前提であるだけでなく、丸めモードが署名を無効化しうる＝#068）。
- サンプラ変更（part 1）と鍵生成の parity 条件（part 2）を**同じ条項で義務づけ**、片方だけの適用が無意味であることを明記する必要がある `[#067]`。
- `FP_CONTRACT`/FMA を規範で禁じるべき（現状の安全は参照実装の (a) FPEMU 既定 (b) 明示 intrinsics (c) fpr ラッパ (d) CRITICAL WARNING に依存しており、どれも規範ではない）`[#074]`。

## 9.4 残る未解決

1. A2a/A2b の分離（複素除算単独か D11 単独か）`[#056,#057]`。
2. 実オラクルによる「検出→求解」の一気通貫 `[#073]`。
3. 盲目 which-call の n=512 実行 `[#075]`。
4. rational snapping の前進誤差の**厳密な上界の証明** `[#064]`。
5. MSVC・実機 aarch64・ベクトル経路の動的比較 `[#072]`。

## 9.5 責任ある開示（Coordinated Disclosure）の姿勢

- 本資料の脆弱性はすべて**特定の脅威モデル**（とりわけ #071 系は「同一鍵を2通りの適合ビルドで建て、両署名を入手できる攻撃者」）の下でのものであり、任意の FALCON 利用者への汎用遠隔攻撃ではない。原稿・NIST コメントの両方でこの限定を最初に置く。
- 攻撃と同時に**防御**（rational snapping、part 1+part 2 の同時義務化）を提示する。「破ったら直す」。
- 主張は「小さく言って正確に」（#053）。反証・撤回の履歴（#054, #067, #068 など）を隠さず、独立検証と新規部分の境界を明示する。
