# モジュール 6: NTRU 方程式 ― 塔を降りて、拾って、縮める

## 6.1 この章で答える問い

FALCON の秘密鍵は、NTRU 格子の**短い基底**である。

```
B = [[g, -f], [G, -F]]
```

`f`, `g` は Gaussian から引くだけでよい。問題は `F`, `G` で、
これらは次の方程式を**整数係数で厳密に**満たさなければならない。

```
f·G − g·F = q        （Z[x]/(x^n+1) の中で）
```

つまり鍵生成は「短い `(f,g)` を引いて、それを基底に**補完する**」作業であり、
補完の部分がこのモジュールである。

Dilithium の鍵生成と比べてほしい。あちらは
「`s1`, `s2` を引いて `t = A·s1 + s2` を計算」で終わる。
解くべき方程式が無い。**Module-LWE は「基底」を要求しないから**である。
FALCON は hash-and-sign なので、trapdoor が本物の短い基底でなければならず、
その代償がこのファイル全体だ。

## 6.2 なぜ難しいのか

1. **体の上の方程式ではない。** `Z[x]/(x^n+1)` は環であって体ではないので、
   「逆行列を掛ける」ができない。
2. **素朴な解が巨大になる。** `(F,G)` は最初、係数が数千ビットになる。
   これを `(f,g)` と同程度まで**縮めないと鍵として使えない**。
   長い基底は幅の広い署名を生み、署名が `β²` を超えて検証に落ちる。

## 6.3 降下 ― 体ノルムで塔を降りる

Pornin–Prest の着想は、塔をもう一度使うことだった。**体ノルム**

```
N : Q(ζ_2n) → Q(ζ_n),    N(a) = a(x)·a(−x)
```

は乗法的で、`a(x)a(−x)` は偶数次のみを含むので**半分の次数の環の元として読める**。
方程式全体に `N` を適用すると、次元 `n` の問題が次元 `n/2` の問題になる。

```
次元 n/2 で  N(f)·G′ − N(g)·F′ = q  を解き、
持ち上げる:  F = F′(x²)·g(−x),   G = G′(x²)·f(−x)
```

持ち上げが機能するのは `N(f) = f(x)f(−x)` だからで、

```
f·G − g·F = f·G′(x²)·f(−x) − g·F′(x²)·g(−x)
          = N(f)·G′(x²) − N(g)·F′(x²)
```

括弧の中身が、まさに半次数の方程式を持ち上げたものになっている。

再帰の底は `n = 1`。そこでは `Z[x]/(x+1) = Z` で、方程式は
`f₀·G₀ − g₀·F₀ = q` という**ただの整数方程式**になり、拡張ユークリッドで解ける。
`gcd(f₀,g₀) = 1` でなければ解が無いので、鍵生成は `(f,g)` を引き直す。
これは防御的なチェックではなく**実際に起こる**（実測: n=128 で 2 回連続で
弾かれてから 3 回目で成功した）。

**解が構成されるのは底の 1 箇所だけ**で、その上は全部「持ち上げて縮める」である。

## 6.4 多倍長がどこで必要になるか

モジュール 5 で測った数字が、ここで判断根拠になる。n = 512 での係数サイズ:

| 段階 | 係数の大きさ |
|:---|:---|
| `f`, `g`（入力） | 数ビット（σ_fg ≈ 4 なので \|c\| < 30） |
| 各降下段の `N(f)` | **ビット長が毎段およそ 2 倍** |
| 底（9 段降りた後） | 数千ビット |
| 拡張ユークリッドの出力 | `q` 倍される。短さの保証は一切無い |
| 持ち上げ | さらに `g(−x)` を掛けて伸びる |

**9 段で 2 倍を 9 回**なので、`BigInt` は避けられない。
「数が大きそうだから」ではなく、**毎段 2 倍が 9 回**だから。

そしてこれが、モジュール 5 で「FFT の積の誤差が 1/2 を超えるのは
係数 1e7 付近」と測っておいたことの答え合わせになる。
数千ビットは 1e7 の遥か彼方なので、**この積に FFT は使えない**。
参照実装が Karatsuba を使っているのはそのためで、
コメントにも「n=1024 では全体の 75% 以上のコスト」とある。

## 6.5 Babai 縮約 ― ここで浮動小数点が戻ってくる

縮約は最近平面法（Babai）である。

```
(F,G) ← (F,G) − k·(f,g),   k = round( (F·f* + G·g*) / (f·f* + g·g*) )
```

`k` は実埋め込みにおける `(F,G)` の `(f,g)` 方向の座標なので、
これを引けば `(F,G)` は最短に近づく。
しかも**引くのは `(f,g)` の倍数なので `f·G − g·F` の値は変わらない**。
方程式を厳密に保ったまま係数だけが縮む。

### 数千ビットの数を Float64 で割る、が壊れない理由

`F`, `G` は数千ビットなのに `k` は Float64 で計算する。
モジュール 5 の誤差表を見た後だと不安になるが、3 つの理由で問題ない。
**この 3 つを分けて理解するのが要点である。**

1. **計算するのは比だけ。** `F`,`G` がどれだけ巨大でも、
   分子と分母が一緒に大きくなるので `k` は O(1)。
   **正確でなければならないのは積ではなく商**である。

2. **両辺を 53 ビットに前もって落としている。**
   `f_adjust = f >> (size − 53)` は各係数の上位 53 ビットを取る。
   53 ビットは Float64 の仮数部そのものなので、
   **この変換は厳密**で、丸めは一切入らない。
   `F`,`G` 側も同様に自分のスケールで落とし、
   引くときにスケール差をシフトで戻す。
   丸められるのは最後の `k` を整数にするところだけで、
   そこは元々丸めたい場所だ。

3. **反復する。** `while` ループが `k` がゼロになるか
   サイズが縮まなくなるまで繰り返す。だから
   **`k` が不正確でもそれは誤りではなく、収束が遅くなるだけ**。
   次の周回が直す。これは反復改良であり、
   FALCON がこの箇所については倍精度で済ませられる理由である。

対比が重要だ。**モジュール 8 の `ffSampling` にはこの補正ループが無い。**
浮動小数点の結果がサンプラに直接食われ、出た答えがそのまま署名になる。
だから仕様が丸めまで固定しなければならないのは**あちら**であって、ここではない。
「FALCON は浮動小数点を使うから危ない」ではなく、
**「補正の効かない場所で使うから危ない」**のである。

## 6.6 Python の `//` と Julia の `div` は違う

移植で先回りして潰した罠を 1 つ。底の拡張ユークリッドは

```python
q, b, n = b // n, n, b % n
```

Python の `//` は**床除算**、`%` は**除数の符号**を取る。
Julia の `div` / `rem` は**ゼロ方向切り捨て**である。
`f₀`, `g₀` は負になりうるので、ここは一致しない。

gcd 自体は同じ値になるが、**Bezout 係数が変わる**。
そして Bezout 係数は最終的に鍵の中身になる。
つまり間違えても

- 方程式は成立する
- 鍵は動く
- 署名がほんの少し長くなるだけ

という、**何も文句を言わない**バグになる。
Julia では `fld` / `mod` が Python の `//` / `%` に対応するので、そちらを使う。

（余談: `>>` のほうは Julia も Python も算術シフト（床除算）なので一致する。
食い違うのは `div` 系だけ。この非対称性が余計に紛らわしい。）

## 6.7 「共役」が 2 つある

このモジュールには `galois_conjugate(a) = a(−x)` が出てくる。
モジュール 3 の `polyadj(a) = a(1/x)` とは**別物**である。

| | 定義 | 役割 |
|:---|:---|:---|
| `polyadj` | `a(1/x)` | エルミート随伴。Gram 行列、LDL* |
| `galois_conjugate` | `a(−x)` | `Q(ζ_2n)/Q(ζ_n)` の Galois 自己同型。体ノルム |

どちらも文献で "conjugate" と呼ばれる。
`galois_conjugate` の固定体がちょうど半次数の部分体で、
だから `N(a) = a·σ(a)` が塔を 1 段降ろす。
テストには「この 2 つが一致しないこと」を明示的に書いてある。

## 6.8 検証 ― このモジュールだけオラクルが要らない

このプロジェクト全体で最も強い検証がここにある。

```
f·G − g·F = q
```

は**厳密な整数の等式**である。許容誤差も、標本分布も、
信じるべき参照バイト列も無い。`BigInt` で計算すれば白黒がつく。

したがってテストは 2 段構えになる。

- **`ntru_equation_holds` を全部に掛ける。** オラクル不要。
  これを通った解は、それだけで正しい。
- **参照実装の `(F,G)` と厳密一致**も見る。正しさには不要だが、
  方程式だけでは決まらない自由度 ―
  底の Bezout 係数の選び方と、Babai 縮約がどこまで進むか ― を固定する。
  **鍵が「有効」であることと「短い」ことは別**で、後者を守るのはこちら。

6.6 の `div` / `fld` の間違いを捕まえるのは、まさに 2 番目のテストである。

### 実測

- **n = 512 の求解は約 11 秒**（Julia、BigInt）。参照実装（Python）は分単位。
- **縮約は非常によく効く。** `(f,g)` が 8 ビットのとき、
  `(F,G)` は 8〜16 ビットで返ってくる。
  縮約前は数千ビットなので、**3 桁縮んでいる**。
- n = 256 と n = 512 については、参照実装を待たずに
  **Julia 側で解いて方程式を直接検証**している（オラクル不要なので可能）。

## 6.8b 鍵生成の入口 ― `ntru_gen`

モジュール 7（サンプラ）が揃ったので、鍵生成の入口が書ける。

```
繰り返す:
    f, g を D_{Z, 0, σ_fg} から引く
    (1) gs_norm(f,g) > 1.17²·q なら引き直し        ← 基底が長すぎる
    (2) f が mod q で可逆でなければ引き直し          ← h = g/f が存在しない
    (3) ntru_solve が失敗したら引き直し              ← 底の gcd ≠ 1
    F, G を返す
```

3 つの棄却条件はどれも乱数を消費しないので、順序はバイト列に影響しない。
実測の受理率はおよそ 3 回に 1 回。

### `gen_poly` の落とし穴

参照実装は **`n` によらず 4096 個**サンプルを固定幅
`1.43300980528773` で引き、`4096/n` 個ずつ畳む。
モジュール 1 で触れた話だが、実装すると重みが分かる。

`n` 個を直接 `σ_fg` で引いても**分布は同一**である。
違うのは **PRNG の消費**だけ。つまりこの「最適化」は

- 統計的検定を全部通り
- KAT を全部落とす

モジュール 7 の「KAT のバイトを逆順に食わせる」（#022）と同じ種類の罠で、
**数学には見えず、再現性には致命的**。
だからテストは係数の一致だけでなく**消費バイト数の厳密一致**も主張している。
実測では n=8 でも n=1024 でも約 7 万バイト消費する
（4096 サンプル × 約 17 バイト）。
もし誰かが「n 個引けば十分」と直したら、n=8 の消費が 512 分の 1 になって落ちる。

## 6.9 Dilithium との対比（まとめ）

| | Dilithium | FALCON |
|:---|:---|:---|
| 鍵生成 | `t = A·s1 + s2` を計算するだけ | **方程式を解く** |
| 解くべきもの | 無し | `f·G − g·F = q` |
| 再帰 | 無し | 体ノルムで塔を 9 段降りる |
| 多倍長 | 不要 | **必須**（毎段 2 倍が 9 回） |
| 引き直し | 棄却サンプリング（署名時） | `gcd ≠ 1` と Gram-Schmidt ノルム（鍵生成時） |
| 検証手段 | 分布の性質 | **厳密な整数等式** |

最後の行が、実装者にとっては救いである。
FALCON のほとんどのモジュールは「分布が正しいか」「丸めが許容範囲か」という
確率的・近似的な検証しかできないが、**このモジュールだけは白黒がつく**。
だからこそ、ここで詰まったときは
「方程式が成立しているか」を最初に見ればよい ―
成立していれば降下と持ち上げは正しく、疑うべきは縮約のほうである。
