# モジュール 7: 離散 Gaussian サンプラ ― 本題

## 7.1 序盤の問いを、ここで半分回収する

> **NIST PQC 4 方式のうち、なぜ FN-DSA だけ標準化が遅れたのか。**

モジュール 5 で答えの半分を出した ―
**浮動小数点の結果が bit 単位で再現しなければ、署名が非決定的になり、
それは鍵の漏洩に直結する**。他の 3 方式は整数演算で閉じているので
この要求が存在しない。

残り半分がこのモジュールである。すなわち
**その浮動小数点計算を、同時に定数時間で行わなければならない**。

## 7.2 要求は 2 つ、同時に

中心 `μ` と幅 `σ` を与えられて、`D_{Z, μ, σ}` に従う整数 `z` を返す。
必要な性質:

1. 出力分布が統計距離 `2^-45` 程度まで正しいこと
   （これが `σ_min` を決めた条件。モジュール 1 参照）
2. **実行時間・メモリアクセスパターン・消費した乱数バイト数が
   `μ` にも `σ` にも `z` にも依存しないこと**

2 が効く。Gaussian を引く自然な方法は棄却サンプリングだが、
棄却サンプリングは**定義上、秘密依存の回数だけループする**。
しかも `μ` は公開値ではない ― `ffSampling` の中で、
秘密基底から 1 座標ずつ出てくる。
どの `z` が返ったかが時間に漏れれば格子点が漏れ、格子点が漏れれば基底が漏れる。

## 7.3 参照実装はどう折り合いをつけているか

3 段重ねである。

### (a) 固定された基底分布

`σ` の幅で引く代わりに、**固定幅 1.8205 の半 Gaussian** から引く。
`basesampler` は 72 ビットの一様乱数を 1 個引き、
18 要素の逆累積分布表（RCDT）の**全要素と比較して**、
下回った個数を返す。

```
z0 = Σ_{i} [ u < RCDT[i] ]
```

早期脱出しないので、表アクセスは常に同じ。
そして `σ` は表に一切入らない。

**ここで `σ_max = 1.8205` という半端な小数の正体が分かる。**
これは導出された値ではなく、**表を焼いた幅**である。
モジュール 1 で「上限は理論値ではなく実装の都合」と書いたのは、この意味だった。

### (b) 比に対する棄却

受理確率は `ccs·exp(−x)`、`x` は 2 つの Gaussian の対数比。
基底分布が固定でしかも**どの許容 `σ` より少し広い**ので、
比は必ず 1 以下の確率になる。
**これが `σ_min < σ < σ_max` という制約の買っているもの**である。

### (c) exp の多項式近似を整数演算で

`approxexp` は `2^64·ccs·exp(−x)` を **12 次多項式の固定小数点評価**で計算する。
`exp()` の呼び出しも、浮動小数点の分岐も、秘密で引くテーブルも無い。
係数は FACCT（doi:10.1109/TC.2019.2940949）から借りている。

そして残ったのが**棄却回数**である。ここは依然としてデータ依存で、
参照実装はそれを受け入れている。完全な定数時間実装はさらに手を打つ必要がある。

## 7.4 補正ループが無い

モジュール 6 の Babai 縮約も浮動小数点を使ったが、安全だった。
**反復するから**である ― `k` が不正確でも収束が遅くなるだけで、
次の周回が直す（6.5 節）。

**ここには補正ループが無い。**

Float64 の `x` がそのまま `berexp` に渡り、その 1 ビットが
「この `z` を出力するか」を決める。`x` の丸めが違えばビットが違い、
ビットが違えば署名が違う。

つまり**「同じ鍵・同じメッセージなら、どのプラットフォームでも同じ署名」**
という要求が、ここで浮動小数点への制約に変わる。
そして 5.7 節で見た通り、その非決定性は**壊滅的なセキュリティ障害**である。

> **FALCON の浮動小数点が危ないのは、使っているからではなく、
> 補正の効かない場所で使っているからである。**

これがモジュール 6 と 7 を並べて初めて言えることで、
原稿ではこの 2 章を対にして書くのがよい。

## 7.5 移植で踏んだこと

### (a) Python の多倍長が幅を隠す（3 度目）

- **RCDT** は 18 個の**72 ビット**整数。`UInt64` に入らない → `UInt128`
- **exp の係数**は最上位が `0x8000000000000000 = 2^63`。
  `Int64` に入らない → `UInt64`
- **`approxexp` の中間積**は `2^126` に達する → `UInt128`

Python ではこれが全部見えない。#017（ChaCha20 のカウンタ）、
#015（Keccak の LFSR）に続いて 3 度目である。
**多倍長言語で書かれた参照実装は、固定幅の挙動を隠す。**

### (b) `LN2` は正しく丸めた値ではない

参照実装はこう書いている:

```python
LN2  = 0.69314718056       # 正: 0.6931471805599453
ILN2 = 1.44269504089       # 正: 1.4426950408889634
```

相対で 1e-12 ずれている。**直してはいけない。**

分布には影響しない（`x` を「2 で何回割るか + 余り」に分ける係数なので、
一貫していればどう分けても正しい）。
しかし**参照実装のバイト列を再現するには致命的**で、
分け方が変われば `s` が変わり、シフトが変わり、
同じ乱数バイトに対する受理/棄却の判断が変わる。

**実装の都合が規範に昇格した、この本で一番小さくて明快な例**である。

### (c) KAT のバイトは「逆順」で食わせる

公式 KAT（`samplerz_KAT512.py` など）は
`(mu, sigma, sigmin, octets, z)` の 3072 本。
これを素直に replay すると**答えが合わない**。

参照実装のテストハーネス（`test.py` の `KAT_randbytes`）を見ると:

```python
oc = octets[:2*k]; octets = octets[2*k:]
return bytes.fromhex(oc)[::-1]      # ← 反転
```

**要求ごとに k バイトを取って、反転して返す。**

モジュール 2 の `rng.py` にも反転が 2 回出てきたが、あちらは
**打ち消し合って恒等写像**だった（#005）。
こちらは 1 回だけなので**打ち消さない**。
同じ見た目の処理が、片方では無意味で片方では必須である。

しかも間違えても例外は出ない。**別のもっともらしい整数が返るだけ**。
だから「反転しない replay では 200 本中 100 本以上が違う答えになる」
というテストを入れて、この規約が飾りでないことを固定してある。

## 7.6 参照実装の docstring が間違っていた

`approxexp` の docstring はこう書いている。

> an integral approximation of `2^63 * ccs * exp(-x)`

**2 倍違う。** 実際に返るのは `2^64·ccs·exp(−x)` である
（`z = int(ccs * (1 << 63)) << 1` の `<< 1` の分）。
測ると比はきっかり 2.000000。

そして `2^64` のほうが**正しい**。`berexp` はこの値を
64 ビット一様乱数と 8 バイトずつ比較するので、
確率は `2^64` の分数で表現されていなければならない。
つまりコードは正しく、コメントが誤っている。

危ないのは、**その誤った主張を自分の docstring に写してしまう**ことだった。
実際に一度写し、性質テストが「2 倍違う」と言って捕まえた。

## 7.7 検証の三段構え

サンプラは、これまでのどのモジュールより検証が難しい。
出力は**ランダムに見えるのが正しい**からで、
微妙に間違ったサンプラはもっともらしい整数を延々と返し、
「署名がわずかに長い」か「鍵がゆっくり漏れる」という形でしか現れない。

だから 3 種類を独立に用意した。

1. **公式 KAT 3072 本。** バイト単位で厳密。
   固定小数点演算・定数・バイト消費の全部を一度に固定する。**最強。**
2. **定数を、それが名乗っているものと照合。**
   RCDT が本当に幅 1.8205 の半 Gaussian の逆 CDF か、
   `EXP_COEFFS` が本当に `exp(−x)` を近似しているか。
   高精度演算で計算した理論値と**絶対値で 16 以内**（実測は 8 以内）。
3. **分布そのもの。** 実際の PRNG で 20 万サンプル引いて、
   平均・分散・χ² 検定。統計的には一番弱いが、
   **「我々のコードと KAT が同じ間違いをしている」場合に気づける唯一の検査**。

### 2 番目で 2 回間違えた

- 最初、半 Gaussian を「折り返し」（`z > 0` を 2 回数える）だと思った。
  表は `P(z0 = 0) = 0.359` だが、折り返しモデルは `0.219` を与える。
  **正しくは `D_{Z+}`、つまり非負整数を各 1 回ずつ**。
  符号は `samplerz` が別に付けるので折り返さない。
- 次に、相対誤差 `1e-9` で比較して深い側 5 本が落ちた。
  表の値は `3e21` から `1` まであり、**末尾では整数への量子化が支配的**になる。
  相対では測れない。絶対値で測るのが正しい。

どちらも**コードではなくこちらの主張が間違っていた**。
このプロジェクトで 4 回目のパターンである（#018, #019, #021, #023）。

## 7.8 Dilithium との対比（まとめ）

| | Dilithium | FALCON |
|:---|:---|:---|
| 秘密の分布 | 一様（`|c| ≤ η`） | **離散 Gaussian** |
| サンプリング | 一様な棄却。定数時間が容易 | 固定表 + 比の棄却 + 固定小数点 exp |
| 浮動小数点 | 無し | **中心 `μ` の計算に必須** |
| 補正の有無 | — | **無い**（モジュール 6 とはここが違う） |
| 定数時間の難所 | 棄却率の扱い | **すべて** |
| 検証 | 分布の性質 | KAT・定数の再導出・χ² の三段構え |

Dilithium を移植したとき、サンプラで悩んだ記憶はほとんど無いはずだ。
一様分布を棄却で作るのは易しく、定数時間にするのも易しい。
**Gaussian に変えた瞬間に、それが全部難しくなる。**
そして Gaussian でなければ hash-and-sign の安全性証明が立たない。

FN-DSA が遅れた理由は、この一点に集約される。
