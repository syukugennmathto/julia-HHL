# C 参照実装 vs. この Julia 実装 ― 速度対決

> 生データと再現手順のみ。設計上の解釈は
> `docs/debug_log.md` #031〜#035 に書く。
>
> **計測方法について #035 を先に読むこと。** このファイルの初版は
> 計測器側の欠陥で署名を 1.5 倍速く報告していた。

## 測定条件

| | |
|:---|:---|
| CPU | x86-64（コンテナ内、`fma` あり）。**Apple Silicon ではない** |
| Julia | 1.12.7（`docs/debug_log.md` #013 の手順で入手） |
| C | round-3 参照実装（algorand/falcon ミラー）、`gcc -O2` |
| 単位 | 1 回あたりのミリ秒、**中央値** |
| 反復 | keygen 20 / sign 200 / verify 200（C）、keygen 3 / sign 50 / verify 200（Julia） |

再現:

```sh
# C 側（cbuild/ に参照実装の .c を置いた状態で）
cc -O2 -o cref_bench cref_bench.c \
   codec.c common.c falcon.c fft.c fpr.c keygen.c rng.c shake.c sign.c vrfy.c -lm
cc -O2 -DFALCON_FPEMU=0 -DFALCON_FPNATIVE=1 -o cref_bench_nat cref_bench.c ...同上...
./cref_bench     9 20 200 200 > c_emu_512.txt
./cref_bench_nat 9 20 200 200 > c_nat_512.txt

# Julia 側
julia --project=falcon falcon/scripts/bench.jl 9 5 30 100 > jl_512.txt

# 突き合わせ
julia falcon/scripts/bench_compare.jl c_emu_512.txt c_nat_512.txt jl_512.txt
```

**中央値を採る理由**: 鍵生成は `ntru_solve` が解けるまで再試行するので
分布に長い右裾がある。平均は代表値にならない
（C の実測でも min 10.9 ms / median 13.0 ms / mean 16.6 ms と開く）。

**Julia 側は計測前に全操作を 1 回空回ししている**。最初の呼び出しは
実行ではなくコンパイルであり、混ぜると 100 倍単位で嘘の数字になる。
GC は止めていない ― 割り当てはこの実装の実コストであり、隠すのは不誠実。

**比較の単位を合わせること**: C の `falcon_sign_dyn` は毎回 Falcon 木を
作り直し、`falcon_sign_tree` は展開済み鍵を使う。我々の `falcon_sign` は
展開済み鍵を取るので、**対応するのは `sign_tree`**。
`sign_dyn` と比べると木の構築コスト分だけ我々に下駄を履かせることになる。

## 【方法】この文書の数字をどう読むか

> **先にこの節を読むこと。** このファイルは過去に二度、方法の欠陥で
> 誤った数字を載せている（#035、#052）。手続きを本文に昇格させたのは
> そのためで、以下は装飾ではなく主張の一部である。

### 1. 中央値を採る。平均は代表値にならない

鍵生成は `ntru_solve` が解けるまで再試行するので分布に長い右裾がある。
署名も棄却で再標本する。GC はいつ来るか分からない。
**平均は「その run で GC が何回来たか」を測ってしまう。**
実測でも `keygen` は median 11.7 / mean 19.6 と 1.7 倍開く。
分布の形が違うものを平均で比べてはいけない。

### 2. Julia は計測前に全操作を空回しする

最初の呼び出しは実行ではなくコンパイルである。
混ぜると 100 倍単位で嘘の数字になる。

### 3. GC を止めない。ただし「止めない」の意味を間違えない

割り当てはこの実装の実コストなので隠さない。
しかし **`GC.gc()` を各計測の直前に呼ぶのは「隠す」に当たる** ―
割り当ての多い段が引き起こすはずだった回収を計測区間の外に出してしまう。
初版のプロファイラがこれをやっていて、**署名を 42% 速く報告していた**
（#035）。既定は「呼ばない」である。

### 4. 比較の単位を合わせる

C の `falcon_sign_dyn` は毎回 Falcon 木を作り直し、
`falcon_sign_tree` は展開済み鍵を使う。
我々の `falcon_sign` は展開済み鍵を取るので、**対応するのは `sign_tree`**。
`verify` は両者とも**バイトからバイトまで**
（`pubkey_from_bytes` + `falcon_verify` 対 C の `falcon_verify`）。

### 5. C は「1 ビルド」ではない。範囲で比べる（#052）

**これが最も新しく、最も痛い教訓である。**
初版は `gcc -O2` の 1 ビルドを「C」と呼んで比較し、
`verify` について「C のどのビルドにも 1.58 倍勝っている」と書いた。
コンパイラと最適化水準を振ったら、**その主張は消えた**。

    verify、C のビルド間の幅   0.0166 ms （clang -O3 -march=native）
                              〜 0.0268 ms （gcc -O2）  = 1.6 倍

**C 側のビルド間の幅が、主張していた差そのものと同じ大きさだった。**
以後、C は `{gcc, clang} × {-O2, -O3, -O3 -march=native} × {native FP, FPEMU}`
の 12 ビルドで測り、**範囲として**提示する。
再現は `scripts/bench_matrix.sh`。

### 6. run 間のばらつきを隠さない

Julia 側は同一設定で 3 回走らせ、**3 つの中央値の幅**を出す。
JIT の判断と GC の状態は run をまたいで同じにならない。
`verify` は 0.0164〜0.0213 ms と 1.3 倍動く。
**1 回しか走らせないと、この幅の中のどこかを「値」として報告することになる。**

## FALCON-512 ― 現在の総合結果

**同一マシン・同一時刻の 1 セッションで測り直した中央値（ms）。**
C は参照実装自身の Makefile と同じ `clang -O3`。
`verify` は両者とも**バイトからバイトまで**（我々の側は
`pubkey_from_bytes` + `falcon_verify`。C の `falcon_verify` は
公開鍵のバイト列を受け取って毎回展開するので、そうしないと比較にならない）。

| op | C (FPEMU, 参照実装の既定) | C (native FP) | **Julia** | Julia / C(既定) |
|:---|---:|---:|---:|---:|
| `keygen` | 10.881 | 5.146 | **132.671** | 12.2x 遅い |
| `expand_privkey` | 1.456 | 0.061 | **0.457** | **3.2x 速い** |
| `sign`（展開済み鍵） | 1.566 | 0.146 | **1.155** | **1.36x 速い** |
| `sign_dyn`（毎回木を作る） | 3.474 | 0.230 | **1.612**（展開+署名） | **2.2x 速い** |
| `verify` | 0.0204 | 0.0204 | **0.0148** | **1.38x 速い** |

`verify` は浮動小数点を一切使わないので **C の 2 つのビルドは同じ値**になる ―
つまりここでの勝ちは FPEMU のハンデに依らない。3 ラウンド反復して
Julia 0.0148 / C(-O3) 0.0206 / C(-O3 -march=native) 0.0167 で安定（#039）。

### 3 つ合わせるとどうなるか

**(a) 1 回ずつ（鍵を作って 1 通署名して 1 通検証する）**

| | 合計 ms |
|:---|---:|
| C (native FP) | 5.37 |
| C (FPEMU, 既定) | 13.92 |
| **Julia** | **134.30** |

C(既定) の **9.6 倍**、C(native) の 25.0 倍。
**そして我々の合計の 98.8% は `keygen` である。**

**(b) 定常運用（鍵 1 個で N 通署名・検証する）**

    Julia      = 133.13 + 1.1698 N
    C (FPEMU)  =  12.34 + 1.5864 N

**N ≈ 290 で逆転する。** 鍵 1 個あたり 290 通を超えて署名・検証するなら、
この実装は参照実装の既定ビルドより**速い**。

C の native FP 版とは、傾き（1.1698 対 0.1664）で負けているので
**永久に追いつかない** ― 署名が 7.9 倍遅いままだからである。

**(c) 検証だけの用途**（署名を受け取って確かめるだけの側）

**どの C ビルドにも勝っている**（1.13〜1.39 倍）。鍵生成も署名も出てこない。

### どの C と比べるのが公平か

`keygen` と `sign` では**両方の数字を見る必要がある**。

- 参照実装が**実際に配布されるビルドは FPEMU** である
  （`config.h` が `FALCON_FPEMU 1` で無条件に上書きし、
  *** CRITICAL SECURITY WARNING *** 付きでそう書いてある）。
  署名の決定性がセキュリティ性質だからで、
  ネイティブ FPU にすると「同一メッセージへの異なる 2 署名から
  任意メッセージの偽造が可能になりうる」と警告している。
- 我々はハードウェアの double をそのまま使っている。
  つまり **C が払っている 1 桁を払っていない代わりに、
  その保証を持っていない**（`docs/debug_log.md` #031）。

だから「`sign` で 1.36 倍勝った」は、**同じ保証の下での勝ちではない**。
公平に読むなら「我々の署名は C のネイティブ FP 版の 7.9 倍遅く、
そして C のネイティブ FP 版は参照実装が使うなと言っているビルドである」。

`verify` にはこの留保が要らない。整数演算だけなので
両ビルドが同じ値を出し、そこで勝っている。

### 読み方

**1. 署名は C の FPEMU 版と完全に互角**（2.05 ms 対 2.04 ms）。
鍵展開に至っては Julia のほうが速い（0.98 ms 対 1.77 ms）。

これは Julia が速いというより、**FPEMU が高い**という話である。
C 側はネイティブ FPU を使えば署名が 10 倍速くなる（2.04 → 0.194 ms）。
つまり参照実装は、移植性・再現性のために**実行速度の 1 桁を支払っている**。
我々はハードウェアの double をそのまま使っているので、
その 1 桁を払っていない ― 代わりに、払わなかったぶんだけ
「どのマシンでも同じ署名が出る」という保証を失っている
（`docs/debug_log.md` #031）。

**この 2 つは同じコインの裏表であり、性能表だけを見ても意味が取れない。**

**2. 検証が 15 倍遅いのは浮動小数点のせいではない。**
`falcon_verify` は**整数演算だけ**である（`src/falcon.jl` の docstring）。
だから「Julia が遅いのは FP まわりだろう」は仮説として外れている（#032）。

内訳を測った（n=512、中央値 ms、**`sqnorm` を直す前**）:

| 段階 | 時間 | 割合 |
|:---|---:|---:|
| `decode_signature` | 0.0065 | 2% |
| `hash_to_point` | 0.026 | 7% |
| `polymulq`（学校算法） | 0.126 | 33% |
| **`sqnorm`（`BigInt`）** | **0.186** | **49%** |
| 合計 | 0.345 | |
| `falcon_verify` 全体 | 0.380 | |

**一番高いのは多項式乗算ではなく `sqnorm` だった。**
`BigInt` の割り当てが 1024 係数ぶん走る。C は `int32` の
積和を回すだけなので、ここは丸ごと余分なコストになっていた。
#034 で潰したので、いまの律速は `polymulq` に移っている（後述）。

そして、参考のために測った `polymulq_ntt` が

| | 時間 |
|:---|---:|
| `polymulq`（学校算法, O(n²)） | 0.126 ms |
| `polymulq_ntt`（NTT 経由, O(n log n)） | **0.938 ms** |

**NTT のほうが 7.4 倍遅い。**
「`verify` を NTT に差し替えれば速くなる」は完全に間違いだった。
n=512 では O(n²) の 262144 回の積和のほうが、
再帰的な `merge_ntt`/`split_ntt` が各段で配列を割り当てるコストより安い。
漸近計算量が勝つ次数にまだ届いていない
（そして FALCON には n=1024 より上が無い）。

**3. 鍵生成の 738 倍が本丸。**
`ntru_solve` の再帰下降が `BigInt` を使っている。
C は 31 bit リムの RNS（剰余系）で同じ計算をやり、割り当てもしない。
これは定数倍ではなく**アルゴリズムの差**であり、
他の 3 項目（0.6x / 1.0x / 15x）と桁が違うことがその証拠になっている。

なお `BigInt` を使っているのは怠慢ではない。
n=512 の降下の底では係数が数千 bit になり、`Int128` でも足りない
（`docs/math/06_ntrugen.md`）。速くするなら「BigInt をやめる」のではなく
「C と同じ RNS を実装する」ことになる。

## どこで遅いのか（段ごとの実測）

`scripts/profile_stages.jl` と `scripts/profile_ntrusolve.jl`。
詳しい読み取りは `docs/debug_log.md` #033 / #034。要点:

### 鍵生成 13.4 s の内訳（#036 で直す前）

**99.98% が `ntru_solve`、そのうち 96.3% が n=128 の `babai_reduce` 1 回**
（11466 ms、9.0 GB）。降下の底（n≤64）は合計 100 ms 程度しかない。

> **これは #036 で 63 倍速くなった**（11913 → 190 ms、9.61 → 0.15 GB）。
> 以下の分析は、その修正に至る過程の記録として残してある。

理由は縮約が 1 反復で上位 53 bit しか削れないこと。
n≤64 では終了条件に届かないまま抜けるので 6200 bit の係数が運ばれ、
n=128 で ~117 反復の巨大な縮約が 1 回だけ走る。
**これは参照実装と同じ挙動**（Python 側にも「この 2 行が
ntru_gen の 75% 以上」という本人のコメントがある）。

### 「Julia なら速いはず」の境界

同じ小さい値（`Int64` に収まる）65536 個の二乗和:

| | 時間 | 割り当て |
|:---|---:|---:|
| `Int64` | 0.031 ms | 0 |
| `Int128` | 0.234 ms | 0 |
| **`BigInt`** | **9.780 ms** | **8.01 MB** |

`BigInt` は GMP の `mpz_t` を包んだ heap オブジェクトで、
`Vector{BigInt}` は値ではなく**ポインタの配列**。
演算ごとに確保と GC が走るので、**Julia の速さの前提が全部崩れる**。
`Int64` に収まる値ですら 315 倍遅い。

### 署名・検証で実際に効いていたもの

`sqnorm` が**検証の 46%、署名の 14%** を占めていた。
扱う係数は `|c| ≤ 6144` で総和は `2^38` 未満 ―
大きい数だから遅いのではなく `BigInt` だから遅い。
#034 で 227 倍速くした（範囲チェック + `Int128`）。結果 **検証は 2 倍**。

### 署名の半分は GC である

`sqnorm` を潰したあとの内訳。**同じ操作を 2 通りで報告する**:

| | median ms | alloc MB |
|:---|---:|---:|
| `falcon_sign` 定常状態 | **2.199** | 1.868 |
| `falcon_sign` 回収直後 | **1.055** | 1.868 |
| `falcon_verify` 定常状態 | 0.225 | 0.064 |
| `falcon_verify` 回収直後 | 0.236 | 0.064 |

**署名の 52% は、署名 1 本が出す 1.87 MB を生きたヒープに確保する代償。**
検証は割り当てが 0.064 MB しかないので差が出ない。

2 行で出すのは、どちらか一方が正解ではないから。
強制回収は GC の停止を計測区間の外に出すだけでなく、
計測対象に**圧縮済みのヒープ**を渡す ― そこへの確保は速く、
現実のワークロードは決してその状態にない。
2 つの数字は真実を**挟む**（`docs/debug_log.md` #035）。

署名の内訳（回収直後の側）:

| | ms | 割合 |
|:---|---:|---:|
| `sample_preimage` | 1.103 | ― |
| `randombytes` インタフェース（5071 回） | 0.157 | 7% |
| `samplerz` ×512 | 0.133 | 6% |
| `fft` 1 回 | 0.052 | ― |
| `sqnorm` | 0.001 | 0.05% |

**サンプラも FFT の演算も律速ではない。**
効いているのは `split_fft` / `merge_fft` / `add_fft` / `mul_fft` が
すべて**新しい配列を返す**こと。`ffsampling` はそれを O(n log n) 回呼ぶ。
署名 1 本が `randombytes` を **5071 回**呼び（平均 3.7 バイト）、
そのたびに `Vector{UInt8}` を 1 つ確保する。

検証のほうは `polymulq`（学校算法）が 0.157 ms で **70%**。
`sqnorm` を潰した結果、次の律速がここに移った。
NTT に差し替えると**遅くなる**（上記）ので、
速くするなら NTT の割り当てを消すことになる。

底の係数の bit 長も伸びて `BigInt` の負担が二重に増えるためで、

## verify: C に勝った（#039）

**バイトからバイトまで、20000 反復の中央値、3 ラウンド交互測定**
（我々の側は `pubkey_from_bytes` + `falcon_verify`。C の `falcon_verify` は
公開鍵のバイト列を受け取るので、展開込みでないと比較にならない）:

| | round 1 | round 2 | round 3 |
|:---|---:|---:|---:|
| **Julia（この実装）** | **0.02550** | **0.02554** | **0.02582** |
| C `clang -O3 -march=native` | 0.02664 | 0.02666 | 0.02667 |
| C `clang -O3`（参照実装の Makefile） | 0.02752 | 0.02750 | 0.02746 |
| C `gcc -O3 -march=native` | 0.02784 | 0.02783 | 0.02772 |

**3 ラウンドすべてで、すべての C ビルドより速い。**
最速の C 比で 3〜4%、参照実装自身のビルド比で 6〜7%。
`verify` 全体では **0.251 → 0.0255 ms、9.8 倍**。

**`-march=native` の C を相手にしている**のは、Julia が既定でホスト向けに
ネイティブコンパイルするから。移植可能バイナリの C と比べるのは不公平になる。

### 決め手

段ごとに測ると、**最後の 3 段が NTT の 70%** を食っていた
（1 バタフライあたり len=256 で 0.67 ns、len=1 で 5.34 ns）。
演算量は全段同じで、違うのは内側ループの長さだけ ―
`len=1` では内側が 1 反復なのでベクトル化する余地が無い。

そこで **len=4,2,1 を 1 パスに融合**し、連続 8 係数をレジスタに載せて
12 バタフライを回す。前進 NTT 4.17 → 1.74 µs、逆 2.62 µs。

ほかに `_reduce_u32` の分岐除去（`s2` は中心化されていて正負が半々なので
分岐予測を 512 回外す）、逆変換 twiddle の事前計算、
`decompress_sig` の 64 bit 窓化、`hash_to_point` の rate ブロック化。

**速くしたつもりで遅くなった変更が 3 つ**（`@view` を渡す、`collect` を省く、
C と同じ UInt16 + Montgomery）。詳細と外した仮説は #039。

## verify を C に勝たせようとした結果（#038）

`docs/debug_log.md` #038。verify だけを本気で詰めた ―
整数演算だけで浮動小数点の再現性が絡まないので、狙うならここ。

**バイトからバイトまで、同時刻・20000 反復の中央値**（我々の側は
`pubkey_from_bytes` + `falcon_verify`。C の `falcon_verify` は
公開鍵のバイト列を受け取るので、展開込みでないと比較にならない）:

| | median ms |
|:---|---:|
| **Julia（この実装）** | **0.03441** |
| C `gcc -O2` | 0.03802 |
| C `gcc -O3` | 0.03124 |
| C `gcc -O3 -march=native` | 0.02773 |
| **C `clang -O3`（参照実装自身の Makefile）** | **0.02746** |
| C `clang -O3 -march=native` | 0.02664 |

**届かなかった。** `gcc -O2` にしか勝っていない。
参照実装が実際に配布されるビルドには **1.25 倍負けている**。
Julia は既定でホスト向けにネイティブコンパイルするので、
`-march=native` の C を相手にするのが公平であり、その意味でも負け。

**ただし 0.251 → 0.0344 ms、7.3 倍**。C 比は 6.5 倍差 → 1.25 倍差。

| 変更 | 効果 |
|:---|:---|
| 反復 in-place NTT（Dilithium と同じ順序）を乗算に使う | 0.176 → 0.021 ms |

## 「本来なら Julia は C と同じ速度が出るはずでは？」

**この表ではその問いに答えられない。** 表には三つの差が混ざっている ―
**言語の差**、**アルゴリズムの差**（我々は `BigInt` の降下と O(n²) の畳み込み、
C は RNS と in-place NTT）、**メモリ規律の差**（C は呼び出し側の
スクラッチ 1 個に書き込み、我々は関数ごとに新しい配列を返す）。
後ろ 2 つは仕様どおりに読めるコードを優先して**意図的に**選んだもので、
言語とは関係がない。

言語の差だけを取り出すために、`polymulq`（学校算法）を C に逐語訳して
比べた（`scripts/langcmp/`）:

| n | Julia | C (clang -O3 -march=native) | 比 |
|---:|---:|---:|---:|
| 128 | 0.0100 ms | 0.0152 ms | **Julia 1.52x 速い** |
| 512 | 0.1563 | 0.2177 | **1.39x** |
| 1024 | 0.6218 | 0.8690 | **1.40x** |

**同じアルゴリズムなら Julia は C と同等以上。** checksum も一致。
したがって上の 16〜35 倍は**言語の差ではない**。
残りはアルゴリズムとメモリ規律であり、**それは変えられる** ―
#036 は値を 1 bit も変えずに鍵生成を 42 倍にした。

（一般化はしないこと。測ったのは 1 つのカーネルで、
自動ベクトル化しやすい形をしている。言えるのは
「この形のコードで Julia が言語として不利ではない」まで。）

動くので、CI に入れれば必ず偽陽性を出す。
