Abstract

FALCON — standardized by NIST as FN-DSA — is the only selected signature whose output is a function of floating-point arithmetic, and its specification's precision analysis is about the sampled distribution, not about whether two conforming implementations produce the same bytes. We wrote an independent implementation in Julia, from the specification, and reconciled it with the C reference until it reproduces the reference's signatures byte for byte. That reconciliation exposes three classes of place where the specification does not determine the intermediate values: how an operation is spelled, a constant that cannot be derived from the published parameters, and a smoothing parameter that is used but not printed.

Two spellings — complex division and the D11 entry of LDL* — change the signature at ≈ 7.5×10⁻⁶ per signature, always at the last two sampler calls: the positions where ePrint 2024/1709 (Lin–Tibouchi–Yu–Zhang, EUROCRYPT 2025) turns a single discrepant pair into full key recovery. Unlike the perturbations that paper studies, these are differences between the specification and the reference, present in both of the reference's signing modes, and not removed by its countermeasure. We reproduce that paper's mechanism independently and check its Heuristic 1 directly, which it does not.

Two further results concern the sampler calls that paper sets aside. The centre of the first two calls is exactly (c·f)[n/2−1] / q — a public linear form in the secret — so an integer centre there is one equation on the key over F_q; from n−1 such events, with no signature difference vectors and no lattice reduction, Gaussian elimination returns the private key, which we run. And the oracle such a channel needs exists inside a two-sided window on the perturbation size whose ends we measure. Our own respellings fall below that window. One optimization flag falls inside it: compiled with clang -ffp-contract=fast, the C reference disagrees with itself on 12 of 100 000 signatures, and 8 of those 12 pairs yield the private key — and every recovered key signs a fresh message that the victim's public key accepts. Universal forgery, at ≈ 1.3×10⁴ messages. Nine ordinary build configurations — two compilers, native against emulated floating point, the reference's own hand-vectorised AVX2 path — are byte-identical, so the hazard is one flag, not build variation in general; and contracting the vector path instead of the scalar one yields a third mutually inconsistent stream.

01 — The question

Does the specification determine the signature?

FALCON computes its output through floating-point arithmetic: its Gaussian sampler runs a fast-Fourier nearest-plane recursion over Complex{Float64}, and the sampled integers — and therefore the signature — are a function of the exact floating-point values that recursion produces. ML-DSA (FIPS 204) and SLH-DSA (FIPS 205) are integer- and hash-based; given the same key, message, and randomness they return the same bytes on any conforming implementation, by construction. FALCON carries no such guarantee, and its specification does not intend to: §2.5.2 analyzes floating-point precision through a Rényi-divergence argument about the sampled distribution, and §4.1 treats C's double as only needing to "match at least" IEEE-754. Both statements are about the distribution, not about whether two implementations agree bit for bit.

That distinction is now load-bearing. The FIPS 206 status update (Perlner, NIST, Sept 2025) indicates the standard will fix the order of floating-point operations, forbid fused multiply-add, and require implementations to match known-answer tests bit for bit. If the standard requires bit-exact agreement, then "does the specification determine the intermediate values?" becomes a normative question. We answer it by building a second implementation and measuring exactly where it disagrees with the reference.

Why Julia — honestly

We chose Julia because we expected it to be fast: native arrays and a reputation for numerical performance suggested the matrix-heavy parts (FFT, NTT, Gram matrix) would be quick to write and quick to run. That was only partly borne out (§6). There is a second reason that is genuine but was recognized only afterward, and we state it as such. FALCON's security-relevant timing variability has two sources — algorithmic (the rejection sampler's data-dependent loop) and implementational (GC, JIT, bounds checks, dispatch). A garbage-collected, JIT-compiled language makes the second impossible to close — which makes it a clean instrument for studying specification-level variance undisguised by implementation-level variance. A language that cannot hide its own runtime variance is exactly the one in which the specification's variance shows up plainly. We did not pick Julia for that reason, but it is why the choice turned out to fit this question.

02 — Underdetermination

Three places the specification leaves open

Reconciling our implementation with the reference, stage by stage on raw 64-bit patterns, splits the floating-point path into three groups: primitives that agree with no change (the FFT family and the whole B0 matrix, 5120/5120 doubles), three computations that agree only once spelled the reference's way, and one constant stored under a different convention. The three spellings are algebraically identical and round differently. Here are the two implementation patterns for the first two, as running code.

(a) Complex division

The specification gives no formula; a reader uses the language's complex division — Smith's algorithm, in both Julia and Python. The reference forms the reciprocal explicitly. Smith's is the numerically better choice; the reference's is the one the KATs encode.

Pattern S — spec reader (Julia's /)# Smith's algorithm; numerically better
ComplexF64[ f[i] / g[i]
            for i in eachindex(f) ]
Pattern C — reference (FPC_DIV)br = real(b); bi = imag(b)
m  = 1.0 / (br*br + bi*bi)
br *= m; bi *= -m
ComplexF64(ar*br - ai*bi,
           ar*bi + ai*br)

(b) The D11 entry of LDL*

Algorithm 8 and the Python reference compute D11 with three multiplications; the C reference keeps the quotient the other way round and folds, doing one. Equal because G00 is Hermitian, hence real.

Pattern S — Algorithm 8 / Python# three multiplications
L10 = div_fft(G[2,1], G[1,1])
D11 = sub_fft(G[2,2],
        mul_fft(mul_fft(L10,
          adj_fft(L10)), G[1,1]))
Pattern C — Zf(poly_LDL_fft)# one multiplication
G01 = adj_fft(G[2,1])
mu  = div_fft(G01, G[1,1])
L10 = adj_fft(mu)
D11 = sub_fft(G[2,2],
        mul_fft(mu, G[2,1]))

The third spelling (c) is the reference's hand-unrolled bottom two levels of ffSampling, folding the split/merge twiddles into 1/√2 and 1/√8. All three are switched independently by with_spec_spelling(f; cdiv, ldl, ffsampling), defaulting to the reference's spelling — and that independence is the whole point: it lets us attribute a divergence to one formula. Two more classes are constants: (II) fpr_inv_sigma is not the correctly rounded reciprocal of the published σ (§5), and (III) σ_min uses a smoothing parameter ε that the text never prints.

"At the key-recovery position" is a claim about consequences; we discharge it rather than cite it. Taking the A2 pair at key 70, sig 534 — two signatures on the same syndrome differing only in the last two sampler outputs — the difference is Δs0 = Δz0·g, Δs1 = −Δz0·f with Δz0 = a + b·x^{n/2}, and since (a+bx^{n/2})⁻¹ = (a−bx^{n/2})/(a²+b²) recovery is a search over (a,b) ∈ {−19..19}² — no ring inversion. The recovered (f, g) is the stored key up to the negation symmetry (f,g) ↦ (−f,−g) — the same signing key. So complex division and D11 suffice not merely to change the signature but to expose the key, in the derandomized settings where a syndrome is signed twice. The recovery algebra is regression-tested (test_falcon.jl).

Why the last two calls dominate — an open question, answered

2024/1709 §6.1 reports, and says it does "not fully understand," that conditional on an integer centre the last two calls diverge more readily than the first two (for the sign_dyn/sign_tree difference, not FMA). We measured the perturbation |Δμ| the respelling puts on the centre at every position — and it accumulates along the tree descent, with a sharp step at the midpoint:

# scripts/position_profile.jl  (mean |Δμ| per position block)
pos    0.. 511  (z1, first descent) : 2.7e-15 → 1.0e-14
pos  512..1023  (z0, second descent): 7.4e-14 → 8.7e-14   # ~7× step
first two (0,1)     : 2.7e-15
last two (1022,1023): 8.6e-14        ratio ≈ 32×

The step is structural: ffSampling samples z1 first, then forms t0 ← t0 + (t1 − z1)·l10 and samples z0. Every centre in z0 — the second half, including the last two calls — passes through the top-level l10 correction that carries the rounding difference; the first-half centres do not. A centre crosses an integer only when |Δμ| exceeds its distance to one, so 32× larger |Δμ| means ~32× more divergence at the last two — the asymmetry, explained. And for A2 (tree-only) the first-two |Δμ| is exactly zero (the first leaf's centre is a pure target split, reached before any l10), so A2 divergences are confined to the last two structurally. The sensitive set is not fixed — it depends on where the perturbation enters.

04 — The other channel

The calls everyone set aside

ePrint 2024/1709 §5 dismisses a divergence at the first two sampler calls in one paragraph: the resulting difference vector "is a short lattice vector, but it is not expected to be short enough to make key recovery feasible." That is a claim about the difference vector. There is a channel at those positions that never reads it.

In sample_preimage the second target component is t1 = (−ĉ·b)/q with b = −f, so as a ring element t1 = (c·f)/q exactly, where c is the public hashed message. Checked against exact Int128 negacyclic arithmetic, the first two sampler centres are coefficients of that quotient, at fixed indices, to floating-point error alone. So an integer centre at call 1 is precisely

(c·f)[n/2−1] ≡ 0  (mod q)

— one F_q-linear equation on the secret, with coefficients the adversary computes from the public message. The leak is carried by the occurrence of the event, not by the value of anything. We ran the solve:

# scripts/event_solve.jl
collected 511 events from 5823368 syndromes (rate 8.77e-05, predicted 1/q = 8.14e-05)
system rank 511 of 512 unknowns
recovered vector: max |.| = 16   (true f has max |.| = 16)

n−1 events give a rank-511 system whose kernel is one-dimensional; scanning the q−1 scalar multiples and keeping the shortest returns f itself. One 512×512 Gaussian elimination, 49 seconds — no lattice reduction, no difference vectors. On real hash_to_point syndromes rather than uniform ones (event_attack.jl) the same pipeline collects 511 events from 3.1M messages, recovers f, and forges a message the victim's key accepts — the one idealisation left is which of the two first calls straddled. Two assumptions did not survive it: that shortness of Δs was the relevant question, and that lifting f mod q to f needs a lattice.

Blind, without the which-call label

The oracle flags a first-two divergence but not which of call 1 / call 2 straddled — a one-of-two disjunction. No public statistic separates them (a trained classifier on the two signatures is at chance, 0.50–0.60), and naive iterative labelling does not converge. But the two candidate rows are related, b = x^{n/2} a, so the disjunction becomes (a·f)(a·f′) = 0 with f′ = −x^{n/2}f — a linear measurement on a rank-2 symmetric matrix S = sym(f f′ᵀ). About n(n+1)/2 events pin S; its column space is exactly span{f, f′}, and f is the short vector in it. blind_solve.jl recovers f with no labels (8/8 at n = 16, 32). So the blind channel is not impossible — it costs O(n²) events against the labelled O(n), an n-fold overhead. A one-bit fault oracle ("the two computations disagreed") is enough.

The oracle it needs is a window, and both ends are measurable

Such a channel needs something that tells the adversary which messages produced an event. A difference between two implementations does that exactly when its perturbation on the centre is neither too small nor too large.

Too small is the interesting bound, and it is not about anyone's precision. At an event the true centre is an exact integer m, but both implementations compute m + η with the same accumulated error — the FFT, the tree and the descent are common to them. floor disagrees only if the difference flips the sign of η. Over 200 manufactured events, |η| has median 2.8×10⁻¹⁴, and the straddle probability under an injected perturbation δ turns over exactly there:

δ010⁻¹⁶10⁻¹⁵10⁻¹⁴10⁻¹³10⁻¹²10⁻¹¹10⁻⁸

Too large is the interior false-positive rate: the same perturbation straddles the ≈ 2n generic centres at rate κδ with κ = 1.62×10³, and the solve tolerates a false fraction of about 1/n. The two bounds give a window 2.8×10⁻¹⁴ … 4.9×10⁻¹¹ — 3.2 decades wide.

Where our own findings sit

Below it. The respellings of §02 perturb the first two centres by 2.7×10⁻¹⁵ (arm A1) and by exactly zero (arm A2). An earlier experiment that manufactured ten integer centres and saw zero straddles was not unlucky; it was an order of magnitude under a threshold we can now name.

05 — The reference against itself

One optimization flag, and the key

C99 6.5p8 lets a compiler contract a*b + c into a single fused multiply-add with one rounding instead of two, under FP_CONTRACT. The FALCON reference sets neither the pragma nor a flag, and the specification does not mention contraction. So we stopped modelling and built the reference itself — three ways, same source, same key, same messages, same PRNG tape.

All three generate the identical private key from the identical seed — key generation runs the FFT too, so that had to be checked rather than assumed. Handing every divergent pair to the recovery of 2024/1709 §5.1, which sees only the two signatures, the public key and the message:

Eight of twelve — and all eight forge. Each recovered pair is an exact NTRU symmetry ±x^k(f,g) of the stored key with ‖(g,−f)‖² = 16676 ≤ 1.17²q = 16822. The public-key relation says the pair is an NTRU pair for h; the norm bound says it is short enough; neither says the sampler will run on it. So we used it: for each recovered (f,g) the script completes the trapdoor basis by solving fG − gF = q — the same descent key generation runs, needing nothing the attacker lacks — signs a message the victim never signed, and offers it to the victim's public key. Eight of eight are accepted. That is universal forgery from two signatures. And the rate gives the cost: a key-yielding divergence occurs on 8 of 100 000 messages, so an adversary who can obtain both builds' signatures on the same messages needs on the order of 1.3×10⁴ messages, then one 40×40 search. The other four are the channel of §04: their Δz is not 2-sparse, which the failed exact division proves, and no interior integer centre was found in 1.02×10⁸ draws. The two coefficient counts separate cleanly, so an adversary can tell the channels apart. The 4/12 split is close to the 30/70 of that paper's Table 2, from a completely different perturbation source. It replicates at FALCON-1024: 6 of 60 000. And it is not an x86 artefact: re-run on aarch64 with a cross toolchain and qemu-user, the real fft.c contracts on exactly the same flags (gcc never; clang only at -ffp-contract=fast/-Ofast/-ffast-math) — FMA being base-ISA there did not make the default build contract, the fpr wrapper blocks it on aarch64 too — and under emulation the contracting build diverges on 19 of 150 000 (1.27×10⁻⁴), first twelve messages identical to x86, pairs recovering the key and forging. The hazard is architecture-independent.

The reference ships the switch itself, and under-rates it. Beyond the compiler flag, the AVX2 path has a documented build option, FALCON_FMA, that emits a real _mm256_fmadd_pd. The reference's config.h rates its risk in its own words: signatures "might theoretically change, but only with low probability, less than 2⁻⁴⁰; produced signatures are still safe and interoperable." Built both ways on AVX2+FMA hardware and signed 274 944 times under one key, the signatures differ on 30 — a rate of 2⁻¹³·², about 2²⁷ higher than the reference's own estimate, and the divergent pairs recover the key and forge. "Safe and interoperable" holds for one signature; it fails when both builds' signatures on a message are seen together, because their difference is the key. This is the paper's thesis, stated and dismissed in the reference's own configuration file.

Is anyone actually exposed today?

No — and that is the argument for acting now. A survey of the deployed ecosystem found no shipped Falcon build that contracts on an FMA-capable target: liboqs and PQClean use integer emulation or hand-written two-rounding AVX2 intrinsics, Bouncy Castle is Java, and OpenSSL 3.5, AWS-LC, Botan, CIRCL and Go do not ship Falcon at all. The threat is latent, held off entirely by the reference's emulation default, its intrinsics, its fpr wrapper and a security warning — none of which is in the specification. FIPS 206's push toward native-FP, bit-exact implementations is exactly the pressure that turns a latent hazard into a shipped one, so the prohibition belongs in the standard before that happens.

The negative control is most of the value

A result that says "builds of the reference differ" would be alarming and useless if ordinary build choices differed too — one could not say which difference mattered. They do not. Over 30 000 signatures each:

(The AVX2 builds really do contain the vector path: 599 ymm instructions under GCC, 4321 under clang.) That the emulated build matches the native one is worth its own line: the reference's config.h recommends emulation because native FPUs "may yield slight discrepancies that could affect determinism", and here they do not. The whole divergence is one flag — which -Ofast and -ffast-math both imply.

Two details sharpen it. GCC does not contract the AVX2 intrinsics either, even when asked — -ffp-contract=fast emits zero fma instructions there — so its default and contracted builds of the vector path are the same program. Clang does contract them, and the result is a third stream, distinct from both the default and from clang's contracted scalar build: over 30 000 signatures the two contracted builds each diverge from the default on five messages, sharing four and each keeping one of its own. This is not "the reference and a broken build". It is three mutually inconsistent conforming builds, and which messages leak depends on which code path the compiler happened to contract.

What is standing between FN-DSA and this today

An accident. The native build wraps double in typedef struct { double v; } fpr;, and fpr.h gives the reason: so the compiler complains if raw arithmetic operators are used on the type. It has a second effect nobody recorded — GCC will not contract through the wrapper at any setting we could find, and clang will only at -ffp-contract=fast. A type-safety idiom is currently doing cryptographic work, in a header, under a comment about something else. We had claimed, one revision earlier, that GCC and clang defaults diverge; building it showed that was wrong, and the corrected claim — one flag, not two compilers — is both narrower and sharper.

What is new, and what is not

The one new empirical fact is A2. Its significance is not a new mechanism — it is Lemma 1 — but a different source. The paper's two sources both live inside the reference: FMA is a build flag, and sign_dyn/sign_tree are two entry points their §7.2 countermeasure reconciles. Complex division and D11 differ between the specification and the reference, so they sit in both signing modes and survive that countermeasure. For a standard that intends bit-exact KATs, this is the difference between "the two implementations should be made to agree" and "the text must say which of two equal formulas to use."

We were wrong first, three times An earlier framing claimed specification underdetermination alone suffices, "no different build needed" — a rediscovery of §6.1, because a single flag we had not read carefully was moving only Class I(c). And a still-earlier claim, "these differences never reach the signature," rested on 480 signatures, which cannot distinguish 10⁻⁵ from zero. Reading the paper, then separating the three spellings and measuring at scale, is what produced the correct and narrower claim.

ePrint 2024/1709 measures the consequence of Heuristic 1 (its Tables 2, 4) and notes it cannot be made a theorem. We measure the cause — how often each call's centre is within 10⁻⁹ of an integer — in an implementation written from the specification, not derived from theirs.

07 — Break & fix

Half a countermeasure protects nothing — and a simpler alternative

ePrint 2024/1709 §7.1 proposes the structural fix in two parts: (1) replace SamplerZ with a rounding sampler (Algorithm 4), moving the instability from integers to half-integers; and (2) force ‖(g,−f)‖² odd, which makes half-integer centres impossible. We implemented it. The χ² test over 200k samples at five (μ,σ) pairs gives χ²/df of 0.72–1.02, so Algorithm 4 is distributionally sound — an independent confirmation.

The asymmetry The reference key generator never produces an odd ‖(g,−f)‖², because it forces the coefficient sums of both f and g odd, so their sum is even. Part 2 is nonetheless deployable — relaxing one parity gives odd norms 40 of 40 (we measured it) — but it is a second change, and an implementer who touches only the sampler makes only the first. And a centre n/g is a half-integer only when g is even. At the first two calls g = q = 12289 is odd → rounding immunises them completely. At the last two g = ‖(g,−f)‖² is even → rounding immunises nothing. And the first two are the harmless positions; the last two are full key recovery.

So we ran the whole attack with part 1 deployed. Over 160,000 signatures on reference keys: 29 near-half-integer centres, 3 divergent pairs, and 3 of 3 private keys recovered — each verified as exactly the stored key up to the NTRU lattice's symmetries. Disclosure: the perturbation source here is arm A1, which the paper's other countermeasure (§7.2, aligning the two signing modes) removes; our own A2 arm survives that but is too rare to have been observed under the rounding sampler. The experiment establishes the mechanism, not a break of the countermeasure as a whole.

The full countermeasure is sound and deployable — with t odd, m₂ and m₃ are odd too and half-integer centres cannot occur anywhere. The normative point is that its two parts are not independently useful: a standard adopting the rounding sampler must mandate the key-generation parity change in the same clause and say that neither part alone suffices.

The replacement: snap the centre to its exact rational

At the sensitive positions the exact centre is n/g and the signer already knows g. The FP centre approximates it to ~10⁻¹³, so g·μ̂ lands within ~1.6×10⁻⁹ of the integer n — seven orders of margin against the 0.5 that would break it (measured max residual: 1.4×10⁻⁹ and 2.4×10⁻⁸ over 100k samples each). So n = round(g·μ̂) is exact, and s = fld(n, g) is pure integer arithmetic.

Reading the ratios from the Julia −O2 row:

  • Verification is the fastest measured, C included — 0.015 ms vs the best C build's 0.0165 (≈1.1×) and gcc −O2's 0.026 (≈1.6×), and 235× faster than Python. Verification is NTT-heavy integer work with no sampler and no big integers — where Julia's arrays and LLVM are at their best.
  • Signing ≈1.8× faster than the emulated C build (the one most deployed FALCON runs), 20× faster than Python, and ≈6× slower than native-FP C — the floating-point sampler is where C's SSE2 doubles win.
  • Key generation ≈9.78 ms — faster than every emulated C build and 272× faster than Python, but ≈1.9× slower than native C. Its big integers live in BigInt against the reference's 31-bit-limb RNS.

At n=1024 the pattern sharpens: verification is again the fastest measured (0.031 ms vs best C 0.035, 245× Python), signing is ≈1.7× faster than emulated C and 18.8× faster than Python, and key generation is 296× faster than Python but now ≈1.3× slower than even emulated C — the BigInt-vs-RNS gap widens with degree. Notably, Julia −O2 wins at 512 and −O3 wins at 1024: the best level is per-operation, and reporting one level would misrepresent the implementation. Key generation is also the endpoint of a long optimization — 9610 ms in the first working version — reached almost entirely by removing allocation, not by high-level array rewriting.

09 — Scope & limits

Constant time, and what we can't yet say

This implementation is not constant-time and does not try to be. Where the code does something a constant-time implementation could not, a CONSTANT TIME: comment marks it. A Julia implementation cannot close the implementation-level channels (GC, JIT, bounds checks, dispatch) at all — which is precisely why it is a clean instrument for the specification-level question here, and a poor vehicle for a deployable signer. We state this rather than claim a side-channel contribution we did not make.

Open, and marked as such:

  • A2a / A2b are not separated — complex division alone and D11 alone each gave 0/100k; separating a ≈3.75×10⁻⁶ single-arm rate from zero would take millions of signatures. We can say the two together reach the signature, not which one.
  • A2 and A1 rates are not distinguished — factor 2.5 apart but p ≈ 0.23 over 925k pooled signatures; reported as comparable, not ordered.
  • The asymmetry ePrint 2024/1709 leaves unexplained we give a mechanism for, not a calibrated model: three estimates of the ratio span a factor of ten and we have not reconciled them.
  • The event channel's two halves are measured, their composition is arithmetic. §04 runs the solve and §05 exhibits an oracle, but not together: at 3.3×10⁻⁵ informative events per query, 511 rows is ≈1.5×10⁷ signature pairs, on the order of a day, which we did not spend. §04 also draws syndromes uniformly rather than hashing messages.
  • The contraction result is one compiler pair on one machine. We did not test aarch64 — where FMA is in the base ISA — nor MSVC, nor other compiler versions. That the fpr wrapper blocks contraction may be robust or an artefact of these two versions; only a wider survey would say.
  • Verification speed beats the fastest C build by ≈10%, which is inside the spread that build options alone produce. The defensible claim is "competitive with C", not a ranking.
  • FALCON-1024 is measured at lower volume for the respellings (350k, one event); the contraction result does replicate there (6 of 60k).
10 — Recommendations

What FIPS 206 should do

If FIPS 206 requires bit-exact KAT agreement:

  1. Say that FP_CONTRACT must be off, normatively. This is the one we would put first. §05 is what it costs otherwise: 12 divergent signatures in 100 000 and 8 private keys, from one flag that -Ofast and -ffast-math both imply. The reference is protected today by an undocumented side effect of a type-safety idiom, and an accident is not a specification.
  2. Say that a fix at the last two positions alone is not a fix. §04 recovers the key from first-two events, so the reason 2024/1709 §5 gives for treating those calls as harmless does not hold, and any countermeasure justified in those terms needs a different justification.
  3. Say whether the floating-point environment is in scope. A signer conforming in every respect except the ambient IEEE-754 rounding direction emits signatures that fail verification — 0 of 200 valid under FE_UPWARD and FE_DOWNWARD — while still satisfying the norm bound. That is a correctness requirement, and no current text states it.
  4. Pin the spellings of complex division, D11, and the bottom-level ffSampling block — or, better, adopt ePrint 2024/1709 §7.1's structural fix (sample the centre with round not floor, and require ‖(g,−f)‖² odd), which removes the sensitivity itself. Mandate both parts in the same clause: with round, the first two calls are closed unconditionally because q is odd, while the last two — the cheapest key-recovery positions — are left exactly as exposed as before. Adopting it also requires relaxing the reference's key-generation parity condition, which currently forces ‖(g,−f)‖² even.
  5. Publish fpr_inv_sigma at full precision rather than leaving it to be derived from a rounded σ, and say whether intermediate values are within KAT scope.
  6. State σ_min's ε, or its derivation.
  7. State the SamplerZ byte-assembly convention alongside the vectors.
