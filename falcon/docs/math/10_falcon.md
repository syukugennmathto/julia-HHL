# モジュール 10: 結線 ― そして「何が固定できるか」の決着

## 10.1 方式を 1 ページで

FALCON は NTRU 格子上の hash-and-sign である。

- **公開鍵**は多項式 1 個、`h = g/f mod q`。
  これが定める格子は `{ (s1, s2) : s1 + s2·h ≡ 0 (mod q) }`。
- **署名**は、`c = HashToPoint(salt ‖ message)` に対して

  ```
  s1 + s2·h ≡ c (mod q),      ‖(s1, s2)‖² ≤ β²
  ```

  を満たす**短い**対 `(s1, s2)`。送るのは `s2` だけで、
  検証者は `s1 = c − s2·h` を計算し直す。
- 合同式を満たすだけなら誰でもできる（`s2 = 0`, `s1 = c` とすればよい）。
  **難しいのは短い解**で、そこに秘密の短い基底が要る。

したがって**検証は自明な演算**（NTT の積 1 回、引き算、ノルム）であり、
**署名はモジュール 6〜8 のすべて**である。

## 10.2 署名の代数 ― `h` が一度も出てこない

`sample_preimage` は 3 行に見えるが、中身はこうだ。

目標点 `(c, 0)` を基底の座標で表すと `(c, 0)·B0⁻¹`。
`det(B0) = q` と NTRU の形のおかげで逆行列は閉じた形で書けるので、
行列を解く必要がなく、

```
t0 = c·d/q,    t1 = −c·b/q        （B0 = [a b; c d]）
```

で済む。`ffSampling` が `(t0, t1)` を近くの**整数**ベクトル `z` に丸め、
`v = z·B0` が格子点になる。署名は残差 `s = (c, 0) − v`。

ここで注目すべきは、**合同式 `s1 + s2·h ≡ c` を誰も強制していない**ことである。
`v` は格子の元で、格子上ではこの式が消える。だから合同式は**継承される**。
**署名の計算に `h` は一度も現れない。**

## 10.3 やり直しループ ― 条件は 2 つ、salt は変えない

署名は次のどちらかで再試行する。

1. **`‖(s1, s2)‖² > β²`。** サンプラは Gaussian なので、
   たまに長いベクトルが出る。捨てるしかない。
2. **圧縮した `s2` が入らない。** Golomb-Rice は可変長で
   フォーマットは固定長（モジュール 9）。実際に起こる。

**そして salt は変えない。** C も Python も、
salt は 1 回だけ引いてループの外に置き、
やり直すのは**サンプリングの乱数だけ**である
（C は `falcon_sign_start` で nonce を 1 回引き、
ループ内で同じ 40 バイトを `memcpy` している）。

意味が違う。salt を変えれば `c` が変わり、**別の問題例**を解くことになる。
変えなければ、**1 つの問題例に対してサンプラを振り直している**。

（この点は最初 encoding.jl のコメントに「fresh salt で」と書いてしまい、
C のループを読んで訂正した。#029。）

## 10.4 何が固定でき、何が固定できないか ― 決着

このプロジェクトの最後の判断がここにある。

| | C 参照実装と厳密一致するか | 理由 |
|:---|:---|:---|
| 鍵・署名のエンコード | **する** | 整数演算のみ |
| **検証** | **する** | 整数演算のみ（NTT とノルム） |
| **署名の生成** | **しない** | 浮動小数点。根の表の 1 ulp で変わる（#025） |

だから目標を「C の署名バイトを再現する」に置くのは**間違い**である。
正しい目標は「**C の署名を検証できる**」で、これは達成した。

C 参照実装が固定シードから生成した本物の FALCON-512 の鍵・メッセージ・署名
（`test/vectors/cref_kat.jl`）に対して、我々の `falcon_verify` は
**受理する**。`‖(s1,s2)‖² = 26536387 ≤ β² = 34034726`。

これは移植版どうしの一致ではなく、**規範的実装との本物の相互運用**である。

### 署名側は性質で守る

再現できない代わりに、性質で守る。

- 自分で署名して自分で検証できる（往復）
- **C の秘密鍵で署名して、C の公開鍵で検証できる**
  （バイトは違うが、有効な署名である）
- ノルムが `β²` 以下、かつ理論値 `2n·σ² = 2.81e7` の付近
- 同じメッセージの署名が毎回違う（乱択されている）
- 改竄（メッセージ・salt・本体・鍵）が拒否される
- **敵対的な入力で例外を投げない**（#027 の教訓）

## 10.5 `set_fpu_cw(2)` ― C はもう一段構えている

C 参照実装の `falcon.c` は、署名の呼び出しをこう囲んでいる。

```c
oldcw = set_fpu_cw(2);
Zf(sign_dyn)(...);
set_fpu_cw(oldcw);
```

x87 の制御ワードを倍精度に固定している。
つまり C は

1. 浮動小数点を**整数演算でエミュレート**し（`FALCON_FPEMU`、#012）
2. その上で FPU の**制御ワードまで固定**している

という二重の備えをしている。
どちらもモジュール 8 で実測した「1 ulp で署名が変わる」（#025）への対策である。

**この 2 行が、この本の主題の要約になっている。**
他の 3 方式（ML-DSA / SLH-DSA / HQC）の参照実装に、
FPU の制御ワードを触る行は 1 行も無い。

## 10.6 Dilithium との対比（最終）

| | Dilithium (ML-DSA) | FALCON (FN-DSA) |
|:---|:---|:---|
| 署名の骨格 | Fiat–Shamir + 棄却 | hash-and-sign + Gaussian サンプリング |
| 鍵生成 | `t = A·s1 + s2` | **NTRU 方程式を解く**（塔を 9 段降りる） |
| 事前計算 | 無し | **ffLDL 木**（葉 n 個） |
| 浮動小数点 | 無し | **必須、かつ補正が効かない場所がある** |
| 検証 | 整数のみ | 整数のみ（**ここだけは同じ**） |
| 署名長 | 2420 B | 666 B |
| 実装の再現性 | 自明 | **定数表の最下位ビットに依存** |

Dilithium 移植のとき、浮動小数点のことを一度も考えずに済んだ。
FALCON では、モジュール 5 で「なぜ float が要るのか」を書き、
6 で「補正があるから安全な場所」を測り、
7 で「補正が無い場所」を特定し、
8 で「1 ulp で署名が変わる」ことを実測し、
10 で「だから署名は再現できないが検証は相互運用できる」に着地した。

**これが「FALCON だけ FIPS 化が遅れた理由」の、実装からの答えである。**
仕様が難しいのではない。
**「誰が実装しても同じ答えになる」ように書き下すのが難しい**のであって、
その難しさは浮動小数点の最下位ビットに宿っている。
