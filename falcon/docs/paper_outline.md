## 選ぶ主張（2026-08-21、**測定により二度改訂 ― 三度目を保留中**）

> **仕様書が中間値を決めていないという事実だけで、
> ePrint 2024/1709 が危険だと示した発散が起きる。
> 違うビルドは要らない ― 仕様書に忠実な 2 つの実装で足りる。**

### 改訂の経緯（両方とも測定による）

**初版**: 「独立実装が参照実装の署名をビット単位で再現できる」。
→ 関連研究調査で、著者自身の C/Rust/Go が既に相互運用を前提としており、
**最も再発見の危険が高い**と判定。

**二版**: 「仕様書の不決定性は署名まで届かない」。
→ **測って反証した**（#054）。480 署名で 0 件だったのを「届かない」と読んだが、
2024/1709 の率は 1e-4 であり、**480 本では 1e-4 と 0 を区別できない**。
10 万本で測ると **5 件**出た。

**現行**: 上記。**反証されたことで主張は強くなった。**
「届かない」は弱い否定的主張だったが、
「仕様書の不決定性だけで既知の危険な発散が起きる」は標準化に直接効く。

### 測定（`scripts/divergence_rate.jl`、n=512、10 万署名）

| | 摂動する量 | 木の葉 | 署名の食い違い | 率 |
|:---|:---|---:|---:|---:|
| **A** 演算の書き方（複素除算・`D11`・ffSampling 最下段） | **中心 μ** | ― | **5 / 100,000** | **5e-5** |
| **B** 定数 `fpr_inv_sigma` 対 `1/σ` | **幅 σ** | **444.6 / 512** | **0 / 100,000** | < 3e-5 |

食い違うとき、1 署名あたり約 **470 / 512 係数**が違う
（バイト消費がずれて PRNG が同期を失う）。

### 機構（`scripts/first_divergence.jl`）

**5 件すべてが整数近傍の中心での `floor` のまたぎ**で、
**すべて call 1023 または 1024（1024 中）** ―
すなわち **2n−2 と 2n−1**、2024/1709 が予測する 4 箇所のうちの 2 つ。

    call 1023   mu = 221.00000000000006   vs   220.99999999999997   z 223 / 222
    call 1024   mu = 436.99999999999994   vs   437.00000000000011   z 437 / 438
    call 1024   mu = 444.0                vs   443.99999999999977   z 444 / 443
    call 1023   mu = -180.99999999999997  vs  -181.0000000000002    z -179 / -180
    call 1023   mu =  60.000000000000007  vs   59.999999999999957   z  60 /  59

中心は 1024 回中 **76.2%** が最下位ビットで食い違う（|Δμ| 中央値 5.3e-14）。
そのうち整数の 1e-13 以内に落ちたものだけが反転する。

**A と B が分かれる理由も機構から出る**:

- A は**中心**を摂動する。中心は `s = floor(mu)` を通る。**不連続。**
- B は**幅**を摂動する。幅は `dss`, `ccs` を通って `berexp` の比較に入る。**連続。**

> **境界は「差の大きさ」ではなく「差がどの量に届くか」。
> 中心は floor を通り、幅は通らない。**

## 構成案

### 1. Introduction

- FALCON / FN-DSA は署名が**浮動小数点の関数**である唯一の NIST 署名標準。
  FIPS 204（ML-DSA）は "No Floating-Point Arithmetic" を明示的な節に持ち、
  同一入力・同一乱数なら同一出力が保証される。**FALCON にはその保証がない。**
- FIPS 206 は演算順序を規定し FMA を禁じ、署名が KAT にビット一致することを
  要求する方向である（Perlner, NIST, 2025-09）。
  **ならば「仕様書は中間値を決定しているか」は規範上の問いである。**
- 動機（正直に）: 我々は速度を期待して Julia を選んだ。
  期待は部分的にしか当たらなかった（`docs/why_julia.md`）が、
  **別言語で書いたことが仕様書と参照実装の差を可視化した。**
  同じ言語で書き直していたら「同じコードだから同じ」で終わっていた。
- 貢献:
  1. 仕様書が中間値を決定していない箇所を **3 クラス**同定する
     （演算の書き方・定数そのもの・導出の欠落）
  2. それぞれについて、**実装が違えば何が変わり、署名は変わらない**ことを
     厳密な bit 比較と大標本で測る
  3. ePrint 2024/1709 が示した「伝播する差」との**境界**を与える
  4. 参照実装から独立に書かれた実装が、参照実装の署名を
     ビット単位で再現することを示す（上記を測るための実験装置）

### 3. Methodology

ここは**弱点ではなく強み**として書く。本リポジトリの記録は
計測器の失敗を 6 回含んでおり、そのすべてが対照によって検出された。

- 比較は**生の 64 bit パターン**で行う。「1e-12 で一致」は
  `samplerz` が中心を丸める以上、何も言っていない。
- 変更の効果は**変更を戻して**測る（#043、#044、#050）。
- 計測器には**陽性・陰性の対照**を常設し、雑音床を実測する（#051）。
- C は**ビルドの集合**として測る（#052）。
- Julia は**run 間の幅**を出す。

### 4. Bit-exact reproduction

- 実験装置: 参照実装を共有ライブラリにし、`prng` の 56 バイト状態を
  直接与える shim（`scripts/cref_shim.c`）。
  **これが本当の障害だった** ― 参照実装の公開 API は
  サンプラの ChaCha20 を内部で SHAKE から導出するので、
  乱数を固定する手段がなかった。
- 段階的な突き合わせ（`scripts/cmp_cref_fp.jl`）:
  - 無改修で bit 一致: `fft` `ifft` `split_fft` `merge_fft`
    `add` `sub` `mul` `adj` `mul*adj` `mul*selfadj`、`B0` 行列
  - 書き方を合わせて一致: 複素除算、`LDL*` の `D11`、
    `ffSampling` の最下 2 段
  - 規約が違う: 木の葉（互いの逆数）、`fpr_inv_sigma`
- 結果: 展開秘密鍵 5120/5120、`s2` 25/25、圧縮バイト 25/25
- **注意**: 3 箇所を戻しても署名は再現する ―
  **ただしそれは「差が無い」ことではなく「率が 5e-5 である」ことを意味する**（#054）。
  §5 を参照。ここで「伝播しない」と結論したのが二版の誤りだった。

### 5. The constants: `fpr_inv_sigma` cannot be derived from the specification

`scripts/inv_sigma_audit.jl` が生データを出す。400 bit で計算し、
生のビットパターンで比較する。

参照実装は ffLDL 木の葉に `fpr_inv_sigma[logn]` を掛ける
（`ffLDL_binary_normalize`: "we actually store in the tree leaf the inverse of
the value mandated by the specification"）。この定数は:

| 導出 | logn=9 | logn=10 |
|:---|---:|---:|
| Table 3.3 の印字値（12 桁）の正しく丸めた逆数 | **+941 ulp** | **+18545 ulp** |
| Python 参照実装の Float64 σ の正しく丸めた逆数 | +1 ulp | +2 ulp |
| Float64 除算 `1.0/σ` | +1 ulp | +2 ulp |
| (2.13) を 400 bit で評価した σ の逆数 | +1 ulp | +1 ulp |
| (2.13) を Float64 で評価してから `1.0/` | +2 ulp | +1 ulp |

**構成できるどの導出とも一致せず、常に上方にずれる。**
さらに fpr.h の 35 桁十進リテラルは `1/σ` の 35 桁展開ではない ―
有効数字 16 桁ほどで分岐する。つまりこのリテラルは
高精度計算の出力ではなく、**ある Float64 を 35 桁で印字したもの**である。

**帰結**（ここを誇張しないこと）:

- Table 3.3 の σ から `1/σ` を計算する実装は、
  **展開秘密鍵が違う**（木の葉 512 個中 **444 個**が食い違う）。
- **署名は変わらない。** 同一鍵・同一メッセージ・同一 PRNG 状態で
  120 署名・61440 係数のうち **0 件**。
- したがって **署名 KAT には効かず、中間値 KAT・展開鍵形式には効く。**

**付随発見**: `inner.h:749` は `fpr_sigma_min[] 1/sigma_min` とコメントするが、
配列が保持するのは **σ_min そのもの**（1.2778…）である。
参照実装のヘッダコメント自体の誤り。

### 5b. `sigma_min` の ε は印字されていない

σ は (2.13) を `ε ≤ 1/√(Q_s·λ)`（`Q_s = 2^64`、`λ = 128/256`）で評価した値
（相対誤差 2e-16 で再現）。σ_min は Table 3.3 に**値しかない**。
Z の平滑化パラメータ

    η_ε(Z) = (1/π)·√( (1/2)·ln(2(1 + 1/ε)) )

を `ε = 1/√(2^64·n³)` で評価すると 3e-13 で再現する。
**(2.13) の ε とは別物**で、取り違えると 10〜11% ずれる。

> **注意**: (2.13) の対数の引数は `4n(1 + 1/ε)`（`Z^{2n}` の平滑化）、
> 上の η は `2(1 + 1/ε)`（`Z` の平滑化）。**別の式である。**
> 関連研究調査の回答はこの 2 つを混同して「(2.13) の記述が誤り」と
> 指摘してきたが、`test/test_spec.jl` が両方を数値で検証しており、
> 本稿の記述は正しい。査読でも同じ混同が起きうるので本文で明示すること。

### 5c. SamplerZ テストベクタの replay 規約

Table 3.2 の 16 本は、9 バイトを 72 bit 語に組む順序が本文に無い。
左から読むと 16 本中 4 本しか再現せず、チャンクを反転すると 16 本すべて再現する。
規約は参照実装のテストハーネス（`test.py` の `KAT_randbytes`）にしかない。

→ **FIPS 206 への含意**: 5 は定数を全精度で公表すべき、
   5b は ε を明記すべき、5c は KAT の規約を本文に書くべき。
   `docs/nist_comment_draft.md`。

### 6. Implementation notes（従属）

- 鍵生成 9610 → 11 ms。効いたのは全部**確保の除去**であって
  高水準の配列演算ではない。Karatsuba が schoolbook に n=2〜2048 で全敗。
- 性能は範囲比較で: `verify` 同着、`sign` は FPEMU 帯より速く native 帯に 7 倍負け、
  `keygen` は FPEMU 帯。

### 7. Timing leakage（付録）

- 脅威モデル（受理署名は公開／棄却候補は非公開）
- dudect + 対照 + 実測雑音床
- 見つけた最大の漏洩は**自分の実装の欠陥**であり参照実装には無い。
  一般化できる教訓は「漏れるのはデータ依存分岐があることではなく、
  分岐結果が一方のクラスで学習可能で他方で不能であること」。
- Julia では処理系と FPU 由来の変時間性を閉じられない、と明示。

### 8. Conclusion / Limitations

- 単一マシン。マイクロアーキテクチャ 1 種。
- 攻撃は示していない。
- FIPS 206 未発行なので、指摘は round-3 仕様書に対するもの。
