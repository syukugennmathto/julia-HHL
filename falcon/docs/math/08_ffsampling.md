# モジュール 8: ffSampling ― すべてが合流する場所

## 8.1 このモジュールのために前の 7 つがあった

署名が解くべき問題はこうである。目標点 `c`（メッセージのハッシュ）と
秘密の短い基底 `B` が与えられたとき、`c` に近い格子点を見つける。
ただし **`‖c − v‖` が `β²` を下回るほど近く**、かつ
**`B` を漏らさないよう乱択されて**いること。

古典的な答えは Klein/GPV サンプリングで、`B` の Gram-Schmidt 直交化を
最後の座標から順に降りながら、各座標で残差を中心とする Gaussian から
整数を 1 個引く。しかしこれは 1 署名あたり O(n²) で、
2n×2n の Gram-Schmidt 基底（n=512 なら倍精度で 1MB 超）が要る。

FALCON の貢献 ― 名前の "F" ― は、**同じことを O(n log n) 時間・O(n) 空間で**
やることである。2n×2n の実行列を直交化する代わりに、
**環の上で 2×2 行列を直交化し、対角成分を塔に沿って分割しながら再帰する**。
結果は葉が n 個の二分木で、サンプリングはその木を降りる歩行になる。

つまり:

- **`ffLDL` = 環の上の Gram-Schmidt**
- **`ffSampling` = 環の上の Klein アルゴリズム**

そして前の 7 モジュールで作ったもの ― `polysplit`、`splitfft`、随伴、
「**この**再帰木を持つ FFT」― は、**すべてこの 2 つの関数を書くために存在する**。

## 8.2 なぜ Cholesky ではなく LDL* なのか

Gram 行列 `G = B·adj(B)ᵀ` はエルミートかつ正定値なので
Cholesky 分解 `G = C·adj(C)ᵀ` を持つ。
**しかし Cholesky は平方根を要求し、環の元の平方根は環の元ではない。**

LDL* は代わりに `G = L·D·adj(L)ᵀ` と分解する（`L` は単位下三角、`D` は対角）。
平方根が要らない:

```
L10 = G10 / G00
D11 = G11 − L10·adj(L10)·G00
```

どちらも環の演算である。
**平方根が現れるのは最後、葉の上だけ** ― そこでは成分がただの正の実数に
なっているので、`normalize_tree!` が `‖b_i‖²` を `σ/‖b_i‖` に変える。

木が次数 1 まで降りる理由はこれである。
**対角成分がスカラーになるまで再帰し、そこで初めて平方根を取る。**

## 8.3 再帰の形

各ノードで `G` を `L·D·adj(L)` に分解し、`L10` を保存して、
2 つの対角成分に降りる。降りるとは:
`D00` を `split_fft` で塔に沿って分割して `(d00, d01)` を得て、
1 段下で 2×2 の Gram 行列を組み直す。

```
G0 = [ d00      d01 ]
     [ adj(d01) d00 ]
```

この行列は、`D00` を小さい体の上で見たときの
「`D00` 倍写像を基底 `{1, x}` で書いた行列」である。
**対角が等しく非対角が共役**というエルミートな形は、
まさに「環の元を掛ける」という操作の形であり、
だから再帰が閉じる。

## 8.4 順序が意味を持つ

`ffSampling` は **`z1` を先に**引き、それから中心を補正して `z0` を引く。

```
z1 ← sample(t1)
t0b = t0 + (t1 − z1)·L10
z0 ← sample(t0b)
```

これが Klein のアルゴリズムである。
第 2 座標を自分の Gram-Schmidt 幅で引き、
第 1 座標は `z1` の誤差のうち自分の方向に乗る分だけ再中心化する。

**順序を逆にしたり補正を忘れたりしても、
それなりに短いベクトルが返り、検証も通る。そして基底が漏れる。**
これを捕まえるテストは、参照実装との一致以外に存在しない。

## 8.5 補正ループの無い浮動小数点、その帰結を測った

モジュール 6 と 7 で立てた対比 ―
「Babai 縮約には補正ループがあるから浮動小数点が安全、
`samplerz` には無いから危ない」― の、**実測による決着がここで付いた。**

### 実験

我々の FFT の根は `cispi` で計算しており、**正しく丸められている**。
C 参照実装の表（27 桁）とも一致する。
一方 Python 参照実装の表は**有効数字 15 桁しかなく**、
n=512 で最大 370 ulp ずれている（#010）。

差は相対 1e-16。モジュール 5 のテストはどちらの表でも全部通る。
**この差が見えるようになるのが `ffSampling` である。**

記録した 6 本の ffSampling ベクタで測った結果:

| 使った根の表 | 参照実装と一致した本数 |
|:---|---:|
| 我々の `cispi`（正しく丸めた） | **1 / 6** |
| Python 参照実装の表を注入 | **6 / 6** |

**根の表の 1 ulp の違いが、署名を変える。**

### なぜそうなるか

`ffSampling` の中で、FFT の結果は**離散 Gaussian の中心 `μ`** になる。
`samplerz` は棄却ループの中で、`approxexp` の 64 ビット値を
乱数バイトと 1 バイトずつ比較する。
`μ` が 1 ulp 違えば `x` が 1 ulp 違い、比較対象の値が 1 ulp 違い、
**バイト比較の結果がときどき反転する**。
反転すれば別の整数が返り、以降の補正がすべてずれる。

補正ループが無いので、**ずれは直らない。増幅されるだけ**である。

### これが FN-DSA の話の全部

C 参照実装が浮動小数点を整数演算でエミュレートしているのは、
まさにこれを避けるためである。
`config.h` の *** CRITICAL SECURITY WARNING *** ―
「ネイティブ FPU はわずかな差異を生み、決定性を壊しうる。
署名の非決定性は壊滅的なセキュリティ障害につながる」―
の「わずかな差異」の正体が、**この 1 ulp** である。

そして序盤の問いへの答えが完成する。

> **NIST PQC 4 方式のうち、なぜ FN-DSA だけ標準化が遅れたのか。**

標準化とは「誰が実装しても同じ答えになる手順を書き下すこと」である。
ML-DSA も SLH-DSA も HQC も整数演算で閉じているので、それは容易だ。
FN-DSA だけが、**定数表の最下位ビットまで含めて手順を固定しなければ、
実装ごとに違う署名が出る**。しかも違う署名が出ることが、
単なる非互換ではなく**鍵の漏洩**を意味する。

そのうえで、その浮動小数点計算は同時に定数時間でなければならない（モジュール 7）。
この 2 つを両立させる規定を書くのに、他の 3 方式より 2 年余計にかかった。

## 8.6 検証 ― 木は目で見られない

n=512 の木は葉 512 個・内部ノード 511 個の複素ベクトルである。
**C 実装と目視で diff する、は計画になりえない。**
だから最初の計画段階で自分に課した方針どおり、
**トイ次数（n=8, 16, 32）を先に完全に通し、n=512 は性質で守る**。

使える性質が、ここでは異例に良い。

1. **Gram 行列がエルミートかつ正定値であること。**
   そうでなければモジュール 3 の随伴の符号が間違っており、LDL* は無意味。
2. **`L·D·adj(L)ᵀ` が `G` を再構成すること。**
   分解の定義式そのもので、参照実装を一切必要としない。
3. **葉の σ が `[σ_min, σ_max]` に入ること。**
   これは `samplerz` の前提条件そのものであり、
   鍵生成の Gram-Schmidt 上限 `1.17²q` が保証しようとしていたものそのもの。
   **モジュール 1・6・7・8 が 1 本のテストで繋がる。**
4. **サンプルした点が短い署名を与えること。**
   `(t − z)·B` のノルムが `β²` 以下。実測 `2.8e7` に対し `β² = 3.4e7`、
   理論値 `2n·σ² = 2.81e7` とぴったり合う。

4 について 1 つ間違えた。最初「残差 `t − z` の各係数が小さいはず」と思って
`< 8` を主張したが、実測は 32〜38。
**サンプリングは Gram-Schmidt 基底で行われるので、
係数ごとの残差は小さくない。** 小さいのは `(t−z)·B` のほうである。
GPV が保証しているのが何なのかを取り違えていた（#026）。

## 8.7 Dilithium との対比（まとめ）

| | Dilithium | FALCON |
|:---|:---|:---|
| 署名の作り方 | Fiat–Shamir + 棄却 | **格子上の Gaussian サンプリング** |
| 必要な前計算 | 無し | **ffLDL 木**（葉 n 個） |
| 直交化 | 不要 | 環の上の LDL*、O(n log n) |
| 木構造 | 無し | 部分体の塔そのもの |
| 浮動小数点 | 無し | **中心の計算に必須、補正なし** |
| 決定性 | 自明 | **定数表の最下位ビットに依存** |

Dilithium の署名は「引いて、確かめて、駄目なら引き直す」だけだった。
FALCON の署名は、鍵ごとに木を組み、その木を降りながら
n 個の Gaussian を引く。
**そして木の各ノードの値が、最下位ビットまで一致していなければならない。**
